実装に基づく重要な所見

秘密情報の種別と保存実態が一致していない

src/modules/settings/settings.service.ts は value: { value } と valueKind: "encrypted" をrepositoryへ渡す。SQLite repositoryは JSON.stringify(input.value) を保存し、Rust側の query_secret_value はJSONを読み出す。これはコードから確認した保存形式の問題であり、実際の秘密値を読み取った結果ではない。ログのredactionやHTTPの認証は、この保存時の保護とは別の対策である。

READMEのcompile例は再現可能な導入障害になっている

README / Getting Startedの例には --repo-path も --global もない。一方、src/cli/compile.ts:75 はどちらもない場合にエラーを返す。作業用の隔離ディレクトリで同じ引数を与え、Repository identity is required と終了コード1を確認した。リポジトリ分離を守るCLIの要件は妥当であり、公開例を追従させる必要がある。

加えて spec/docs/pub/operations.md のbackup例は --output を案内するが、現在のRust parse_backup_options が受け付けるのは --json と --require-idle。後者の不一致は静的確認であり、backupの実操作は行っていない。

改善用の実装が存在することと、既定動作が改善済みであることは異なる

CompileFoundationMode::from_env は未指定時に legacy を選ぶ。この経路は with_writer の中で検索から compose_context_response まで実行する。分離経路ではcomposeをWriterの外に置いており、改善の方向性と実装はある。今回、稼働中daemonの環境設定を調べていないため、実際のdaemonもlegacyで動いているとは断定しない。

search_knowledge_items はscope内のactive行を読み込み、本文を採点してから件数を絞る。条件を満たす行にはsource linkを個別取得する。小規模ローカルDBでは許容できる可能性があるが、知識数増加時の検索量とクエリ数は別途測るべきである。typed memory recallの1万行テスト成功を、このcompile経路全体の性能保証に読み替えてはいけない。

カバレッジ設定とE2Eには穴がある

vitest.config.ts のcoverage対象から context-compiler、knowledge、llm、queue/core、UIのTSXなどが除外される。これらにテストがないという意味ではないが、カバレッジの数値を製品全体の網羅率として使えない。今回、カバレッジ測定自体は実行していない。

e2e/admin-ui.spec.ts は expect(true).toBe(true) のみ。ほかに画面遷移・登録を試すテストはあるが、CIのverify workflowにPlaywrightが組み込まれていない。UIを開く前に検証を終える現状では、初回の操作成功を高く採点できない。
