Findingロジックの評価と改善候補

2026年9月6日時点のワークスペースを評価した。対象はFindingキューの候補抽出であり、Landscape Curationのfinding生成ではない。 結論は、トランザクション・実行権限確認・再試行の基盤はある一方、対応入力の選別、再抽出時の候補と下流評価の整合性、入力の秘匿化、出力異常の扱いに先に修正すべき問題がある、というもの。 抽出品質では、入口の語句スコアとRust／TypeScript間の契約差が取りこぼしを生む。

実装は変更していない。既存の未コミット変更を含む現在のコードを読み、実装から関数をそのまま抜き出した一時プログラムとメモリ内SQLiteで境界条件を検証した。 実稼働DB、外部LLM、他のCodexタスクは操作していない。以下の再現結果は不具合の成立条件を示すものであり、本番での発生件数やLLMの抽出精度を示すものではない。

評価範囲と良い点

Agent log取り込み時のenqueue判定、既存ログのbackfill、入力フィルター、LLMへの指示、候補parser、found_candidatesへの保存、Coveringへの引き渡し、再実行を確認した。 Rustの常駐executorとTypeScriptのdomain／queue workerには別々の実装がある。利用経路によって評価条件が変わるため、両方を対象とした。

  • Rust split処理はLLM呼び出しをSQLite writerから切り離し、外部I/O中にwriterを占有しない。
  • Rust splitの保存はprovider leaseの所有権を確認し、古い実行結果をdiscardする。
  • Rustでは候補保存とCoveringへのenqueueを同一トランザクション内で行う。
  • 自己取り込み防止、provider障害時のbackoff、procedureの最低限の構造検証がある。
  • TypeScriptにはparser診断、読んだ範囲、フィルター統計と、設定で有効にするCodex再評価の仕組みがある。

F1：処理可能な入力だけをclaimする

dynamic_provider.rs:478–486はsource接続に対し、knowledge_candidate、web_ingest、wiki_file、sourceを許可する。 executor.rsのqueue_spec_for_poolもsourceルートを候補に含める。 しかしfinding_executor.rs:116–121のexecute_findingはsource_targetかつvibe_memoryだけを処理し、それ以外をFailedにする。 非splitのprocess_jobにも同じ制約がある。

sourceルートがRust実行対象のproviderに割り当てられていると、wiki、web、提供済み候補のジョブをRustが獲得し、未対応入力として失敗させる。 TypeScript workerにはwiki／web／provided_candidateの分岐があるので、パイプライン全体で入力が禁止されているわけではない。 実稼働のルート設定と失敗件数は今回確認していない。

改善は、まずexecutorの対応能力をinput_kindとsource_kindの組で定義し、claimに同じ条件を適用すること。 未対応行を既存の対応workerへ渡す経路まで確認する。provided_candidateはLLM不要の登録経路として扱える。 全入力種別について、claimできた行は実行できること、対応workerが存在することを契約テストにする。

F2：再抽出の結果を世代で管理する

finding_executor.rs:869–895はjob IDと配列indexから候補IDを作り、同じindexの候補本文を上書きする。 一方、Coveringジョブはfound_candidate_idが既存なら作らない。 queue_lifecycle/state.rs:90のresumeはcompleted／skippedのジョブもpendingへ戻すので、正常終了後の再抽出も到達可能な操作である。

2候補を保存し、Coveringをcompletedにしてから1候補で再抽出すると、候補本文は更新されるが保存候補は2件のまま、pendingのCoveringは0件だった。 件数が減ると旧候補が残り、並び順が変わると同じIDが別知識を指す。既に済んだ評価や下流参照と、現在の本文が一致しなくなる。 既存テストはCoveringがpendingの間の上書きと件数だけを確認しており、completed後の再抽出を検証していない。

改善は、同じ結果の保存再試行と、新しい抽出を区別すること。source hash、抽出run ID、正規化した候補内容のhashを記録し、同じrunは冪等に保存する。 新しいrunでは候補を新しい世代として保存し、旧候補をsupersededにし、新しい内容に対するCoveringをenqueueする。 最低限でも、評価済み本文を同じIDで上書きしない不変条件を設ける。

必要な回帰テストは、同一結果の再送、候補の順序変更、2件から1件、1件から0件、Coveringがrunning／completedの状態での再抽出である。

F3：LLMへ渡す直前の秘匿化を共通の契約にする

finding_executor.rs:623–660の判定はapi_key、access_token、passwordなど一部の文字列に限られる。 DATABASE_URL=postgres://...、JSONの"apiKey":"..."、CLIの--token ...を含む架空入力は、一切変更されず通過した。 この文字列はrequest_candidatesのuser messageへ渡される。

TypeScriptのsrc/shared/utils/secret-redaction.tsは構造化キー、接続文字列、CLI引数、秘密鍵なども対象にしており、実行経路の切替で保護範囲が変わる。 実データの漏えいは確認していない。指摘は、未秘匿の値がvibe memoryまたはdiffに含まれる場合の送信境界の欠陥である。

改善は、両言語で同じ秘密値fixtureを使い、フィルター契約を一致させること。 入力本文、diff、関連metadataを組み立てた後にも秘匿化を適用する。実在する秘密値を検証ログへ残さず、削除形式と削除件数だけを診断に残す。

F4：候補なし、形式不正、出力途切れを区別する

finding_executor.rs:745–753はJSON復旧時に最初の開き角括弧と最後の閉じ角括弧でsliceする。 ] explanation [では開始位置が終了位置より後になり、ResultのErrではなくpanicした。 少なくともこの抽出呼び出しが通常の失敗分岐を通らなくなる。daemon全体が終了するかどうかは今回検証していない。

同じparserは{}、全候補が不正なJSON配列を正常な0件として返す。 さらに、20件の不正候補の後ろに正しい候補を1件置いても、検証前のtake(20)で正しい候補が落ち、0件になった。 保存側は空のCandidatesをskipped/no_candidateにするため、正しい判断による空配列と出力契約違反を区別できない。 TypeScriptも診断値はあるが、通常workerの最終状態は候補なしに集約される場合がある。

改善は、parserの返値にvalid_empty、valid_candidates、schema_invalid、truncatedを設け、panicしないJSON復旧にすること。 0件成功は明示的な空配列として扱い、不正候補の理由と件数は保存する。 providerのfinish_reasonも確認し、出力上限に達した応答は「知識なし」としない。 スキーマ違反の再生成は回数を制限し、全候補を検証してから有効候補の上限を適用する。

F5：メッセージ境界と根拠を保持して入力を削減する

Rustのフィルターは行頭が<INSTRUCTIONS>等の場合だけブロックを除く。 しかしRust agent log syncのbuild_readable_transcriptは各メッセージにUSER: 等を付けるため、メッセージ冒頭がタグならUSER: <INSTRUCTIONS>になる。 この形のブロック内部に置いた架空の指示文は残った。入力自身の指示が再利用可能な知識と誤認される余地を増やす。

同じ処理は各行を2,000文字で無表示に切り捨て、本文と全diffを結合後に32,000文字基準で中央を削る。 1行の2,100文字目以降に置いた根拠と、長い入力の中央に置いた根拠は、どちらもLLM入力から消えた。 Rustにはその続きのreaderがない。通常のRust取り込みは12,000文字を目安にchunk化するが、単独の長いメッセージや追加diffに対する問題は残る。

TypeScriptにはtoken window readerがあるが、その前のblock切り詰めで捨てた中央部分は追加readでも戻せない。 また長いTOOL／FUNCTIONブロックを全体除外するため、末尾のテスト結果などが失われる可能性は別途実ログfixtureで測る必要がある。

改善は、構造化されたroleと本文を保持してboilerplateを除去し、エラー・修正・検証のまとまりを読み取り単位にすること。 長いdiffは生成物を除外したうえで分割し、省略範囲と取得可能な参照を残す。 source hash、読んだ範囲、省略量を保存し、候補が0件でも未読部分が残る場合は完全評価済みと区別する。

F6：入口の語句スコアを再利用価値の判定と分ける

vibe-finding-eligibility.ts:20–31とRustのagent_log_sync/store.rs:363では、検証・失敗語が40点、混合roleが20点、preference語が20点で、通過点は50点。 継続的な好みを明示し、user／assistant両roleがある120文字超の入力は40点で両実装とも落ちた。 一方、120文字超の単なるbuild succeeded報告は、同じbuildが検証語40点とcommand語10点に二重加点され、両実装で通った。

通過した単発報告は後段のLLMが棄却できるが、入口で落ちた好みはLLMに届かない。 さらに短い高signal入力は、Rustでは75点で通過し、TypeScriptでは同じ75点でもcontent_too_shortで必ず棄却された。 TypeScriptにあるdiff加点もRustの判定には存在せず、backfillと通常取り込みの選別が一致しない。

改善は、継続的な好み・禁止事項・検証付きの原因と修正・diff根拠を独立した通過理由にし、文字数だけの必須条件を見直すこと。 同じ単語による二重加点を避け、評価はboilerplateを除いた内容で行う。 軽い入口判定は取りこぼしを減らす用途とし、後段LLMによる再利用価値判定と別の指標で測る。 しきい値を変更する前に、両言語共通のfixtureで判定を一致させる。

F7：prompt、parser、観測項目を同じ契約から作る

TypeScriptはcontexts/findCandidate/extract.context.tomlなどの管理対象promptを読み込む。 Rustのfinding_executor.rs:669は別の固定文字列で、procedureの2step以上という条件やnegative procedure禁止を明示しない。 しかしRust parserはその両方を必須にしているため、promptに従って生成できる出力を後段が捨てる不一致がある。 procedureを構成できない場合のruleへの整理方針もTypeScriptの指示に比べて省かれている。

Rustの候補には根拠の引用・位置がなく、originにはsourceの参照しかない。保存metadataにも入力の省略量、parser棄却理由、prompt digestはない。 TypeScriptにはreadRangesとparser診断があり、0件時のCodex再評価もあるが、Rust経路に対応する処理はない。 そのため、prompt更新やprovider変更の効果と入力不足・形式不正を分けて分析しにくい。

改善は、管理対象contextからRust／TypeScriptの指示を生成し、受理schemaと同時に検証すること。 共通の境界fixtureとprompt digestを持たせ、source hash、モデル、raw件数、有効件数、棄却理由、読了率をrun単位で記録する。 candidateごとの根拠位置は後段Coveringと責務を合わせて導入し、Findingで最終的な真偽や信頼度まで確定させない。 再評価機能を維持するなら対応経路を明示し、まず形式修復や未読部分の補完と、より強いモデルへの再評価を分ける。

改善の進め方と受け入れ条件

  1. F1〜F4を先に修正する。未対応入力を誤claimしない、完了済み評価と本文がずれない、秘密値fixtureが通過しない、不正JSONでもpanicせず原因が残ることを確認する。
  2. 両言語の入力・出力・promptの共通fixtureを整える。短文、長文、否定ルール、2step未満のprocedure、role付き指示タグ、diff、切れたJSONを含める。
  3. F5〜F7の品質調整を行う。同じsource集合で旧方式と新方式を比較し、拒否理由・省略量と後段の結果まで追跡する。

品質評価用には、継続的な好み、原因・修正・検証を含む会話、否定された方針、diff中心の記録、単発報告、boilerplate中心の入力、長文を層別して人手で正解ラベルを付ける。 入口で落ちた入力も抽出してラベル付けしなければ、取りこぼし率は測れない。比較集合はsession単位で分け、同じ会話断片が調整用と評価用に重複しないようにする。
