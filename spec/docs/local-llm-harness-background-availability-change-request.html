local-LLM-harness Service Activity連携契約

ContextStillがSAAAを含む他サービスとlocal-LLM-harness（LARM）を安全に共有するための、 LARM側live配備条件とContextStill側の受信契約を定める。Profile単位では判定せず、 LARM全体の利用状況をservice activityで判定する。

固定判断: ContextStillはSAAAへ通知、callback、webhookを送らない。 LARMが集約する全serviceのactivityをjob境界で確認し、freshなidleかつworkload 0の場合だけ 新しい処理へ進む。

1. Service Activity request

GET /v1/activity HTTP/1.1
Cache-Control: no-cache
  • query parameterを付けない。
  • request bodyを送らない。
  • Profile、audience、Connection IDによる除外を要求しない。
  • timeoutはContextStillの接続設定で制限する。
  • CONTEXT_STILL_LARM_API_TOKENが設定されている場合だけ Authorization: Bearerを付ける。未設定ならAuthorization headerを送らない。

2. Response contract

{
  "contractVersion": "larm-service-activity.v1",
  "state": "idle",
  "activeWorkloads": 0,
  "observedAt": "2026-09-06T12:34:56.789Z",
  "validForMs": 1000,
  "retryAfterMs": 0,
  "reservationGuaranteed": false,
  "bootEpoch": "epoch-...",
  "configRevision": "..."
}

ContextStillは未知fieldを拒否し、contract version、時刻、validity、count、state、retry hint、 reservation flag、boot epoch、config revisionをstrictに検証する。期限切れ、5秒を超える未来時刻、 不正値、非200、timeout、通信errorはすべてfail closedで待機扱いにする。 401をidleへ変換せず、旧static Providerへfallbackしない。

Job開始判定
受信状態 ContextStillの動作
idleかつactiveWorkloads === 0 Profile discoveryまたは次jobへ進む
activeかつcount 1以上 Connectionを新規作成せず、retry hint以降に再確認する
draining 新規処理を開始せず待機する
invalidまたはerror fail closedで待機する

activityは短時間だけ有効なsnapshotであり、予約ではない。idle確認後の競合はAgent Connection 作成時のLARM admissionで最終判定する。

3. Profile discoveryとConnection lifecycle

  1. Queueに対象routeのdue jobがある場合だけservice activityを取得する。
  2. idleの場合、GET /v2/agent-profilesでProfileとaudienceを確認する。
  3. catalog revisionがactivityのconfigRevisionと一致することを確認する。
  4. contextstill-backgroundが存在し、deprecatedでないことを確認する。
  5. HTTP SSEはOpenAI互換contractの一部として扱い、WebSocket専用の streamingProtocol広告をProfileの必須fieldにしない。
  6. POST /v1/agent-connectionsでConnectionを作成する。
  7. readyをpollし、claimして短期credentialとendpointをmemory上だけで使用する。
  8. 必要ならrenewし、Queue idle、構成変更、resident終了時にDELETEする。

createではallowFallback: false、 deploymentPolicy: existing-onlyを維持する。従来の静的Providerへ暗黙にfallbackしない。

4. Job境界

Provider response bodyを読み終えてjob結果を確定した後、次jobをdequeueする前に GET /v1/activityを再実行する。実行中jobはactivityの変化だけでは中断しない。 次の観測がactive、draining、error、invalidならConnectionを解放し、新規jobを開始しない。

5. Live配備待ち

2026-09-06のlive確認では、GET /v1/activityは401を返し、 Profile catalogにcontextstill-backgroundは存在しない。ContextStill側sourceは contractへ整合済みだが、恒久Queue自動消化は次の条件を満たすまで有効化しない。

  • ContextStillが利用できる形でGET /v1/activityがlive配備される。
  • contextstill-background Profileがlive catalogへ追加される。
  • JSON応答品質canaryが合格する。

6. Acceptance

  • activity requestのpathが正確で、queryとbodyがない。
  • freshなidleかつcount 0の場合だけcreateする。
  • active、draining、HTTP error、timeout、未知field、stale responseではcreateしない。
  • 次job前にactivityを再確認する。
  • Queueが空ならactivityをpollしない。
  • Connection lifecycle、静的Providerのroutingとrequest contractに回帰がない。
  • optional Bearerは設定時だけ送られ、401はfail closedになる。
  • 動的ProviderはclaimされたURL、model、短期tokenだけを使い、 127.0.0.1:44448へ接続しない。
  • startupログでProvider kind、control host、Profile、audienceをsecretなしで確認できる。
