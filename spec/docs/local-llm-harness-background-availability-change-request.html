local-LLM-harness Background Provider Availability API 変更依頼書

Status

Status: proposed

Created: 2026-09-06

Request ID: larm-background-provider-availability-v1

依頼先: local-LLM-harness。依頼元: ContextStill。

1. 依頼概要

ContextStillが背景LLM処理を開始してよいかを、SAAAからの通知に依存せず local-LLM-harness（以下LARM）へ問い合わせられるAPIを追加してください。 ContextStillはqueueに実行可能なjobがある間だけこのAPIをポーリングし、 LARMが利用可能と返した場合に限って既存のAgent Connection APIでproviderを確保します。

本依頼で固定する判断は次のとおりです。

  • LARMをproviderの利用可能性に関する唯一のauthorityとする。
  • SAAAからContextStillまたはLARMへの通知、callback、webhookは追加しない。
  • read-onlyな空き判定はadvisoryとし、接続作成時の原子的なadmission判定を置き換えない。
  • 背景処理の開始可否はAgent Profileに紐づくpolicyとしてLARM側で管理し、 ContextStillへruntime内部構造や利用者情報を公開しない。
  • foreground側の利用がjob実行中に始まっても、そのjobを途中で強制中断しない。 新しいjobを開始する境界で再判定する。

2. 確認済みbaseline

2026-09-06時点のLARM sourceとlive APIでは、次の基盤がすでに存在する。

  • GET /v2/agent-profilesによるProfile discovery。
  • POST /v1/agent-connections、status poll、claim、renew、deleteからなる Agent Connection lifecycle。
  • admission時のmemory headroom、runtime allocation数、swap group、transition状態の検査。
  • backend observerとsemantic readinessが保持するBUSY、 ready、acceptingRequests等のlive signal。
  • llm-agent-worker routeと、1 allocation／1 requestに制限された qwen-worker-agent runtime。

一方で、Profile単位で接続作成前に利用可能性を問い合わせる狭い公開APIはない。 management向けinspection APIやmetricsは、権限・公開範囲・契約安定性の点から ContextStillの制御入力には使用しない。

3. 追加するAgent Profile

config/local-node/agent-connections.yamlへ contextstill-background Profileを追加してください。公開契約として必要な意味は 次のとおりです。YAMLの内部表現は既存schemaに合わせて調整して構いません。

Table: ContextStill background profile
項目 要求値
Profile ID contextstill-background
Audience saaa-desktop
Route llm-agent-worker
Fallback 禁止。allowFallback=false
Deployment 既存artifactのみ。existing-only
Selection 明示Profile指定のみ
Workload class background
Foreground protection llm-defaultに解決される保護対象runtimeがBUSYの場合は開始不可

foreground protectionはSAAA processやSAAA connectionの存在ではなく、LARMが直接観測する protected routeの実行activityで判定する。単にSAAAのAgent Connectionが存在するだけで backgroundを恒久的に止めてはならない。

4. Profile availability API

4.1 Request

GET /v2/agent-profiles/contextstill-background/availability?audience=saaa-desktop
Cache-Control: no-cache

既存のbackground connectionを再利用中は、次のように currentConnectionIdを指定できるようにしてください。 

GET /v2/agent-profiles/contextstill-background/availability?audience=saaa-desktop&currentConnectionId=ac_123
  • audienceは必須とする。
  • currentConnectionIdは任意とし、同じprincipal、Profile、audienceに属する 非terminal connectionだけを受理する。
  • current connectionを指定した場合、そのconnection自身のallocationは 「新規allocation枠が埋まっている」という判定から除外し、再利用可能性を評価する。
  • protected foreground runtimeのBUSY状態、他connection、resource headroom、drain、 transitionは除外しない。
  • このGETによってCOLD runtimeを起動したりallocationを作成したりしてはならない。

4.2 Response

正しく評価できたdomain stateは、状態にかかわらずHTTP 200で返す。

{
  "contractVersion": "agent-profile-availability.v1",
  "agentProfile": "contextstill-background",
  "audience": "saaa-desktop",
  "state": "available",
  "reasonCode": "available",
  "observedAt": "2026-09-06T12:34:56.789Z",
  "validForMs": 1000,
  "retryAfterMs": 0,
  "reservationGuaranteed": false,
  "catalogRevision": "...",
  "bootEpoch": "..."
}

ResponseにはCache-Control: no-storeを付ける。 retryAfterMsが正の場合はHTTP Retry-Afterも可能な範囲で付ける。

4.3 State semantics

Table: Availability states
state 意味 代表的reasonCode client動作
available 現在のsnapshotでは、fallbackやpreemptionなしにProfileの新規作成または指定connectionの再利用が可能 available Agent Connection作成または次job開始へ進む
busy 一時的な競合によりbackgroundを開始できない protected_runtime_busy、runtime_allocation_busy、 swap_group_busy、resource_exhausted retryAfterMs以降に再評価する
unavailable Profile、route、artifact、audienceまたは構成上の理由で利用できない profile_disabled、unsupported_audience、 no_eligible_provider、artifact_unavailable 長いbackoffとoperator向け警告
unknown 安全な判定に必要な観測値が揃わない stale_observation、transition_in_progress、 draining、observer_error fail closedで待機する

path、query、principal、current connectionの検証に失敗した場合は既存API規約に従って 400、403、404、409または 410を返す。daemon自身が評価不能な場合は503とし、clientは unknown相当に扱う。

4.4 Evaluation rules

availability handler専用の判定を複製せず、Agent Connection作成時のadmission evaluatorと 同じcoreをread-only modeで利用してください。availableには少なくとも次をすべて要求する。

  1. Profile、audience、route、artifactが有効である。
  2. deploymentを追加せず、fallbackを使わずにcandidateが解決できる。
  3. protected routeのlive observationがfreshで、実行中activityがない。
  4. 対象runtimeとswap groupに、current connection以外の競合allocationがない。
  5. memory headroomとruntime allocation capacityを満たす。
  6. drain、mutation、transition、observer errorのいずれでもない。

protected routeの「activity」は、可能ならrequest gateまたはbackendのBUSY signalを利用する。 health endpointへの単純なTCP到達性や、Agent Connectionの存在だけをactivityとみなさない。

5. Atomic admissionとの関係

availability responseは短時間で失効する観測結果であり、reservationではない。 available取得後に別clientやforeground requestが開始する競合は正常系として扱う。

  1. ContextStillがavailabilityをGETする。
  2. availableなら既存のPOST /v1/agent-connectionsを呼ぶ。
  3. LARMはPOST時点の最新状態で原子的なadmissionを再評価する。
  4. 競合していれば既存のstructured errorで拒否し、ContextStillは待機へ戻る。

availability GETとconnection POSTを一つのtransactionに見せる必要はない。 reservationGuaranteed: falseを恒久contractとして明示する。

6. Security and privacy

  • management inspection tokenをContextStillへ渡す設計にしない。既存Agent Connection APIと同じ local lifecycleの認証・到達範囲を利用する。
  • responseへclient ID、prompt、model出力、他connection ID、process情報、VRAM内訳を含めない。
  • currentConnectionIdから他principalのconnection存在を推測できないよう、 ownership不一致時のerror形状を既存規約へ揃える。
  • availability responseとerror responseはすべてno-storeとする。
  • logにはProfile、state、reasonCode、duration、revisionだけを残し、credentialを残さない。

7. Compatibility

  • 既存/v1および/v2/agent-profiles responseを破壊的に変更しない。
  • coding-defaultとcompatibility aliasのselection、claim、renew、delete契約を変更しない。
  • availability policy未設定のProfileに対するendpointは、明示的な unavailableまたは404のどちらかに統一し、曖昧なavailableを返さない。
  • API追加後もPOSTを直接呼ぶ既存clientをサポートする。

8. 実装ガイダンス

責務は次のように分離する。

Table: Suggested ownership
責務 推奨owner
HTTP parse、strict query validation、response mapping Agent Connection API route/controller
Profile policy解決 Agent Profile catalog/service
candidate、headroom、allocation、swap group判定 既存admission evaluator
protected route activity backend observer／semantic readiness
current connection ownershipと再利用判定 Agent Connection lifecycle service

observer snapshotのfreshness上限はLARM側で決め、responseの validForMsへ反映する。ContextStillが独自にbusy判定規則を再実装する前提にしない。

9. 必須test

9.1 Contract tests

  • unknown Profile、unsupported audience、余分なquery fieldをstrictに拒否する。
  • すべてのstateでschema、enum、timestamp、revision、no-store headerを固定する。
  • 既存Profile catalogとAgent Connection fixtureが変化しない。

9.2 Policy tests

  • protected runtimeがIDLEかつcapacity十分ならavailable。
  • protected runtimeがBUSYならprotected_runtime_busy。
  • protected observationがstaleならunknown。
  • 別connectionがworker allocationを保持していればbusy。
  • current connectionが同じProfileを保持している場合は、自身のallocationを除外して再利用可能性を返す。
  • 他principalまたは別Profileのcurrent connection指定を受理しない。
  • swap group transition、drain、resource exhaustionをfail closedで分類する。

9.3 Race and lifecycle tests

  • available取得直後に競合し、POSTが拒否されるraceを正常系として固定する。
  • 同じidempotency keyのPOST replayが既存どおり同じ結果を返す。
  • renew後のcurrent connection指定で再利用可能性を正しく評価する。
  • delete済みまたはexpired connectionの指定を安全に拒否する。
  • GET availabilityだけではruntimeがCOLDから変化しない。

10. Acceptance criteria

  1. live LARMでcontextstill-backgroundが GET /v2/agent-profilesに公開される。
  2. foreground runtimeのIDLE／BUSYを切り替えるcanaryで、availabilityが期待stateへ遷移する。
  3. available時だけAgent Connectionを作成でき、競合時はPOSTの原子的判定が拒否する。
  4. current connection指定によって、同一connectionを使った複数jobの境界判定ができる。
  5. availability pollがSAAA API、SAAA process、SAAA callbackに依存しない。
  6. 既存Agent Connection contract testとlocal-node smoke testがすべて通る。

11. Non-goals

  • SAAAからのactivity通知、callback、webhook。
  • ContextStill queueの状態管理をLARMへ移すこと。
  • 実行中generationの強制cancelまたはpreemption。
  • management inspection APIやmetricsをclient向けcontrol contractへ転用すること。
  • background Profileからresident foreground modelへfallbackすること。
  • availability GETによるresource reservation。

12. 依頼する成果物

  1. Profile availability contractを記載したLARM Spec HTML。
  2. contextstill-background Profileとbackground policy設定。
  3. read-only availability endpointと共有admission evaluator。
  4. contract、policy、race、lifecycleの自動test。
  5. local-nodeでのIDLE／BUSY／connection reuse canary結果。
