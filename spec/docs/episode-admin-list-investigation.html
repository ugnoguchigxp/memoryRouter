Episode管理一覧の空表示と取得遅延の調査

2026年9月6日にローカル稼働環境を調査した。SQLiteの簡易整合性検査は正常であり、Episodeの消失やDB破損の兆候は確認されなかった。

空表示の原因と修正

DBにはactiveのEpisodeが6,826件あり、全件がrepo scopeだった。分類済みは5,985件、未解決は841件、globalは0件だった。管理一覧APIはAI検索用のsearchEpisodesを呼んでおり、プロジェクト指定のないリクエストにglobal-only制約と分類済み制約を適用していた。その結果、認証済みGET /api/episodes?status=active&limit=100はHTTP 200と空配列を返していた。

管理一覧専用のlistEpisodesForAdminを追加し、プロジェクト未指定時に全プロジェクトと未解決の記録を閲覧できるようにした。明示的なプロジェクト条件、状態、検索語、facet条件は維持する。AI検索のsearchEpisodesは従来のrepository isolationを維持し、管理一覧への切替フラグは公開入力に追加しない。

取得遅延の測定と改善

一覧表示復旧後のAPIを連続測定すると約230〜330msだった。100件の表示に対して6,826件の本文とメタデータ約25MB、および参照情報を読み込み、JSON解析、検証、並べ替えを実施していた。これは毎回の取得に不要な負荷を生んでいた。

SQLiteの条件なし管理一覧では、日付と品質の順にIDを最大100件選んでから本文と参照を取得するようにした。SQL形式、ISO形式、unix-ms形式の保存日時を同じ時刻として並べ替える。検索語などによる順位付けが必要な検索では、検索対象を事前に切り捨てない。

修正反映直後の初回は320ms、その後4回は76ms、42ms、38ms、37msだった。レスポンスは100件、約896KB。ユーザーが体感した非常に長い初期待ち時間は測定中に再現できず、その原因まで断定していない。開発サーバーの初回変換やブラウザー側の負荷が原因であるとの裏付けも得ていない。

検証

  • DBを読み取り専用で開き、PRAGMA quick_checkはokだった。
  • 修正後APIの100件のID順序は、DB全件から独立して日付・品質順に計算した最新100件と5回とも一致した。
  • ブラウザーで100 cardsと1ページ25行の表示を確認し、Refreshでも一覧表示を維持した。
  • PostgreSQLとSQLiteのrepository回帰テストで、管理一覧の全プロジェクト表示とAI検索の隔離を検証する。
  • 実SQLiteの一時DBで、混在日時形式、未解決記録、件数制限、同日時の品質順、参照取得、検索、プロジェクト条件、deprecated条件を検証する。

残る制約

管理画面は従来どおり最大100件を取得し、25件ずつ表示する。全6,826件をページ送りで閲覧できる仕様には変更していない。検索条件付き取得には全候補の読み込みが残り、今回の高速化は条件なしのSQLite管理一覧が対象である。
