LANDSCAPEの重複候補、到達不能、陳腐化、適用範囲不良を継続的に整理する第6のvisible queueとして、landscapeCurationを実装する。本仕様はプロジェクト開始をGOとし、個々のactionに対する自動実行権限をruntime gateで段階解放する。

0.1 Autonomous decision override

Version 1.2では、人間承認をCurationの処理条件から除外する。LLM評価とdeterministic policy gateが揃った時点で、jobは自動終端、安全な既存下流queueへの委譲、または証拠不足／未対応actionとして終端する。awaiting_human、human_review、request_human、human decision APIおよびhuman action UIは新規jobでは使用しない。本文の旧記述と競合する場合は本節を優先する。

  • keep_separate / observeはrecord_only / completed。
  • merge_review / deprecate_duplicateはconfidence、blocker、input参照、status、type、polarity、repository identityのgateをすべて満たし、bodyとnormalized appliesToが完全一致する場合だけ既存Merge Reviewへ自動委譲する。semantic duplicateはV1では自動mutationしない。
  • Merge Reviewの結果がmerge_recommended / high、blockerなしで、提案bodyが現在のcanonical bodyと完全一致する場合だけFinalizeへ自動委譲する。条件不足はterminal outcomeとして記録し、ユーザー確認へ送らない。
  • needs_evidenceはawait_evidence / skipped。
  • V1で安全な自動actionを持たないrepair_scope / escalateはblocked / skipped。人間判断待ちにはしない。
  • LANDSCAPE画面は永続queueからpending / running / paused / failedとcompleted / awaiting_downstreamを未処理として表示し、ユーザー操作を要求しない。

LLMはKnowledgeを自由に変更するagentではない。deterministic detectorが固定した候補とevidenceを評価し、typed action planを返すcuratorである。mutationの許可、対象scope、実行順序、完了判定、rollbackはdeterministic codeが所有する。

本文のうち、4.1〜4.4節と20節以降を実装時のnormative contractとする。その他の節は目的と設計意図を示し、値、型、状態遷移、ファイル配置、API、実装順がnormative contractと競合する場合はnormative contractを優先する。未確定事項を実装担当へ委ねないため、本仕様に記載のない自動mutationはV1へ追加しない。

1. Goals

  • LANDSCAPEに継続的に発生するreview対象を、人間の常時監視なしでtriageする。
  • 重複Knowledgeをscope-awareに発見し、安全なcanonicalization pathへ送る。
  • 到達されないKnowledgeを、不要、適用範囲不良、根拠不足、需要未観測に分ける。
  • deterministicに修復できる問題はLLMを使わず、自動maintenanceへ送る。
  • 曖昧または高影響なcaseは自動mutationせず、理由付きblocked outcomeとして記録する。
  • すべての判断、mutation、下流job、postcheck、rollbackを追跡可能にする。

2. Non-goals

  • LLMが全Knowledgeを自由探索し、任意のKnowledgeを生成、削除、統合する仕組みにはしない。
  • repository eligibilityをLLMに判断させない。
  • source根拠やusage signalがないことだけを理由に、Knowledgeを自動deprecateしない。
  • cross-repository Knowledgeを自動mergeしない。
  • 既存Coveringのingress dedupe、Merge Review、Finalizeを置き換えない。
  • 通常のKnowledge生成queueより高いpriorityで実行しない。

3. System position

Queue DashboardにはFinding、Episodes、Covering、Merge Review、Finalizeに続く6番目のvisible tabとしてCurationを追加する。内部には既にhiddenなmergeActivationFinalizeがあるため、technical queueとしては7番目になる。

  1. LANDSCAPE snapshotまたは関連eventがcuration findingを生成する。
  2. landscapeCurationがfindingとevidence snapshotをclaimする。
  3. deterministic preflightがeligible scopeとevidence completenessを検証する。
  4. 必要なcaseだけをLLM curatorが評価する。
  5. deterministic policy gateがdispositionを決める。
  6. non-destructive actionは記録またはmaintenanceへ送る。
  7. mergeは既存Merge ReviewとFinalizeへ送る。
  8. mutation後のpostcheckが成功した時点でcuration jobを完了する。

4.1 Finding materialization contract

4.1.1 Review item mapping

Producerはstatusがpendingまたはreviewingで、knowledge_idが存在するreview itemだけをqueue候補にする。knowledge_idがnullのcommunity-level itemはCurationへ展開せず、LANDSCAPEの未処理項目として表示する。

Table: Existing review reason to curation finding
Review reason Finding type Candidate source
duplicate_candidate duplicate_candidate payload.candidateKnowledgeIds
dead_zone_reachability_risk reachability_gap same-repository semantic neighbor上位5件
dead_zone_stale stale_knowledge same-repository active semantic neighbor上位5件
negative_attractor_candidate、wrong_review_required、over_selected_not_used、baseline_off_topic、baseline_wrong applicability_issue review itemのsuggestedAppliesToとsame-repository neighbor
contradiction_review contradiction_candidate payload.rightKnowledgeIdの1件だけ

used_baseline_lost、baseline_missing_after_recompile、semantic_reachable_dead_zone、semantic_split、semantic_merge、relation_orphan、promotion_gate_reviewはV1 producerの対象外とする。これらを自動的にsubjectへ分解する処理は追加しない。

4.1.2 Duplicate detector

既存review itemにduplicate候補がないため、producer実行時にdeterministic detectorを1回実行し、候補ごとにlandscape_review_itemsをidempotentにmaterializeする。

  1. statusがactive、classificationStatusがclassifiedのrule / procedureだけを対象にする。
  2. repository identityはprojectRef → repoKey → repoPathの既存優先順位で解決する。identityが異なるpairは比較前に除外する。globalとrepoを組み合わせない。
  3. exact候補はnormalize(title) + "\n" + normalize(body)のSHA-256が一致するpairとする。normalizeはUnicode NFKC、trim、連続whitespaceの1文字化、英字lowercaseだけを行う。
  4. semantic候補はcosine similarity 0.92以上、同じtype、同じpolarity、scope overlap 0.8以上とする。各subject最大5件に制限する。
  5. scope overlapはtechnologies / changeTypes / domainsのJaccard平均とする。両方空のfacetは計算から除外し、全facetが空なら1.0とする。repo identityはscoreへ含めず、事前一致を必須にする。
  6. group内のcanonical候補は、status active、source link数、90日used数、compileSelectCount、updatedAtの順に降順、最後にID昇順で決める。
  7. canonical以外をsubjectとしたreview itemを作る。reasonはduplicate_candidate、proposedActionはsplit_or_merge_review、payloadへcanonical ID、candidate IDs、similarity、exact flag、detectorVersionを保存する。
  8. review itemのidempotency keyはsemantic_relation_comparison:duplicate_candidate:{subjectId}:{canonicalId}:v1とする。

4.1.3 Subject and candidate rules

  • subjectはactiveまたはdraftだけを許可する。deprecatedはskipped / not_eligible。
  • candidateはactiveだけを自動action対象にし、draftまたはdeprecatedはevidence表示だけに使う。
  • candidate listはID昇順でdedupeした後、similarity降順、usage降順で最大5件にする。
  • subjectとcandidateのrepository identityが一致しないjobは作らない。worker preflightでも同じ判定を繰り返す。
  • 作成からnewKnowledgeObservationDays未満のKnowledgeはduplicate exact match以外enqueueしない。

4.2.4 Immutable input snapshot

snapshotは次のtop-level keyを必須とし、job作成後は書き換えない。

  • schemaVersion: 1、capturedAt、finding、versions
  • subject: ID、title、body、bodyHash、status、type、polarity、scope、classificationStatus、projectRef、repoKey、repoPath、appliesTo、appliesToHash、confidence、importance、timestamps
  • candidates: subjectと同じfields、similarity、scopeOverlap。最大5件。
  • evidence: { id, kind, knowledgeId, value, observedAt, source }のarray。IDはev:{kind}:{knowledgeId}:{window}形式。
  • usage: subjectとcandidateごとの30日・90日selected、used、notUsed、offTopic、wrong、uniqueUsedRun IDs。
  • lineage: source link ID、origin link ID、件数、最新source timestamp。
  • reviewItem: ID、source、reason、suggestedAppliesTo、evidence、payload。
  • capabilities: backend、vectorAvailable、semanticComparisonAvailable、contradictionAvailable。

workerはmutationまたは下流enqueueの直前にsubjectとcandidateのbodyHash、appliesToHash、status、repository identityをreadbackする。差分が1つでもあればskipped / stale_inputにし、古いresultを適用しない。

4.2.5 Job detail response

job detailはqueue rowの全scalar、typed result、policy result、mutation plan、postcheck、rollback、job links、関連review itemを返す。body全文を含むためgeneric /api/queue listには含めず、専用detail endpointだけで返す。

4.3 Producer algorithm

4.3.1 Entrypoints

  • CLI bun run queue:curation:enqueue:dry-runはwriteせず、candidate数、budget除外、cooldown除外、作成予定jobをJSON出力する。
  • bun run queue:curation:enqueue:writeだけがreview itemとqueue jobを作る。
  • continuous queue supervisorは起動時とproducerIntervalMinutes経過時にwrite producerを呼ぶ。前回tick実行中なら次tickをskipする。
  • runtime settingのproducerEnabled=falseならCLI dry-run以外は何も作らない。

4.3.2 Exact steps

  1. runtime settingsを毎tick再読込し、enabled、budget、cooldownを解決する。
  2. duplicate detectorを実行し、review itemをidempotentにmaterializeする。
  3. 4.1.1節に該当するreview itemをpriority降順、updatedAt昇順で最大scanLimit件読む。
  4. subject、candidate、usage、lineage、capabilityをbatch loadする。loop内の1件ずつqueryは禁止する。
  5. subject eligibilityとrepository identityを検証し、invalid itemはjobを作らずskip reasonを集計する。
  6. snapshot、evidence hash、fingerprint、cooldown bucket、idempotency keyを計算する。
  7. active fingerprint、cooldown、daily global、daily repository budgetを順に確認する。
  8. transaction内でqueue rowをinsertし、review itemがpendingならreviewingへ変更する。
  9. enqueuedeventへfindingType、reviewItemId、subjectId、fingerprint、producerVersionを記録する。

4.3.3 Priority

base priority:
  contradiction_candidate = 95
  applicability_issue      = 85
  duplicate_candidate      = 75
  reachability_gap         = 65
  stale_knowledge          = 45

adjustment:
  +10 if wrongCount90d > 0
  +5  if offTopicCount90d > 0
  +5  if exactDuplicate
  -10 if evidence count < 2
final priority = clamp(0, 100, base + adjustment)

budget消費順はpriority降順、review item updatedAt昇順、subject ID昇順で固定する。repository別budgetはresolved identity key単位で数え、global Knowledgeはglobalという1 bucketにまとめる。

4.4.3 Constraints and indexes

  • landscape_curation_queue_idempotency_uniqueをidempotency_keyへ作る。
  • landscape_curation_queue_active_fingerprint_uniqueをfingerprintへpartial uniqueで作り、statusがpending / running / pausedの行だけを対象にする。
  • claim用に(status, next_run_at, priority DESC, created_at)、Knowledge表示用に(subject_knowledge_id, updated_at DESC)、cooldown用に(fingerprint, created_at DESC)をindex化する。
  • link tableは(curation_job_id, role)をunique、(queue_name, queue_job_id)をindex化する。同一roleを再作成せずupsertする。
  • PostgreSQLは全JSON columnへjsonb_typeof checkを付ける。
  • SQLiteはJSON object columnへjson_valid(column) AND json_type(column) = 'object'、array columnへjson_type(column) = 'array'を付ける。
  • migrationはdistillation_queue_events_queue_name_checkを全7 technical queue名で再作成する。event type checkにはphase_changed / policy_decided / downstream_linked / rollback_started / rollback_completedを追加する。

4.4.4 Fingerprint and cooldown

fingerprint = sha256(
  "curation:v1" + findingType + subjectKnowledgeId
  + sort(candidateKnowledgeIds).join(",") + evidenceHash
)

bucket = floor(nowEpochSeconds / (cooldownDays * 86400))
idempotencyKey = "landscape-curation:" + fingerprint + ":" + bucket

evidenceHashはbody hash、appliesTo hash、status、repository identity、usage集計、source count、similarity、review reasonをkey順にcanonical JSON化して計算する。generatedAt、queue status、provider、modelは含めない。同一fingerprintのactive jobがある場合、または最新terminal jobからcooldownDays未満の場合はenqueueしない。

5. Finding producer contract

Finding producerは、日次snapshot、Knowledge finalize、usage threshold到達、source verification更新から起動できる。大量scanをそのままLLM callへ変換してはならない。

  • 同一findingはfindingType + subjectKnowledgeId + candidateIds + evidenceVersionでfingerprint化する。
  • active jobまたはcooldown中の同一fingerprintを再enqueueしない。
  • 1日あたりの新規job数、repository別件数、LLM token budgetに上限を持つ。
  • high-impact negative feedback、exact same-scope duplicate、stale retryを優先する。
  • 新規Knowledgeには最低観測期間を置き、作成直後の未選出をDeadZone処分候補にしない。

初期defaultはdaily 100 jobs、repositoryごと20 jobs、同一finding cooldown 30日とする。値はruntime settingsで変更可能にする。

6. Job input snapshot

各jobは、判断時点の入力をimmutable snapshotとして保存する。

  • finding ID、type、reason、priority、producer version、snapshot ID
  • subject KnowledgeのID、title、body、body hash、type、status、scope、repository identity
  • subjectのappliesTo、importance、confidence、created / updated / verified timestamps
  • 最大5件のcandidate Knowledgeと同じsnapshot fields
  • lexical similarity、vector similarity、relation / semantic community evidence
  • 30日・90日のcompile candidate、selected、used、not_used、off_topic、wrong集計
  • source link、origin link、source freshness、embedding capability
  • 関連replay caseとbaseline結果
  • detector、policy、prompt、model routeのversion

body hash、status、repository identityのいずれかが実行時に変化していた場合、古いLLM判断を適用せずstale_inputとして再評価する。

7. Deterministic preflight

  • subjectが存在し、対象statusであり、他のactive curation mutationに所有されていない。
  • repository-scoped Knowledgeでは、candidateが同じcanonical repository identityに属する。
  • global Knowledgeとrepository Knowledgeを自動merge candidateにしない。
  • 必要なembedding、similarity、usage、source capabilityが利用可能である。
  • SQLiteでsemantic retrievalとcontradiction detectionが利用可能である。
  • evidence不足をsemantic verdictへ変換せず、needs_evidenceへroutingする。

preflight failureはprovider failureとして数えず、repairable、unsupported、stale、policy blockedに分類する。

8. LLM curator contract

LLMは次のschemaに適合するJSONだけを返す。

{
  "schemaVersion": 1,
  "decision": "merge_review | deprecate_duplicate | repair_scope | keep_separate | needs_evidence | observe | escalate",
  "confidence": "low | medium | high",
  "canonicalKnowledgeId": "input candidate id or null",
  "rationale": ["short evidence-based reason"],
  "supportingEvidenceIds": ["input evidence id"],
  "counterEvidence": ["reason against the proposed action"],
  "blockers": ["blocking condition"],
  "proposedAppliesTo": {},
  "proposedSummary": "short summary or null"
}
  • 入力に存在しないKnowledge IDを返してはならない。
  • repository identityを変更するproposalを返してはならない。
  • merge bodyの最終生成は既存Merge Reviewが担当し、curatorはcanonical候補と根拠を選ぶ。
  • supporting evidenceとcounter-evidenceの両方を評価する。
  • blockerが1件でもあればdestructive auto-executionへ進めない。
  • parse failure、provider failure、timeoutはretryable queue failureとして処理する。

9. Deterministic policy gate

LLMのdecisionとconfidenceはpolicy inputの一部であり、単独ではmutation権限にならない。policy gateは次のdispositionを返す。

  • auto_execute: 現在解放されているactionを自動実行する。
  • enqueue_downstream: 既存Merge Review、Finalize、maintenanceへ送る。
  • record_only: keep separateまたはobserveをTTL付きで記録する。
  • await_evidence: deterministic repair完了後に再評価する。
  • blocked: scopeまたはsafety violationとして実行しない。

9.1 Action-specific conditions

Table: Required conditions for automatic actions
Action Required conditions Fallback
Keep separate / observe scope差またはunique evidenceが明示され、mutationを伴わない 30日TTL後に再評価
Needs evidence missing embedding、source、usage、semantic capabilityを具体的に特定できる repair jobまたは観測待ち
Repair scope repository identity不変、scopeを狭める変更、replay非劣化、rollback snapshotあり broaden / splitはblockedとして終端
Merge review 同一eligible repository、高scope overlap、canonical候補active、unique evidence保持可能 既存Merge Reviewへenqueue
Deprecate duplicate 同一repositoryとappliesTo、active canonicalが完全包含、90日unique useなし、source lineage移管済み 条件不足ならblockedとして終端
Contradiction resolution 自動実行しない 常にblockedとして終端

10. Execution contracts

10.1 Merge

  1. curation jobがcanonical候補を確定する。
  2. 既存deadZoneMergeReviewへidempotentにenqueueする。
  3. Merge Reviewがmerge bodyとblockerを生成する。
  4. policy gateがLLM結果、input hash、scope、source lineageを再確認する。
  5. 既存Finalizeがcanonical updateとduplicate deprecationを反映する。
  6. postcheck後にcuration jobをcompletedにする。

10.2 Scope repair

  1. curatorがrepo identityを除くappliesTo patchを提案する。
  2. baseline replayとpatched replayを同一run cohortで比較する。
  3. wrong / off_topic非増加、used retention非劣化の場合だけpatchを適用する。
  4. bodyを変更しないためembeddingは再生成しない。対象Knowledgeを再読込し、persisted appliesToと既存vectorのcontent hashが不変であることを確認する。
  5. postcheck failure時は保存済みsnapshotへrollbackする。

10.3 Deprecate duplicate

  1. canonicalへのsource / origin lineage移管計画を作る。
  2. canonicalがduplicateの適用scopeとunique assertionを包含することを再確認する。
  3. 既存Merge Review / Finalizeを通してduplicateを削除せずdeprecatedへ変更し、canonical IDとcuration job IDを記録する。Curation workerから直接statusを変更しない。
  4. compile eligibilityとgraph表示から除外されたことを確認する。
  5. rollback window中はUIからreactivateできるようにする。

11. Persistent state model

共通queue statusは既存契約を維持し、詳細な待機理由はphaseで表す。

Table: Queue status and phase
Status Phase or outcome examples Meaning
pending evaluate、policy、awaiting_downstream 再claim可能な待機状態
running preflight、llm_review、policy、mutation、postcheck、rollback workerがleaseを保持している
paused pause前のphaseを保持 laneまたはjobの明示的なresumeを待つ
completed outcome: recorded、repaired、merged、deprecated 必要なdownstream updateとpostcheckが確認済み
skipped outcome: stale_input、superseded、not_eligible、cooldown failureではない非実行終端
failed outcome: provider_failed、parse_failed、mutation_failed、postcheck_failed retryまたはrollbackが必要

Version 1.2では、安全な既存downstream jobの作成とlink永続化をCurationの責務境界とする。link保存後はpaused / awaiting_downstreamとし、Curationがlinked queueを30秒間隔でpollしてterminal状態へ収束させる。

  • subject Knowledge ID、candidate Knowledge IDs、repository identity

  • input snapshot、LLM result、policy result、mutation plan
  • downstream queue name / job ID、postcheck result
  • rollback snapshot / rollback status
  • prompt、model、detector、policy、schema version

13. UI specification

13.1 Queue Dashboard

  • 6番目のtabとしてCurationを表示する。
  • statusに加えてfinding type、phase、subject、proposed action、policy dispositionを表示する。
  • LLM provider / model、attempt、last error、downstream jobを表示する。
  • lane pause、job pause / resume / retryは既存queue contractを使う。

13.2 LANDSCAPE

  • 各Knowledgeにcuration statusと最新decisionを表示する。
  • rationale、supporting evidence、counter-evidence、policy blockerを区別して表示する。
  • 未処理jobはstatusとerrorを表示するが、判断操作は要求しない。
  • destructive mutationにはbefore / after、downstream result、Undoを表示する。
  • frontend-only stateを真実にせず、表示は永続job stateから取得する。

14. Safety invariants

  • cross-repository mutationは常にblockedにする。
  • LLMはrepository identity、status、Knowledge IDを直接変更できない。
  • すべてのmutationはbefore snapshot、idempotency key、actor、reasonを持つ。
  • 同じsubjectに複数のdestructive curation jobを同時実行しない。
  • curationが生成したfindingを同じfingerprintで再生成するloopを抑止する。
  • mutation後のembedding、scope、status、lineage確認なしにcompletedにしない。
  • rollback不能なactionをauto_executeへ解放しない。

15. Release modes

release modeはlane全体ではなくaction classごとに設定する。

  • disabled: findingをenqueueしない。
  • shadow: LLMとpolicy resultを保存するがUIとKnowledgeを変更しない。
  • auto_non_destructive: observe、keep separate、needs evidenceを自動処理する。
  • auto_bounded: gateを満たすrepair、merge、deprecateをrate limit付きで実行する。

16. GO conditions embedded in delivery

本機能はGOとする。以下はプロジェクト開始の承認条件ではなく、各release modeを解放するためのacceptance gateである。未達の場合も実装を停止せず、到達済みmodeで運用する。

G1 Decision quality 最低200件、action別label、repository violation 0、destructive precision 98%以上 auto_non_destructive

17. Delivery sequence

  1. SQLite semantic evidence parityとnegative scope fixtureを実装する。
  2. landscape_curation_queue、worker、persistent phase、queue eventを実装する。
  3. shadow curatorとpolicy gateを実装し、既存review itemsで評価する。
  4. Curation tabとLANDSCAPE recommendation UIを実装する。
  5. non-destructive actionを自動解放する。
  6. scope repairを最大5件/dayでcanaryする。
  7. 既存Merge Review / Finalize連携を最大5件/dayでcanaryする。
  8. 既存Merge Review / Finalize経由のduplicate deprecationを最も厳しいsame-scope subsetから解放する。

19. Completion criteria

最初の正式releaseは、次をすべて満たした時点で完了とする。

  • Curationが6番目のvisible queueとして稼働し、pause / retry / auditが使える。
  • SQLiteで全finding typeのcandidate evidenceを生成できる。
  • shadow、auto_non_destructive、auto_boundedをaction別に切り替えられる。
  • 既存Merge Review / Finalizeのlinked resultを追跡できる。
  • non-destructive actionが自動処理され、未処理jobだけがLANDSCAPE画面に残る。
  • destructive actionはgate未達ならblockedとして終端し、誤って自動実行されない。

20. Fixed implementation decisions

V1では次の判断を固定し、実装中に別案へ置き換えない。

22. SQLite evidence parity implementation

G0を満たすまでproducerはdefault disabledとする。空結果を正常結果として扱う実装を残さない。

22.1 Similar Knowledge

  • listSimilarKnowledgeRowsのSQLite branchはknowledge_items_vec_fallback.embedding_jsonをbatch loadし、landscape-trajectory.service.tsと同じcosine計算を共有helperへ抽出して使う。
  • subject集合と同じresolved repository identityのrowだけをvector計算前に絞る。
  • 各subjectについてsimilarity降順、updatedAt降順、ID昇順でtopKを返す。
  • invalid JSON、次元不一致、zero vectorはそのpairだけ除外し、capability warningを返す。

22.2 Semantic community

  • buildSemanticCommunityAssignmentsはSQLiteでもfallback vectorからpair similarityを計算し、既存buildCommunityAssignmentsへ同じnode / edge shapeを渡す。
  • 各nodeのedgeはsimilarity降順でsemanticTopK件、全体上限はknowledgeIds.length * semanticTopK * 3とする。
  • 同じfixtureに対するcommunity comparison kindがPostgreSQL実装と一致することをtestする。community key文字列そのものは比較せず、membership集合を比較する。

22.3 Contradiction evidence

  • loadContradictionKnowledgeRowsはSQLiteで同じstatus、type、sort、limitを適用する。
  • recent selectionはcontext_pack_itemsとcontext_compile_runs、semantic pairはfallback vectorを使い、PostgreSQL branchと同じpair keyとthresholdを返す。
  • capabilityが不足する場合は空arrayだけでなくcapabilities.contradictionAvailable=falseをsnapshotへ残し、jobをneeds_evidenceへ送る。

22.4 G0 fixture

12 Knowledge、3 repository、2 global、exact duplicate 1組、semantic duplicate 2組、contradiction 1組、dimension mismatch 1件を含むfixtureをPostgreSQLとSQLiteへ投入する。次が一致したときだけG0をpassとする。

  • same-repository neighbor pair集合とsimilarity差0.0001以内
  • cross-repository pair 0件
  • semantic community membership集合
  • contradiction pair集合、selection count、confidence label
  • dimension mismatchが全体failureではなくcapability warningになること

23.4 Scope repair gate

repair_scopeをauto_executeできるのは次をすべて満たす場合だけとする。

  • confidenceがhigh、blockersが空、supporting evidenceが2件以上。
  • subjectがactive、repo scoped、repository identity不変。
  • 現在のappliesToにtechnologies、changeTypes、domainsの少なくとも1つが存在し、generalがtrueではない。
  • proposed appliesToはrepoKey / repoPathを変更せず、既存facet keyを追加しない。各arrayは現在値の非空subset、少なくとも1 facetがstrict subsetである。全facet削除、未知key追加、general変更は拒否する。
  • 90日、最大100 runのreplayでused eventのeligibility retentionが100%、off_topic / wrong eligible件数が増加せず、cross-repository eligibilityが0件。
  • rollback snapshotが保存済みで、当日のscope repair実行数がglobal / repo budget内。

replayはknowledge.repository.shared.tsのbuildApplicabilityQuery / computeApplicability / hasApplicabilityQueryを使い、SQLite検索と同じmatching semanticsで評価する。別のfacet matcherを再実装しない。

23.5 Merge and deprecation gate

merge_reviewまたはdeprecate_duplicateをenqueue_downstreamできるのは次をすべて満たす場合だけとする。

  • confidenceがhigh、blockersが空、canonical IDがinput candidateに含まれる。
  • subjectとcanonicalがactive、typeとpolarityが一致し、同じresolved repository identity。
  • body hash、status、appliesTo hashがsnapshotから変わっていない。
  • V1はbody hashとnormalized appliesTo hashがともに一致するexact duplicateだけを許可する。similarity 0.92以上かつscope overlap 0.8以上のsemantic duplicateは候補として記録できるが、AUTONOMOUS_EXACT_DUPLICATE_REQUIREDでblockedにする。
  • subjectにcanonicalで説明できないused runが90日内に0件。1件でもあればblocked。
  • source / origin linkをcanonicalへcopyするplanがあり、postcheck countがmutation前のunion以上になる。
  • merge body生成とdeprecationは既存Merge Review / Finalizeへ委譲する。

curatorがdeprecate_duplicateを返した場合もeffective actionはenqueue_merge_reviewとする。直接statusをdeprecatedへ変更するbranchは作らない。

From To Status after transition

24.3 Processing steps

  1. jobをreadし、phaseに応じて処理をresumeする。phaseをevaluateへ戻さない。
  2. preflightでsnapshot readback、repository identity、capability、active mutation lockを確認する。
  3. exact duplicateを含む候補をcuratorへ渡し、LLM評価をtyped resultとして保存する。完全一致の事実はLLMに委ねず、後段policyで再計算する。
  4. LLM resultをschema parseし、input ID参照を検証して保存する。
  5. policyを評価し、policy_decidedeventを記録する。
  6. record_onlyはcompleted、await_evidenceとblockedはskipped、enqueue_downstreamはlink永続化後にpaused / awaiting_downstreamへ進める。human_reviewは生成しない。
  7. repair_scopeはrollback snapshotを保存してmutationし、readbackとreplay postcheck後にcompletedにする。
  8. mergeはmerge review jobをidempotentに作成してlinkし、completed / awaiting_downstreamで責務を委譲する。
  9. merge reviewがcompletedかつmerge_recommendedならsnapshotを再gateし、auto_boundedの条件を満たす場合だけFinalize jobを作る。merge_blocked / keep_separate / needs_evidenceは対応するrecord outcomeでcompletedにする。
  10. Finalizeがterminalになるまでpollし、completedならKnowledge、lineage、statusをpostcheckする。skipped / failedならcuration jobをcompletedにしない。

24.4 Retry and polling

  • Curation curatorのprovider timeout、HTTP retryable、parse failureはattemptを増やし、60秒、300秒、1800秒で最大3回retryする。
  • downstream pollはattemptを増やさず30秒後にpausedへ戻す。24時間超過でfailed / downstream_timeout。
  • Curation由来Merge ReviewとFinalizeの一時失敗は60秒からのbackoffで各queueのmax_attemptsまで自動retryし、上限到達時だけCurationと下流jobをfailedにする。
  • stale input、not eligible、policy blockedはretryせずskipped。
  • V1 exact duplicate pathはcanonicalを変更せず、duplicate 1行のdeprecationだけを行う。mutation後のqueue更新失敗はdeprecation metadataを使って自動収束する。将来の複数行mutationでは自動rollbackを必須とする。
  • lane pauseによるAbortは既存queue contractに従いpausedへ戻し、provider failureへ数えない。

24.5 Atomic mutation and rollback

  • scope repairは単一Knowledge row updateを1 transactionで行い、appliesTo以外のbusiness fieldが変わっていないことをpostcheckする。
  • V1のcuration由来merge finalizeは提案body、現在のcanonical、duplicateのbodyとappliesToが完全一致することを再確認し、canonicalを変更せずduplicate 1行だけをdeprecatedへ更新する。mutation後にqueue更新が失敗した場合は、finalizeJobId付きdeprecation metadataを検出してcompletedへ収束させる。
  • 既存Finalizeのcuration以外のpathは挙動を維持するが、body/status hash checkとatomicityは共通repositoryへ移す。
  • rollback windowは7日。scope repairは旧appliesTo、mergeは旧canonical body/appliesTo/metadataとduplicate status/metadataを復元する。
  • rollback前に現在値がpost-mutation hashと一致しない場合は上書きせず、rollback_status failed / stale_rollback_targetとしてfailedへ遷移し、未処理一覧へ表示する。

  • drawerはOverview、Evidence、Decision、Policy、Downstream、Mutation / Rollback、Eventsの順に表示する。rationale、counter-evidence、blockerを同じlistへ混在させない。
  • pause / resume / retryは共通buttonを使う。retryはstale inputを自動force適用せず、新snapshot作成をproducerへ委ねる。

26.2 Unresolved Curation status

  • LANDSCAPE画面には永続queueの非終端jobだけを表示する。
  • 表示対象はpending、running、paused、failedとし、completedとskippedは除外する。
  • ユーザーへApprove、Override、Dismiss、Request evidenceを要求しない。
  • status、finding type、phase、subject knowledge ID、last errorを表示する。
  • Undoはrollback可能なcompleted job、7日以内、rollback not_requestedの場合だけ表示する。実行前にbefore / afterを再表示する。
  • mutation成功をoptimisticに表示せず、APIから返ったpersisted statusでquery cacheを更新する。

26.3 LANDSCAPE Knowledge integration

  • LANDSCAPE取得後、画面に表示中のKnowledge IDsを50件ずつcuration jobs APIへ渡す。Knowledgeごとの個別requestは禁止する。
  • 各Knowledgeへ最新jobのstatus、finding type、decision badgeを表示し、clickで同じdetail drawerを開く。
  • active jobが複数存在しないことはDB constraintで保証するが、履歴は最新5件を表示する。
  • review itemの既存manual actionは残し、Curation recommendationがある場合だけ新UIを併記する。

26.4 Loading, error, and accessibility

  • drawer fetch中、schema not ready、404、409、retryable errorを別表示にする。
  • badgeだけで状態を伝えずtext labelを併記する。action buttonへaccessible nameを付ける。
  • modal open時のfocus trap、close後のrow focus復帰、Escape closeを既存UI primitiveで実現する。

28. Observability and auto-pause

28.1 Events and audit

  • 全phase変更でphase_changed eventへfrom、to、status、reasonを保存する。
  • policy eventへdecision、disposition、reasonCodes、releaseMode、policyVersionを保存する。
  • rollbackはqueue eventに加え、既存audit log serviceへactor、job ID、before / after hashを保存する。
  • LLM raw output全文は保存せず、最大1200文字excerptとparse statusをresultへ保存する。

28.2 Metrics and health

既存Overviewまたはqueue statsから次を集計できるよう、columnとevent metadataを欠かさない。

  • findingType、decision、disposition、outcome別job count
  • oldest pending、downstream wait age、failure / retry / rollback count
  • provider / model別latency、token usage、parse failure
  • repository violation、stale input、policy blocked、autonomous delegation
  • scope repair後のused retention、negative eligibility delta、merge後のlineage count

28.3 Auto-pause

次のいずれかを満たしたらlane controlを使いCurationだけを自動pauseする。core queueはpauseしない。

  • 直近20件でprovider / parse failureが5件以上
  • repository identity violationが1件以上
  • 24時間内rollbackが2件以上
  • postcheck failureが連続2件
  • downstream failure率が直近20件で25%以上

auto-pauseはpausedeventとaudit logを残し、理由をQueue Dashboardへ表示する。provider cooldown後のretryまたは運用上のlane resumeで再開するが、Knowledge判断をユーザーへ要求しない。

31. Definition of done

Terraによる実装完了は、次をすべて満たした状態とする。

  • 21節のfile mapにある変更が実装され、記載外のmutation pathが追加されていない。
  • PostgreSQLとSQLiteで同じschema、finding、policy、state transition、API shapeが成立する。
  • 6番目のCuration tabがgeneric queue controlと専用detailを表示する。
  • LLM resultはschema、input ID、repository identityの3段階で検証される。
  • downstream link、postcheck、rollbackがprocess restart後も続行できる。
  • downstream enqueueとlink永続化が同時に成功した場合だけcuration jobをcompletedにする。
  • cross-repository mutation、contradiction auto mutation、direct duplicate deprecationがcodeとtestの双方で禁止される。
  • 29節のtestとverification commandがpassする。
  • shadow 200件のlabel datasetとG1集計を作成できる。
  • 運用開始時のdefaultがproducer disabled、全action shadowである。
