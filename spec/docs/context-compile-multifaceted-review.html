context compileの多角評価：検索・情報保持・運用信頼性

評価日：2026年9月6日。対象は作業ツリーのRust native MCPとTypeScriptのcompile実装。総合評価は「分離・保存の基盤には強みがあるが、関連情報を取得し、条件を落とさず返す保証には不足がある」。見出しの整った回答や既存テストの合格だけで、実務上の有効性は判断できない。

この文書は現行コードの評価であり、新たに混入した回帰だけを扱うレビューではない。製品コード・設定は変更していない。既存の未コミット変更を維持し、再現用の一時Rustテストは実行後に削除して元ファイルのSHA-256一致を確認した。検証は隔離fixtureとローカルmockを使用した。

優先度付き指摘

P1は実務の回答品質・禁止事項・共有Writerの可用性へ直接影響するもの。P2は条件付きの誤判定、障害診断、予算と計測の不正確さ。再現済みの問題と、コードから確認した運用リスクを区別する。

F01 / P1：legacyは関連性より履歴値を優先できる

native_compile/retrieval.rs:104でquery_score + dynamic_score.round()を順位と採用条件に使う。文字列一致0でもdynamic_scoreが正なら候補に残る。Knowledgeは上位8件なので、再現fixtureでは関連知識「backup retention」1件が、dynamic_score=100の料理知識8件に完全に押し出された。Episodeにもquery_score + importance / 10で同様の構造がある。

Foundationはこのfixtureで正解を取得した。関連性による採用条件と効用による同点処理を分ける方針は妥当。ただし昇格は日本語、独立課題、負荷、空結果率も含めて判断する。既知の問題でも、既定経路に残る限り利用者への影響は続く。

F02 / P1：日本語の関連情報を文字列検索で取り逃がす

native_common.rs:160のscore_textとnormalized_query_tokensは英数字以外ではなく、Unicodeの文字・数字以外で分割する。そのため「バックアップの保存期間を変更する」が1トークンとなり、「バックアップの保存期間は30日です。」への一致スコアが0だった。Foundationのquery_score > 0でも救えない。facetが同じ場合は候補に入り得るが、facet語への一致とgoalへの関連性を混同する危険がある。

日本語の短い名詞句・文字n-gram等を含む検索契約を定め、語尾違い、言い換え、長いgoalの後半条件をfixtureに加える。単純に採用閾値を下げるとF01のノイズを戻すため、取得率と誤採用率を同時に測る。

F03 / P1：TS重複抑制で禁止事項を削除できる

src/modules/context-compiler/duplicate-suppression.service.ts:100以降はtype・statusを比較するが、構造化polarityを比較しない。逆の意味の検出も本文先頭400文字と正規表現だけで行う。正負Knowledgeを合わせてこの関数へ渡すため、同じタイトル・共通の長い前文を持ち、後半で「復元確認は不要」と「復元確認前の削除は禁止」に分かれる候補を与えると、negative側がconfidence=1で重複抑制された。

polarityが異なる候補を統合対象から外す。条件、数値、否定、適用範囲が異なる知識を、類似度だけで同一視しない。共通前文の後ろに制約があるケースを恒久テストにする。

F04 / P1：fallbackが本文の条件を落とし、利用済みとして記録する

native_compile/composition.rs:205以降ではruleをタイトル中心で返す。本文が「保存期間は30日。削除前に復元確認を必須とする。」でも、生成設定なしのfallbackでは「30日」「復元」がともに消え、errorはNone、usedKnowledgeにはそのIDが残った。生成を無効にした運用とprovider失敗時に影響する。

fallbackにも根拠本文の条件・数値・否定を保持する出力を用意し、タイトルへの言及と本文を利用したことを区別する。通常composerの1,200文字化だけではこの経路は直らない。

F05 / P1：legacyは外部LLM応答をWriterの中で待つ

コードで確認した運用リスク。native_compile/mod.rs:109でcompile全体をwith_writerへ渡し、その中で同期HTTPのplannerとcomposerを呼ぶ。sqlite_writer/service.rsは同じDBのWriterジョブを順番に実行するため、生成待ちが他の保存処理の待ち時間になる。transaction開始前でもWriterジョブの占有は続く。

HTTP timeoutは呼出し単位で、providerごとに2呼出しがあり、fallback先も順番に試す。10秒設定で3経路がそれぞれtimeoutするなら、通常HTTP経路では約60秒の待ちが生じ得る。これは構造からの見積もりであり、今回測った本番遅延ではない。split経路への段階移行と遅いprovider・並行書込みfixture、compile全体のdeadlineを優先する。

F06 / P2：日本語goalでは出力整合性チェックが素通りする

native_compile/prompts.rs:329のlooks_goal_alignedはASCII語だけを取り出し、語がなければtrueにする。「バックアップの保存期間を変更する」に対して「料理手順：野菜を切る。」がtrueだった。生成後の受理条件なので、F02の検索失敗を最後の段階でも検出できない。ASCII語がある場合も、1語含まれるだけで十分となる。

同じ語があることと根拠に沿っていることを分けて検証する。少なくとも純日本語を無条件合格にせず、言語に依存しない候補利用・根拠整合の検証と誤採用fixtureを設ける。

F07 / P2：SQL検索失敗がstatus=okのNo Contentになる

native_compile/retrieval.rs:51ではprepare/query_mapエラーを空配列へ変換し、行エラーもflattenで捨てる。degraded_reasonsが確認するのは主にテーブル有無だけ。隔離DBでknowledge_itemsのbody列を改名してSQLエラーを起こすと、MCP本文はNo Content、保存runはstatus=ok、degraded_reasons=[]だった。

検索関数からResultと段階別の理由を返し、正常な0件、部分読取失敗、全件検索失敗を区別する。No Contentとして呼出し側に見せる場合でも、内部のstatusと原因を正しく記録する。

F08 / P2：本番用のLLM試行数が実測ではない

コードで確認。native_compile/composition.rs:43でProviderCallを一時Vecへ記録して捨て、native_compile/mod.rs:519ではagentic_usedからlogicalCallsとproviderAttemptsを2または0にし、failovers=0、attempts=[]を保存する。全provider失敗で実際は呼出しがあっても0となり、fallback成功時の追加試行も2へ縮む。

実験runnerには実測収集経路がある。これをproductionのComposeResultへ渡し、失敗・fallback・usage不明をそのまま記録する。snapshotComplete=trueは保存完了を表すだけで、これらの数値が実測である保証にはならない。

F09 / P2：TSトークン予算の上限と切詰め診断が不正確

src/modules/context-compiler/token-budget.ts:110では最初の候補が大きい場合、タイトルとrankingReasonを差し引かずに本文だけを予算まで縮める。32トークンの予算に対して、同じ推定器で合計54となり、1件を切り詰めてもdropped=falseだった。セクション比率はrules=0.55、procedures=0.45、guardrails=0.3で合計1.3。

これは候補パックの予算制御の問題であり、LLMの実トークン使用量を54と測ったものではない。共通の残予算からタイトル・理由・本文を控除し、切詰めと件数減少を別々に記録する。guardrailの追加枠が意図的なら総予算とは別の契約として明示する。

性能・保守性で追加検証すべき点

Rust検索はscopeで許可された全行を取得して本文を走査する。256件・96件のcandidate limitはDB走査上限ではない。Knowledgeでは選択前の各候補についてsource_refs取得SQLも実行する。データ量に伴う本文処理、メモリ保持、ソート、参照取得の増加を、1千・1万・10万件などの固定データで測り、選択後の参照取得と索引検索を検討する。安易なSQL LIMITをscope・facet・関連性評価より前に入れると取得率を悪化させる。

Rust plannerのquery hintsは現在の候補選択では利用されず、select_prompt_knowledge_candidatesのplan引数も未使用。2回の生成が品質改善にどれだけ寄与するかを、同じ候補・同じ課題でcomposer単独と比較する価値がある。ただし本評価では効果も時間短縮も未測定で、planner削除を結論にはしない。

機能追加より先に、RustとTSが共有すべき契約を固定する。repository分離、負の知識の保持、No Contentと失敗、使用IDの意味、証拠本文の保持、予算の定義を共通fixtureで検証し、意図的な経路差は明示する。

既存の実モデル評価をどう読むか

既存の効果実証レポートでは、固定12課題で正答率が記憶なし62.5%、legacy検索47.9%、Foundation検索100%、Recall@8がlegacy 0%、Foundation 100%と報告されている。平均時間はそれぞれ1.12秒、5.07秒、6.69秒。今回の独立した小さな履歴偏重fixtureは、その失敗の仕組みと整合した。

これらの実モデル数値は既存レポートの引用であり、今回再実行していない。改善に使った小規模課題での100%は、未知のコード変更作業、利用者の修正時間、本番の日本語入力全体への一般化を証明しない。次は独立holdout、反復試行、検索前後の必須条件保持率、禁止事項消失率、No Contentの適否、writer待ちp95、総provider試行数を合わせて測る。

推奨する着手順

  1. 負の知識と必須条件の消失を防ぐ。F03・F04を恒久fixtureにし、検索成功後の情報破壊を先に止める。
  2. F01・F02・F06の検索と受理条件を改善し、日本語を含む独立課題で誤採用と取り逃がしを測る。
  3. F07・F08を直して失敗・試行数を正しく観測し、F05のsplit経路を段階的に検証する。
  4. F09の予算契約を整理し、候補件数増加とplannerの費用対効果を測定する。
