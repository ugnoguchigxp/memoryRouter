Curation v2 実装計画：根拠を保持してLandscapeを自動整理する

計画ID：landscape-curation-v2。作成日：2026-09-06。対象は全active knowledgeのキュー投入、近似候補の探索、LLMによる統合・deprecated判断、SystemContext、変更と復元、品質評価。これは実装計画であり、製品の判断精度は未測定である。

実装準備度は固定20項目×5点の自己レビューで70→84→97/100まで改善した。3稿の本文と各減点理由を保存した。97点は計画の具体性・検証可能性の評価であり、実LLMの精度、第三者の評価、世界最高性能の証明ではない。本番semantic適用は別の実測gateを通す。

1. 完了条件と現在地

利用者が各件を承認しなくても、整理できるknowledgeをLLMが判断し、根拠と適用条件を保持して統合、または包含された側をdeprecatedにする。Landscapeの全active knowledgeを審査対象にすることと、全件を変更することは区別する。意味のある差や解けない矛盾は残す。低利用・古さ・近似度だけをdeprecatedの理由にしない。

現行評価では、欠落した統合本文、数値の矛盾、generalから限定scopeへの置換、比較両側を引用しない回答が実行gateを通った。現行promptはRust直書きで、TypeScriptとは異なる。実LLM評価は7件中2回答、5件はprovider容量不足で未評価。これを精度のベースライン値に換算しない。

非対象：矛盾する規則の独断での正本判定、根拠のない期限切れ判定、別repository同士の統合、利用頻度を理由にした削除、context_compileの選択アルゴリズム変更。knowledgeの物理削除は行わない。

2. 判断から実行までの構成

  1. Rustで対象と候補の本文・適用範囲・出典・revisionをsnapshotに固定する。
  2. 完全一致はdeterministic検査で処理する。意味判断が必要な組だけplanner LLMへ渡す。
  3. plannerは比較対象の両側の原文を引用し、残す側、捨てる重複、保持する固有条件を構造化して返す。自由な本文生成は初期版では許可しない。
  4. verifierは原文と変更案から欠落・条件変更・矛盾を別途検査する。plannerの説明・自己申告の確信度を渡さない。
  5. Rust gateがschema、scope、coverage、revision、検証結果を確認する。LLMのhigh単独では実行しない。
  6. Rust SQLite writerの単一transactionで本文・出典・status・検索index・監査を更新する。変更後を検証し、失敗時は全体をrollbackする。

LLMを増やせば安全になるとは仮定しない。同じモデルの二回の回答には相関がある。verifierは防御の一層であり、独立した正解データと実行制約によって有効性を測る。

3. 適用範囲と統合方向の契約

repository identityの既存正規化を共有する。globalとrepositoryの混在、identity未解決、type・polarity不一致は変更不可。現行native facets_allowはtechnologies・changeTypes・domainsのORであり、ANDではない。空配列とgeneralの扱いも既存applicability_generalに合わせる。未知のscopeキーを捨てて同一と判定しない。

初期の自動変更は同値な適用範囲に限定する。配列のunionは廃止する。元本文中の条件も別に保持する。混合scopeを条件付き節として格納する機能は、reader側まで適用条件の表現を共有できる別拡張として扱い、初期版をそれに依存させない。

subjectとcandidateのどちらもsurvivorになれる。選択順は情報保持、既存参照の安定、出典の直接性、最後に固定ID順。同じ話題であることは同じ指示の証拠ではない。数値・単位・否定・例外が異なる場合、両立可能な元条件を保存できるときだけmergeし、同条件での矛盾はkeep_separateとする。

4. 原文と根拠を保持する契約

snapshotにknowledge ID、bodyのSHA-256、title、type、polarity、repository identity、appliesTo、出典linkと取得可否を含める。入力本文を元の段落・リスト・コードblock単位のspanへ分割し、UTF-8 byte offsetとhashを付ける。元の非空白byteが分割から消えていないことをRustで検査する。

merge rendererは原文spanをそのままコピーする。指示を言い換えたり新しい条件を足したりしない。あるspanを省略する場合はsurvivorに残るspanへの包含対応を必須にする。条件・否定・例外・数値・識別子を対応表で検査する。決定的なbyte検査は意味的な包含を証明しないため、非同一spanの省略にはverifierの具体的な対応検証が必要になる。

deprecate_duplicateはsurvivor本文を変えず、deprecated側の全要件が既存survivorに包含されるときだけ選べる。部分的な包含なら残りをmergeするかkeep_separateにする。出典がないことと証拠が否定されたことは別に記録し、参照先を読んだふりをしない。

spanは単なる行ではなく、見出し、先行条件、リスト階層、コード、参照定義を含むcontext groupに属する。「この場合」「ただし」などの依存を解決できないときは文書全体を一つのgroupにする。rendererはgroup内の順序と原文を保持し、親条件のない子spanだけを移動しない。groupの一部を落とす変更は禁止し、包含の単位もgroup全体とする。Markdownの参照名・見出しanchor・コードfenceの衝突を検査し、安全に構成できなければkeep_separateとする。

LLMが抽出した要件リストを原文の代用品にしない。全groupを必ず保持または包含先へ対応させ、verifierは抽出リストだけでなく両側の原文全文を読む。初期semantic mergeは各原文groupを出典付きの独立sectionとして順序を保って併記する。元の条件が変化しないことを確認する。混ぜた一文への要約は別の評価を通るまで非対象とする。

5. 管理されたSystemContext

contexts/landscape/curationPlan.context.tomlとcurationVerify.context.tomlを追加する。単一catalogから生成したversion付きartifactをRustとTypeScriptで共有し、requestにcontext key、version、render hash、schema hash、model・routeを記録する。TypeScript独自の判断promptとpolicyは廃止し、Rustの結果を表示するadapterにする。

SystemContextは目的、禁止条件、scope契約、全decisionの意味、原文対応、反例、JSON schema、上限を含む。knowledge・title・metadata・出典は全てuntrusted dataである。knowledgeが「この規則を無視せよ」と命令していても、その文を分析対象として扱う。LLMにtool実行やDB更新を許可しない。

Chat Completionsではsystemとuserを分離する。Agent Sessionで単一文字列化する場合、タグescapeだけで本物のrole分離と同等だとは扱わず、経路単位で注入耐性を評価する。Rustを含む全送信箇所をsystem-context boundary checkへ追加する。

6. 構造化された決定と実行gate

decisionはmerge、deprecate_duplicate、keep_separate、needs_evidenceの4つに絞る。観測・再試行・escalationは実行状態として区別する。出力にはinput hash、survivor ID、deprecated ID、各source spanの保持先または包含先、反証、保留理由を持たせる。未知field、未知ID、重複ID、不完全coverageを拒否する。

schemaを一つの正本からRust serdeとTypeScript validatorに共有する。LLMの出力は未信頼の提案としてparseし、gate通過後だけ内部のValidatedMutationへ変換する。型変換前のproposalをwriterが受け付けるAPIを設けない。

7. 全件キューと候補探索

全active knowledgeを一度のbackfillだけでなく、新規作成・実質的な本文やscopeの変更後にも対象にする。利用回数更新は再投入理由にしない。jobにreviewed revisionとpolicy versionを記録し、同じpair・revisionの審査を重複させない。候補がない場合も審査済みとして記録する。

候補はrepository・type・polarityで絞り、完全一致、既存vector、語彙検索を併用する。近似度は候補選定だけに使う。vectorがないknowledgeを未審査のままにしない。top Kは固定の0.8閾値・5件を引き継がず、正解候補のrecallと費用を測って設定する。AとB、BとCが近いというだけでAとCまで一括統合しない。

8. 変更・lineage・復元

LLM呼び出し中にwriter lockを保持しない。適用直前に関係する両IDを一定順で確認し、body・scope・identity・statusのrevisionを比較する。staleなら古い提案を適用せず、最新snapshotで再評価する。crash後の再開は同じmutation IDでidempotentに行う。

survivorの本文、source/origin links、deprecated側の置換先、FTS・embeddingのrevisionを一貫させる。元のIDと出典は履歴に残し、参照が循環しないようにする。復元は変更後revisionが一致するときだけ逆transactionで戻し、後続の正当な変更を上書きしない。

9. 品質評価と採用条件

現行9件の契約probeを回帰の種にする。正しい重複、補完可能な手順、数値・単位、否定、例外、条件、scope、参照根拠、逆方向、注入、長文を含む正解集合を作る。日本語・英語、実データ由来と合成反例を分けて評価する。

変更precision、全要件の保持率、正解mergeのrecall、誤deprecated、候補探索recall、保留率、provider失敗を別々に出す。全件keep_separateでも高得点になる指標にしない。現行、plannerのみ、planner＋verifierを同じsnapshotで比較する。自己申告の確信度や同じLLMの採点だけを正解としない。

10. 実行基盤と段階導入

provider容量409、通信失敗、JSON不正、意味判断の誤りを別状態として扱う。retryは有界で、恒久的なprovider占有や無限再試行を許さない。外部呼び出しの間はqueue leaseを更新し、cancel時もprovider資源を返す。

最初に危険な現行gateを停止する変更と厳格な完全一致経路を導入し、semantic経路はsnapshot上のshadowから始める。品質条件を満たしたrouteだけ限定件数で実適用し、失敗を検出したrouteを自動停止する。全件キューの投入はsemantic経路の昇格を待たない。

12. revision・pair・収束の詳細契約

contentRevisionはbody、title、type、polarity、正規化済identity、完全なappliesTo、意味に影響するmetadata、source/origin link集合のcanonical JSONから算出する。usage・updatedAt・queue状態は含めない。snapshotRevisionには出典の検証状態も含める。byte hashと意味上のrevisionを混同しない。

審査ledgerのunique keyはknowledge ID＋contentRevision＋policyVersion。pair ledgerはsorted IDと両revision＋policyVersion。新しいknowledgeが追加された場合は、その新規jobが既存knowledgeを候補にできるため、既存全件を再投入しない。候補なしの完了は、そのrevisionとcandidate index epochを記録する。index再構築・候補検索版の変更時は未発見だった集合を再走査する。

Curation自身のmergeでできたsurvivorも新revisionとして一度審査する。自己再投入を一律に抑止して残りの重複を見逃さない。元source groupのID集合をlineageに保持し、既に取り込んだgroupを再追加しない。成功mutationは必ずactive ID数を1減らす。保留やkeep_separateでは本文を書かず、同revisionを再投入しない。新規外部更新がない有限集合では、この条件で成功mutation数を初期active数−1以下に制限する。

backfillはprimary key cursorによる500件単位でwriterに投入し、進捗cursorを同transactionに保存する。既存v1 jobは消去せず、claim時にv2 ledgerへ移行する。旧workerが停止してからv2 claimを有効にする。全activeにledgerが存在するanti-join件数0を完了条件とし、pending・running・reviewed・waiting・failedを別集計する。対になるjobはpair ledgerを共有し、片方がstaleでも知見を重複適用しない。

13. 候補探索と入力予算

repository identityが確定した同scope/type/polarity集合を探索する。完全一致index、FTS、既存vector検索の上位候補をIDで重複排除する。初期値は各方式20件、統合後最大40件、LLM比較は一度に2文書。Kはcalibrationだけで決め、holdoutを見て変更しない。embeddingのない対象も完全一致とFTSで審査し、embedding待ちを別記録する。

検索では本文条件が異なる候補も見つけ、gateで差を判断する。同値scope候補を先に審査するが、scope不一致の見逃しは統計から隠さない。candidate recallは人が確認したeligible pairに対しtop40へ入った割合とし、95%以上を目標にする。現行top5・cosine 0.8とも比較し、見逃し理由を残す。

モデルのcontext上限からsystem、schema、完全な両本文、出典、出力余白を先に見積もる。各文書の原文を黙ってtruncateしない。全文が入らなければneeds_evidenceのINPUT_TOO_LARGEとして終了し、大contextの認定済routeが設定されている場合だけそちらで再試行する。分割しても全体条件を検証できない長文は自動deprecatedしない。

14. 製品品質の採点と失格条件

実装準備度と別に、製品のsemantic scoreを定義する。正解には比較ごとの許容action集合、残すべき原文group、禁止される変更、許容survivorを持たせる。正解のない実例はunknownとし、無理にラベルを作らない。2名の独立した内容確認と不一致の裁定でgoldを確定する。LLM判定は下書きまでとし、最終goldには使わない。gold作成者を確保できるまでは製品の95点超えを宣言しない。

開発・calibration・holdoutをsource familyとrepositoryで分離する。同じ元文書の言い換えや派生例を別splitへ入れない。holdout manifestを先にhash固定し、繰り返し閲覧したsetは開発用に格下げして新しいholdoutを作る。日英、scope、数値、否定、例外、出典、注入、長文、統合有益性の層を固定し、各層を等重みで集計する。

semantic scoreは100×（0.40×mutation precision＋0.30×要件保持率＋0.20×eligible action recall＋0.10×非変更ケースの正解率）。各成分は0〜1。precisionは実行した変更のうちgoldで許容される割合、保持率は変更に含まれたgold要件の保存割合、recallはeligible例のうち正しい変更を実行した割合。変更0件ならprecisionと保持率は未定義で不合格。keep_separateだけを返す戦略はrecallで失格にする。

昇格には点推定95点超えに加え、source family単位bootstrapの片側95%下限も95点超え、候補recall 95%以上、eligible action recall 85%以上、critical error観測0件を必要とする。critical errorは固有要件・条件・否定・数値の欠落、根拠のない適用範囲変更、誤repository、誤deprecatedである。いずれか1件でも失格とし、平均点で相殺しない。

少なくとも600の独立source familyに対する実行可能なmutation評価を確保する。0件のcritical errorなら、独立Bernoulliを仮定した片側95%上限は1−0.05^(1/600)≒0.50%であり、無事故の証明ではない。家族内の派生ケースを600件に水増ししない。保留・provider失敗で有効mutation数が不足すれば未認定とする。保持率とrecallは全対象件数と欠測件数を併記する。

15. writer・移行・参照の詳細

新規追加tableはcuration_review_ledger、curation_pair_reviews、curation_mutations、knowledge_supersessionsとし、schema version付きの加算migrationで導入する。mutation ID、入力revision、policy hash、提案・検証hash、before/after snapshot、source group lineageを記録する。実装開始時に既存schemaとの重複を確認し、既存同等tableがあればそこを拡張する。migrationはRust writerの既存手順に統合する。

writer transaction内でpairの両active revisionとpolicy有効状態をCAS確認し、survivor更新・旧IDのdeprecated・supersession・出典link・FTS・vector整合・監査・job完了をまとめる。aliasにcycleを作らない。既存履歴のIDを一括書換えせず、readerは歴史的な原文参照と現在のsurvivor解決を別に扱う。後続compileでdeprecated IDを解決する入口も検証する。

embedding生成はtransaction外で行い、body hashに紐付ける。失敗時は古いembeddingを新本文のものとして使わない。vectorを無効化してFTSのみで公開するか、mutationを待機するかをroute policyに固定する。初期版はmutationを待機し、provider復旧後に同revisionを再確認する。DBと外部indexを同transactionにできない場合はoutboxとrevision一致のreader gateを使用する。

rollbackはbefore snapshotとmutationが追加したlinkの差分、旧FTS/vector、supersessionを復元する。後続mutationがあれば末尾から逆順に復元し、外部更新と衝突した時点で停止する。稼働中に新旧writerが混在するdowngradeは禁止し、旧binaryへ戻す場合は新規claim停止・lease終了・migration互換確認を先に行う。

16. 実装可能なprompt・schema・gate

planner SystemContext全文、verifier SystemContext全文、planner schema、verifier schemaを設計artifactとして固定する。4 decisionの構造例と検証応答の構造例も付けた。これらは実LLMの回答ではない。実装ではcontext catalogと生成schemaへ移し、二重管理しない。

schemaは追加fieldを禁止する。文字数はUnicode code pointで数え、Rust charsとTypeScript Array.fromの境界を一致させる。plannerのmutationはsurvivorが両入力のいずれか、deprecatedIdsが他方の1件、両者が相異なることをhostで確認する。retainedGroupIdsは重複のない実在group集合。coverageは両入力の全groupをちょうど一度列挙し、retainedは自分自身、entailedは実際に保持されるgroupだけを参照する。省略先同士の循環や第三候補の根拠を拒否する。

deprecate_duplicateの保持groupはsurvivor全文と完全一致する。mergeは少なくとも1つの旧IDを減らし、元groupの文脈と順序を保持する。構造検査後にrendererがbodyとproposalHashを確定する。verifierにはplannerのrationaleとreasonCodesを除いた構造案、確定body、原文を送る。verifier findingsは原文groupと一対一対応し、target集合は確定coverageと一致すること、全8検査項目とnoNewMeaning・noUnresolvedContradictionがpreservedであることをgateで要求する。schemaに通ったsupportedだけでは不足である。

完全一致経路でも本文だけでなくtitleの意味、適用範囲、identity、type・polarity、重要metadataと出典の制約が等価であることを要求する。metadataは全fieldを保存・比較し、無視可能な運用fieldだけを明示allowlistにする。未知fieldの差は非互換とする。一般scopeの判定は現行関数を共有し、その上で全appliesToの正規化一致を要求する保守的なsubsetから開始する。

source linkの不在だけで原文同士の完全一致を否定しないが、どちらが正しいか外部根拠で決める必要がある提案はneeds_evidenceにする。callerが指定したURLをLLMに取得させない。保存済みsource fragmentだけをsnapshotに読み、出典の検証は既存の取得経路へ委ねる。

17. provider容量と命令境界を独立に認定する

評価単位はmodel名だけでなく、model revision・prompt/schema hash・transport・provider設定の組とする。実運用と同じrequest_decision経路で認定する。plannerとverifierが同モデルでも開始できるが、別モデルとの比較はcalibration上で実際に設定可能な候補に限定する。設定を無断で切り替えず、認定が失効したrouteはsemantic mutationを実行しない。

agent_sessionのcreate→turn→SSE完了→releaseを成功・parse失敗・timeout・cancelの全分岐で追跡する。release成功がhostのloaded-session枠解放を意味するか、provider契約と連続20 session試験で確認する。解放を確認できないときは新規sessionの連打を止め、所有sessionの再利用または文書化された終了APIを実装する。他用途のsessionを削除して解決しない。

初期の同時実行はrouteごと1。容量409は意味判断の不正解に数えずwaiting_providerへ戻し、5秒・30秒・120秒のjitter付き最大3 retry後はroute circuitを5分開く。復帰probe成功後に再開する。transport timeoutは1 request 120秒、JSON再生成はschemaエラー内容だけで最大1回、semantic rejected/unknownを回答が変わるまで再試行しない。待機はschedulerで行いworker slotを保持しない。

raw role delimiter、多言語命令、metadata経由、出典偽装、schema field内の命令、偽の検証結果を回帰に含める。単一文字列routeはJSON encodingと長さ付きdata境界を使用してもrole分離の保証とはしない。そのrouteで全注入ケースが変更を誘発しないことを確認するまでsemantic適用は無効。送信前のmanaged context fingerprintと送信payload fingerprintを両方記録し、Rust literal system promptや任意role昇格をCIで検出する。

18. 容量・費用・公平性

8,000件の固定snapshotで候補探索時間、LLM呼出回数、token数、provider待機、queue滞留、SQLite writer占有時間を測る。8,000は負荷試験の規模であり現在のactive実測件数ではない。採用目標は候補探索p95 500ms以下、writer transaction p95 100ms以下。既存の全vector走査を毎jobで繰り返して満たせない場合、同一index epochの候補計算を共有するか既存vector indexへ切り替え、recallの低下も比較する。

1 pairはplanner 1回、mutation候補だけverifier 1回、schema修正を含めても最大3回。最初の1 knowledge訪問は4 pairまでとし、残りの候補cursorを保存して他のknowledgeへ順番を渡す。routeごとの有効token予算と価格情報を事前計算し、予算未設定ならsemantic shadowも大量には開始せず単件診断に限定する。価格不明のlocal routeはtoken・GPU稼働秒・完了件数を出し、金額0円とは表示しない。

全queueの既存schedulerを維持しつつ、Curationが他queueの継続入力で永久に後回しにならないようweighted round-robinとagingを追加する。負荷試験ではCurationに10 claimに最低1回の機会を保証し、単一repositoryはCuration連続4 claimまでとする。provider共用時は他業務の予約枠を侵食しない。実際の全件完了予測は測定throughputから算出し、固定の完了時間を約束しない。

19. 自動導入・停止・回復

  1. W1の既知穴を閉じ、全activeのrevision ledgerを作る。完全一致以外はshadowに送る。通常の各jobに人手承認は追加しない。
  2. W2〜W7を統合したsnapshot replayで、deterministic回帰・復元・provider20 session試験を通す。未認定routeのsemantic proposalは監査だけに残す。
  3. W8の固定holdoutで第14節の品質条件を通し、比較対象のうち品質条件を満たす最小コストの構成を選ぶ。verifier追加が損失防止に寄与するかもablationで報告する。
  4. 認定済policyで実適用100 mutation、次に累計500 mutationを上限に段階拡大する。各段階で100%のdeterministic postcheck、無作為30件の原文対応監査、最低24時間の運用観測を行う。監査が揃わなければ昇格を待つが、審査とshadowは継続する。
  5. critical error 1件、index/revision不整合1件、100件windowのprovider最終失敗率5%超、またはwriter p95目標超過が3 window連続で発生したら該当semantic routeのmutationを自動停止する。元snapshot・判断traceを保持し、原因を回帰ケースへ追加する。

停止はqueue投入や他業務まで止めない。誤変更の復元は第15節のrevision保護に従う。独立監査は導入品質を判定する活動であり、利用者が毎件mergeを承認するUIにはしない。model/prompt/schema/transport変更時は認定を失効し、回帰＋holdoutと限定適用を再実行する。

21. 作業順、互換性、評価成果物

依存順はW1→W2→W3→W4→W5→W6→W7→W8。W7のprovider診断とW8のgold準備はW1直後から始められる。W2のscope契約が確定する前にpromptを最適化しない。W5のatomic性を検証する前にsemanticを本番へ昇格しない。各単位のPRは反例と対照の結果を含め、巨大なcuration_executor.rsへ機能を積み増さずsnapshot・proposal・verification・policy・applyに分ける。

現行schema.rsはsrc/db/sqlite/core-schema.tsをincludeしており、両方のDDL・migrationを合わせて変更する。既存landscape_curation_queueとlandscape_curation_job_linksは履歴を保持して再利用する。追加tableにはledger・pair・mutation・supersessionの役割を限定する。現在のschema revisionは6だが、実装時の最新revisionに続く番号を確保し、他作業のmigration番号を上書きしない。

関連するcontext_compile v2計画とRust runtime計画に対し、repository identity、readerのdeprecated参照解決、原文provenanceだけを共有contractとする。compileの出力形式や候補選定をCurationの都合で変更しない。統合前後の代表compile要求をreplayし、元の適用条件のknowledgeへ到達できることをgoldで確認する。条件付きgroupを正しくreaderが扱えないケースはmerge eligibilityから除外し、その除外率も公開する。

新規評価CLIの予定contractはcuration evalのsnapshot、labels、policy、route、mode=contract|shadow|quality|load、output directory引数。snapshot DBはread-only、適用試験は使い捨てcopyのRust writerだけを使う。manifestにはsource commit/diff hash、snapshot hash、split/family hash、gold version、prompt/schema/transport hash、model revision、sampling設定、seedの対応可否、全attemptの状態とlatencyを保存する。集計から失敗を黙って除外しない。

semantic scoreは回答が完了した対象で算出し、同時に全eligibleを分母とするend-to-end recallを出す。昇格条件のrecall 85%は後者にも適用し、provider完了率99%以上を別gateにする。各成分を層ごとに算出してから定義可能な層を等重み集計し、未定義層を都合よく落とさず必要サンプルを補充する。bootstrapは10,000回、固定seed、source familyを単位とし、同familyの反復3 trialは独立サンプル数に加算しない。いずれかのtrialのcritical errorは失格にする。

実装後に実行する確認は、対象Rust unit/integration tests、curation contract probes、schema parity、system-context lint/build/check/boundary、SQLite writer ownership、maintainability、Rust clippy、関連TypeScript/API互換テスト。変更範囲に適した検証を完了してからW8実LLM評価へ進む。この計画作成時点ではこれらの新実装テストは実行できず、文書・schema構造検証と区別する。

最終レビューでledger keyを補強する。第12節のcontentRevisionに加え、参照fragment本文と検証状態のevidenceRevision、retrievalVersionをreview key・pair keyへ含める。参照内容が変われば本文不変でも再審査する。DBのupdatedAt全体をkeyにしない。job IDはsubject固定ではなくreview key由来とし、旧landscape-all IDとのmappingを残す。evidence待ちは対応source更新時、candidate待ちは関連index更新時、provider待ちはroute復旧時だけ再開する。適用前CASはこれらの根拠revisionも確認する。

mutationのreasonCodesはCOMPLETE_DUPLICATEまたはCOMPLEMENTARYだけを許可し、CONFLICTやMISSING_EVIDENCE等とmutationを同時に返した提案は拒否する。scope・metadata非互換をplannerが無視してもhost gateで止まる。exact laneの検証結果も同じValidatedMutation型へ変換し、transaction入口を分岐させない。

LLM最大3回は生成呼び出しの上限であり、transport retry最大3回はその各呼出しへの追加attemptである。全体の最悪attempt上限は12回。費用・token予算はこのattemptも数える。embeddingは別種の計算として1回と有界retryを計上する。queue leaseが失われた時点で残りの呼び出しと適用をcancelし、同一pairの再開時は既存の入力・proposal hashに一致する成功結果だけを再利用する。

22. 設計に取り込んだ公開知見

2026-09-06に一次資料を確認した。FActScore（Min et al., EMNLP 2023、https://aclanthology.org/2023.emnlp-main.741/）から、全体のもっともらしさでなく細かい主張と根拠の対応を評価する考えを取り入れた。人物紹介の事実精度を、条件付きの規範knowledgeへそのまま転用したものではない。

Kamoi et al.のself-correction調査（TACL 2024、https://aclanthology.org/2024.tacl-1.78/）を踏まえ、LLM自身による再評価だけで改善を証明しない。AnthropicのDemystifying evals for AI agents（2026-01-09、https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents）を参考に、code・model・人の評価を役割分担し、実行基盤の失敗と意味判断を分離する。これらは設計判断の根拠であり、このCurationが最高性能であるという実証ではない。
