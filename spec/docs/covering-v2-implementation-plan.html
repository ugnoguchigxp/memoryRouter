Covering v2 改善実装計画

作成日: 2026年9月6日。状態: 実装着手可能な計画、自己レビュー最終97/100点。対象はRust residentのCoveringと接続するFinalize。現行ロジック評価のF1〜F8を実装可能な変更へ落とす。この文書の作成は実装や本番切替の実施を意味しない。

目的と完了条件

元資料で支持されない知識、LLMの不正応答、別プロジェクトのidentityを保存経路に流さない。近似した有効候補を捨てず、一時障害と再評価から回復できるようにする。正負両方の経路で同じ受理条件を使い、既存の単一writer、claim fencing、atomic persistenceを維持する。

完了は、F1〜F8の回帰試験、並行実行・移行試験、正解付き品質評価、段階導入の全gateを満たし、失敗・保留の候補に理由と回復経路があること。計画書の自己採点と、実装後の採用精度は別の数値として扱う。

実装範囲と前提

  • 対象: crates/context-stilld/src/domains/queue_lifecycle/covering_executor/、finalize_executor.rs、Coveringのclaim/persist接続、SQLite schema/migration、関連プロンプト、既存retry入口、必要な観測項目。
  • DBは追加テーブルと追加カラムの移行を行う。公開MCP schema、認証、Finding抽出、Compileランキング、Curationの自動統合方針は変更しない。
  • Rustを本番の実行経路とする。TypeScript/PostgreSQLにv2の推論処理を二重実装せず、v2 queueを旧workerが処理できない境界とread側の互換性を検証する。
  • polarityが文字列negativeと完全一致する場合だけ負の経路とする既存ingress contractは維持する。LLMにpolarityの変更権限を与えない。
  • Finalizeとqueue executorには他作業の未コミット変更がある。実装開始時に最新コードと差分を確認し、変更箇所を関数単位で統合する。今回の資料の行番号を固定パッチとして使わない。

確定する処理順

  1. claim時にprotocolVersion、attempt、source provenance、信頼済みidentityを固定する。途中で設定を読み替えない。
  2. 正負共通でsourceを取得する。元本文とdiffは別sourceとして扱い、候補内容そのものを独立した確認資料として数えない。
  3. 原資料を保持したまま、関連箇所と前後の条件・反証を抜粋する。prompt内の引用はこの抜粋集合からのみ選択できる。
  4. LLMが候補を清書・分類する。カテゴリの補完、procedure repair、既存Finalizeと共通化した決定的な匿名化・本文整形を終えてから、保存予定本文の主張が資料で支持されるかを検証する。
  5. identity、型、重要度、主張の支持、根拠の位置、必要な適用カテゴリを実行側で確認する。不足をLLMの自信スコアで代替しない。
  6. 最終本文の完全一致・近似関係を同一scope内で確認する。近似だけを理由にduplicate/near_duplicateで終了しない。
  7. writer transaction内でclaim所有権と入力版・重複相手の版を再確認し、Evidence revision、queue遷移、Finalize要求、イベント、lease解放を確定する。
  8. Finalizeは要求された不変revisionを読み、保存直前にもrevisionとclaimを確認する。draft知識、参照、FTS、embedding、完了状態をatomicに保存する。

応答とidentityの契約

v2実行では正・負・外部評価を単一のJSON contractにそろえる。schemaVersion=2とstageを必須にし、未知enum、必須項目欠落、余分なidentity、型違い、範囲外スコアをparse_failedにする。大文字小文字の補正、titleの存在による採否推定、statusだけの採用からのbody補完は行わない。

段階ごとの応答型
stage 返せる内容 実行側の制約
assessment ready候補またはinsufficientと理由 readyにはtitle/body/type/importance、3カテゴリの配列キー、claimsが必要。カテゴリ配列はこの段階だけ空を許可して補完へ進む。重要度は整数0〜100。confidenceも返すなら整数0〜100に限定する。

procedure_repair title/bodyまたはinsufficient type=procedureを固定。修正本文の最終支持検証を必ずやり直す。

LLM用enumのreadyは実行側が全gateを満たした後だけ既存永続化statusのknowledge_readyへ変換する。duplicateやprovider_failed等の実行結果はLLMに決めさせない。insufficientは候補が付いていても採用へ変えない。unknown fieldは拒否し、拡張はschemaVersionの変更で行う。

responseはRustのserde tagged enumと同じJSON Schema fixtureを持ち、各stageにexpected schemaをbindingする。assessment/repairの自然文を基本は日本語にし、固定見出し・識別子は保持する。titleは1〜200文字、bodyは1〜8,000文字、material claimsは1〜32件を上限とする。超過はparse_failedであり、後半を捨てて採用しない。各claimにはclaim ID、最終本文の範囲、支持判定、引用の配列を持たせる。verificationが追加した未支持claimを無視しない。

identityはsource adapterが渡した共通project identity resolverの結果とprovenanceを固定する。優先順位は共通resolverのprojectRef、repoKey、repoPathに従い、別名の同一性は確認済みaliasだけを使う。LLMと候補本文からidentityを新設しない。identity不足・競合はinsufficientと専用reasonで保持し、補正されたsource metadataを使う明示的な再処理を可能にする。

v1のラベル形式はv1用parser内だけに残す。v2でv1応答を受けた場合にfallbackして採用しない。v2の負のpromptも contexts/coverEvidence/negative.context.toml を正本とし、旧 shared/prompts/cover-negative-evidence-rust-v1.txt はv1専用に固定する。外部finalのラベル形式とJSON指示の混在を解消し、catalogは生成コマンドから更新する。

主張と根拠の契約

SourceEvidenceはsource ID、取得時刻、source kind、原本文hash、提示したexcerpt本文・UTF-8 byte範囲、excerpt hash、取得経路を持つ。改行、コードの字下げ、箇条書き、否定、数値を保持し、解析用の正規化textと引用用の原文を分ける。旧token readRangesは既存の正規化規則から原文への対応表で変換し、変換不能なrangeを原文byteとして読まない。

最終title/bodyの各判断、条件、手順、fix、検証方法をmaterial claimとして列挙し、支持するexcerpt IDとquote、byte範囲を必須にする。validatorはUTF-8境界、範囲内、quote一致、提示済みexcerptへの所属を確認する。検証LLMは最終本文から主張を再抽出し、生成側が不都合な主張を省略していないか確認する。主張が0件、矛盾または不明のmaterial claimが残る場合は採用しない。

引用が実在することは意味的な支持の証明ではない。意味の照合には検証LLMを使い、同一モデルに共通する誤りが残る点を正解付き評価で測る。high-riskタグは重要度・観測の優先度にのみ使う。根拠0件の免除や、同じ事象の言い換えによる件数加点を廃止する。一つの明確な一次資料が全主張を支えるなら、機械的に資料2件を要求しない。

匿名化は支持検証前に一度だけ行い、原文から保存予定本文への変換記録を保持する。scope用identityは匿名化して失わず、検索用columnへ保存する。Finalizeは検証済みartifact_hashと保存予定のtitle/body/type/appliesToのhashが一致することを要求し、後段の清書・正規化で意味を変えない。新たな変換が必要なら新generationでCoveringへ戻す。原文引用のlocatorは匿名化後の本文位置と混同しない。

knowledge_candidateの本文しかなく独立したsource provenanceがない場合はinsufficient / source_provenance_requiredとする。明示的なユーザー方針は、その方針を述べた元メッセージを一次資料にできる。生成候補をそれ自身の検証根拠にはしない。

外部URLは取得済みIDのallowlistからのみ引用可能とする。取得成功をexternal_verificationとして自動付与せず、fetched・supports・contradicts・backgroundを区別する。検索結果のsnippetは根拠に使わない。外部検索の要否を決める既存heuristicは当面残すが、support_verificationで公開仕様の裏付け不足が出た場合は一度だけ外部検索へ進める。元資料が十分なrepo方針に不要な外部検索を強制しない。

重複の契約

重複で終了できるのは、同一の確認済みscope、polarity、type、適用カテゴリ集合、正規化title/bodyが一致した場合だけである。identity不明の既存知識は自動棄却の根拠にしない。global知識はrepo知識の自動棄却相手にしない。再処理元Evidenceから作られたknowledge自身を比較から除外する。

平文は改行コードと連続する横空白を正規化するが、大文字小文字、句読点、否定、数値、コード、インラインコードは保持する。コードを含むblockの字下げと空白は変えない。正規化versionをfingerprintに含める。正規化による完全一致と意味検索のスコアを混同しない。

完全一致検索は上限40件や更新順に依存させない。近似候補は同一scopeのFTS最大20件とvector最大20件を統合し、最大8件を関係評価に渡す。vector障害時はlexicalへ縮退し、障害を記録する。近似検索が失敗しても完全一致の正しさと根拠検証を満たす候補を棄却しない。

近似関係はequivalent、complement、contradiction、unrelated、unknownとしてduplicate_refsに記録する。exactでない候補は、元資料の支持があればdraftとして保持し、既存知識の自動削除・統合・active化はしない。意味検索による自動棄却は別の品質検証が済むまで導入しない。

Evidence改訂とFinalize

evidence_coverage_resultsは互換性のため最新結果を示すprojectionとして残し、v2の採否・候補・根拠・identityを不変なcovering_evidence_revisionsへ保存する。Finalizeはprojectionを推論入力にせずrevisionを読む。既存Finalize rowはEvidenceごとに一つを維持し、requested_revisionとclaimed_revisionを区別する。

再Coveringが成功したら最新revisionをrequested_revisionへ設定する。Finalizeがpending/failed/skippedならpendingへ戻し、別revisionのattemptと旧errorをresetする。runningの場合はclaimed_revisionとロックを変えず、requested_revisionのみ進める。保存直前にrequestedとclaimedが異なれば旧結果を保存せず、次のrevisionをpendingにする。claim自体を失っていたら一切更新しない。

completed済みの知識を同じ内容で再確認した場合は重複保存しない。別内容のrevisionが来た場合は自動でactive知識をdraftへ戻さず、再評価結果を保持してレビュー対象にする。再評価がinsufficientでも既存知識を自動削除しない。

追加schemaとデータの責任範囲

実装時に src/db/sqlite/core-schema.ts と crates/context-stilld/src/domains/sqlite_writer/schema.rs のmigrationを同時に更新する。既存columnの追加はtable_infoで検出し、二度適用しても変化しないようにする。現在確認したschema revisionは6だが、番号は実装統合時の未使用な次番号Nを採番する。PR内ではNを実数で固定し、並行作業のmigration番号を上書きしない。

revision_noはwriter transactionで最大値+1を割り当てる。attempt_idはCovering lease IDとinput_generationから決定し、同じ結果の再送は新revisionを作らず既存の結果に一致するか確認する。resultを上書きするUPDATEをrepositoryに公開しない。artifact_hashは最終本文・型・polarity・identity・適用カテゴリのcanonical JSON hashとし、入力や引用の変化はinput_hashで別に追跡する。

input snapshot取得の外部I/Oはwriter transaction外で実施し、永続化するときにqueueがrunning、lease所有、generation、candidate/provenance hashが一致することを検査する。取得前に落ちた場合は同世代で取り直してよい。inputsのevidence_bundle_jsonには初期sourceのsnapshotを固定する。後段の外部検索で増える資料と各requestで実際に使ったexcerpt集合は、そのattemptのresult_jsonに追記してrevisionとともに不変保存する。これは初期inputを書き換える操作ではない。

同世代のretryでは入力snapshotと前回revisionにcommit済みの外部資料を再利用する。commit前のcrashで失われた取得だけは再取得してhashと時刻を新attemptへ記録する。source hashは資料全体、excerpt hashは提示分、request hashは実送信messagesを区別する。forceRefreshEvidenceまたは明示的な再評価は新世代にし、保存済みの古い外部資料を再利用しない。

Finalizeの同じevidence_result_idに複数rowがないことをmigration preflightで検査し、partial UNIQUE indexを追加する。既存に重複があれば勝手に削除せず、該当IDを出力してmigrationを停止する。修復は知識ID、完了状態、claim履歴を確認した別の修復手順で実施する。元のEvidence一意triggerは維持する。

fingerprint cacheはknowledgeのtitle/body/type/polarity/scope/identity/applies_to/statusの更新・削除で無効化するSQL triggerを持つ。Finalizeの書込みでは同時に再構築する。cache欠落時は同scopeの正本を上限なしで走査し、writer外で正規化して一致を探す。更新中のcacheを信用して候補を捨てず、persist時に相手のmaterial_hashと状態を再検査する。初期backfillは500件単位で行い、hashが一致するrowだけ短いwriter transactionで保存する。

Finalizeの状態ごとの再評価

新しいknowledge_ready revisionを受けたときの遷移
既存状態 操作 保存条件
rowなし requestedを新revisionにしたpendingを作成 UNIQUE(evidence_result_id)で二重enqueueを防止
pending / failed / skipped requestedを更新しpending。別revisionならattempt、next_run_at、旧errorをreset 同revisionの再送だけでattempt上限を解除しない。明示的retryは理由を残す。
paused requestedだけ更新しpausedを維持 利用者のpauseを再評価で解除しない。既存resume操作で進める。
running requestedだけ更新。claimedとclaim_token、lockは維持 旧実行の完了transactionで版の不一致を検出し、知識を保存せずpendingへ戻す。
completed、artifactが同じ 完了とknowledgeを維持。新revisionを検証履歴として関連付ける 既存knowledgeのmaterial_hashが前回保存時と一致すること。参照追記も履歴として保持。
completed、artifactが異なる 未編集draftだけをpendingに戻す。activeまたは別作業が編集した知識はpausedとしreview itemを作る 既存knowledgeのstatusとmaterial_hashを保存直前にCAS。競合すれば書換えない。

Coveringの明示的再処理開始時にinput_generationを増やし、既存FinalizeのrequestedをNULLにして旧入力を無効化する。この操作は queue_lifecycle/state.rs::retry_queue_job_for_connection のtransaction内で行い、Coveringがrunningなら現状どおり受理しない。新しい結果がまだ出ていない間はFinalizeをclaimしない。既存runningの旧世代は完了前のgeneration照合でdiscardする。

再評価の結論がinsufficient/duplicateなら旧要求を無効のままにし、非running・非pausedの未完Finalizeをskippedへ遷移する。再試行中のprovider/parse失敗なら結果を待ち、上限到達では未完Finalizeをfailedにしてupstream_failedを記録する。既存completed知識は削除・無条件変更しない。pausedは利用者の停止意図を保持する。

Finalizeの成功だけでなくmark_failed、mark_retrying、mark_skippedにも同じclaim_token・generation・revision fenceを適用する。旧実行のエラーで新revisionをfailedにしない。古いclaimは更新0件をSupersededとして扱い、所有権を奪い返さない。

activeまたは編集済み知識を保護するreview itemは既存schemaのsource=promotion_gate、reason=promotion_gate_review、proposed_action=review_only、status=pendingを使う。idempotency_keyはcovering-v2-review:{knowledgeId}:{revisionId}とし、payloadへ期待material_hash、requested revision、旧新本文の参照を保存する。Curationへの自動enqueueやmergeは行わない。

レビュー解決のための管理用writer commandをWP5で追加し、review ID・revision ID・expected material_hash・actionを必須とする。actionはkeep_existingまたはcreate_separate_draft。前者は結果を履歴として残してFinalizeをskipped、後者は承認をCASで記録してpendingへ戻し、revision IDから決定した別knowledge IDへdraftを作る。activeな元知識を変更しない。新generationまたは元知識の編集で承認は無効になる。単にresumeしただけでは承認済みにならない。

並行実行の順序と冪等性

  1. Covering persist: 所有権とgenerationを確認 → input/attemptの一致確認 → revision保存とprojection更新 → 完全一致相手の現状態を再確認 → Finalize要求・review item → queue遷移 → lease解放 → event → commit。
  2. Finalize claim: v2対応readerだけがrequestedをclaimedへコピーし、新claim_tokenを割り当てる。input generationと有効なknowledge_ready revisionを同時に検査する。
  3. Finalize execute: snapshotを読む → 機械的validator再実行 → writer外でembedding → persist直前にclaim_token・generation・requested=claimed・knowledgeの変更有無を再検査。
  4. Finalize commit: 最終保存本文に対するscope付き完全一致を再検査 → Knowledge・fingerprint・出典リンク・FTS・embedding → queue完了 → commit。完全一致の既存knowledgeを発見したらcanonicalへの参照を保存し、新Knowledgeを作らず終了する。

2件のCoveringが同時に同じ知識をreadyとしても、最後のFinalize transactionで先行して保存された知識を検出する。この境界で一致相手がないことを確認してからinsertするため、近似検索の時点差に依存しない。embedding等の外部呼び出しをtransaction内へ持ち込まない。staleな結果を持つ実行がqueue更新0件なら、前に行ったKnowledge関連の書込みもrollbackする。

自動duplicateの相手はactive、または出典を持ちv2の全gateを通ったdraftに限る。未検証legacy draftや、失敗済みEvidenceしか持たないdraftを理由に有効候補を捨てない。完全一致の比較はhashだけで結論を出さず、canonical内容とscopeの一致も確認する。fingerprint未計算の同scope候補のfallback走査がwriter時間予算を超えるならdiscardせず、index_not_readyとしてretryする。

snapshotの削除はsourceを削除しただけでは自動連鎖させない。通常source削除と、保存済み引用を含む完全削除要求を区別する。完全削除では対象inputを参照するrevisionと要求を列挙し、全Finalizeのrequested/claimed pointerをNULLにして未完claimを無効化し、Knowledgeに残る引用を削除・無効化する。その後projectionのcurrent pointerと本文・引用を消去してevidence_deletedにし、revision、inputの順に同一writer transactionで削除する。EvidenceとFinalizeの識別rowはtombstoneとして残す。残存Knowledgeにはevidence_deletedを記録し、検証済みという表示を維持しない。型はFK RESTRICTと整合させ、fixtureで経路を確認する。

品質・費用の比較gate

WP0で600ケースをsource family単位で固定し、200件を調整用、400件をholdoutへ分ける。同じログの断片や言い換えを両方へ入れない。holdoutは支持された候補200、非支持候補100、重複・差分ペア100とする。ペアには完全一致20、否定・数値・scope等の重要差分40、言い換え・補足40を含める。正負、日本語・英語、4 source kindを含め、high-riskの非支持例は50件以上にする。

期待する採否・主張・引用・scope・ペア関係を匿名化した原資料から先に確定し、実装出力を見て正解を合わせない。曖昧なケースは調整用へ移し、holdoutの件数を補充してからhashを固定する。別の実装担当者が根拠とラベルを点検する手順をWP0の成果物に含める。現時点ではデータセット未作成であり、以下の数値は目標である。

移行・段階導入・切戻し

  1. 互換reader先行: v1/v2両方を識別し、v2のgeneration/revision/claim_token fenceを持つbinary Bを作る。v2無効で既存queueの回帰試験を行う。旧binary Aは移行後の安全な切戻し先にしない。
  2. offline rehearsal: SQLite backup APIで取得した複製へschema Nを適用する。row件数、FK、Finalize重複、revisionとknowledgeの対応、旧pendingの読込みを検査し、2回目適用と途中失敗rollbackを試す。
  3. 本番移行: 新しいclaimを止め、running jobの完了または所有権を無効化した停止を確認する。writerを一つに限定してbackupを取り、Bでmigrationを適用する。manifestにDB canonical path、backup hash、schema、binary、時刻、queue件数を保存する。
  4. legacy処理: v1の完了済みEvidenceをv2検証済みへ昇格しない。既存pending Finalizeのv1処理をBで完了させるか、ID allowlistでCovering再評価へ戻す。両方を同時に同じ候補へ適用しない。
  5. 比較: 本番DBへ結果を書かない複製上でv1とv2を比較する。本番にshadow LLMを追加して負荷を倍増させない。品質・費用gateが合格してから次へ進む。
  6. canary: DB pathにbindingしたjob ID allowlistで20件、続いて100件をv2処理する。正負を含め、取得可能なsource kindを網羅する。各waveを最低24時間観測し、未到着のsourceはoffline試験の結果と区別する。
  7. 通常運用: canary全件が説明可能なterminal状態または理由付きpauseで、採用内容の確認と運用gateを通った後に新claimのprotocol_version=2を既定にする。過去の棄却候補を無制限に再enqueueしない。

新設定は CONTEXT_STILL_COVERING_PROTOCOL=v1|v2 と既存の CONTEXT_STILL_RUST_COVERING_MODE の直交する組合せとして追加する。offは新Covering claimを停止するだけなので、緊急停止ではFinalizeのv2 claimも停止する専用gateを併用する。v2のinput generationを旧workerが処理しようとしたら明示的なunsupported_protocolとして停止する。PostgreSQLにv2要求を送る場合も同様に拒否する。

即時停止条件は、根拠0件の採用、identityの変化、旧revisionの保存、二重Knowledge、FK/partial writeのどれか1件。運用停止条件は直近50件でprovider/parse失敗率がbaselineより5 percentage points超悪化、または他queueの待時間が10%超悪化。50件未満でも重大欠陥は待たずに停止する。canaryの各採用は根拠との対応を確認する。

切戻しは新claim停止 → runningの完了/失効確認 → queueとrevisionの整合性採取 → schema N対応のBへ切替 → v2 claim停止を維持、の順に行う。新Evidenceをlegacy projectionだけで読むAやv1 workerへ流さない。現在のschema readerは新revision番号を拒否するため、schema versionの数字だけを下げる操作は禁止する。

full DB復元は最終手段であり、移行後の全writeを失う可能性がある。実施するならwriterを停止し、移行後writeと監査履歴をexportし、対象期間の差分と再投入可否を確認してからbackupを復元する。通常のロールバックはDBを保持するBへの切替で行う。復旧後はsource/identity/queue/revision/knowledgeの整合性と該当不具合の回帰試験を確認し、新しいallowlistでcanaryから再開する。

Bはv2 producerの新挙動を無効化しても、revisionを読みfenceする能力を必ず残す。schemaを読めるだけの旧仕様binaryをBと呼ばない。v1→v2の有効化後に、障害回避のため候補を自動でv1へ格下げしない。canaryで発生した問題はallowlistのrevision/knowledge単位で追跡し、全DB復元をせず是正できるmanifestを残す。

移行と切戻し 15/15 追加migration、重複preflight、互換reader、v2の旧reader拒否、停止・復旧順を定義。
実装可能性 10/10 既存関数とschemaへ変更を割り当て、依存順と段階gateを固定。
試験と品質評価 13/15 回帰・crash・実モデルの測定方法は具体化済み。600ケースのラベル監査と費用測定は実装工程で実施するため2点留保。
観測 4/5 metric・reason・再現hash・削除を定義。長期保存容量の実測は未実施のため1点留保。
明確さ 5/5 確認済み事実、設計判断、初期設定、未計測の目標を区別している。

97点は計画の具体性と整合性に対する自己評価であり、第三者評価でも、実装後の精度97%という意味でもない。本番有効化前にはWP0とWP6の実測gateを満たす必要がある。採点にかかわらず、根拠・identity・revision・rollbackの重大欠陥が一つでも見つかれば実装完了にせず計画を更新する。
