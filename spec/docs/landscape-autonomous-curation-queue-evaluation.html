LANDSCAPE Autonomous Curation Queue Evaluation

Status

  • Status: Findings / GO
  • Version: 0.2
  • Last updated: 2026-08-27
  • Scope: 重複知識、DeadZone、到達性修復をLLMへ委譲する案の妥当性評価

結論はGOである。継続的な人手判断をLLMへ移す方向は、現在の件数と既存queue architectureに合っている。自動実行の条件と段階解放は、 LANDSCAPE Curation Queue High-Level Specificationに定める。

推奨する役割は「知識を自由に整理するagent」ではなく、deterministic detectorが作った候補を評価し、typed action planを返すbounded curatorである。mutationの可否はLLM confidenceではなく、別のdeterministic policy gateが決める。

0.1 Autonomous runtime decision

実行時のCuration処理に人間承認を置かない。LLM評価後はdeterministic policyが自動委譲、記録のみ、証拠待ち、blockedのいずれかへ決定し、条件不足caseをユーザー判断待ちにしない。未処理または失敗したjobはLANDSCAPE画面に観測用として表示するが、承認操作は提供しない。

以下のshadowと人間labelは、policy精度を測るoffline評価手段であり、production jobの状態遷移や完了条件ではない。この節と競合する旧提案は、 Version 1.2 implementation specificationを優先する。

1. 現行システムの確認

現行実装は、提案された役割の一部をすでに持っている。

  • Coveringでは、保存前にlexical / semantic dedupeを行い、duplicateまたはnear-duplicateを新規Knowledgeとして保存しない。
  • LANDSCAPEはDeadZone communityを抽出し、知識ごとにmerge、deprecate、keep separate、promote、needs evidenceをheuristicで推薦する。
  • deadZoneMergeReviewは、DeadZoneとcanonical候補をLLMへ渡し、merge可否と統合後bodyをstructured resultとして返す。
  • mergeActivationFinalizeは入力body hashとstatusを再確認し、merge body、appliesTo union、旧Knowledgeのdeprecationを反映する。
  • 現在のUIでは、人間が「Request merge review」と「Send to Finalize」を押す。deprecateは確認dialog後に即時反映し、keep separate、promote、needs evidenceはdecision記録のみを行う。

Queue Dashboardは5つのvisible tabを持つが、内部型にはmergeActivationFinalizeを含む6つのqueue名がある。そのため新しい「第6のvisible queue」は、実装上は7番目のtechnical queueになる。番号ではなく責務名で扱うべきである。

2.1 「同じ文面」と「同じ知識」は一致しない

active Knowledgeには、titleとbodyが完全一致する8 group、余剰30件があった。しかしrepo identityとappliesToまで同一の余剰は0件だった。完全一致文面のすべてが異なるrepositoryまたは異なる適用scopeに属していた。

したがって、semantic similarityやLLMの「内容が同じ」という判断だけでmergeしてはならない。repository eligibilityとscope compatibilityをcandidate generation前とmutation直前の両方でfail-closedに適用する必要がある。

3. 自動化前のblocking findings

3.1 SQLiteでは主要semantic evidenceが利用されていない

現行のSQLite backendでは、次のrepository pathが明示的に空結果を返す。

  • DeadZone Knowledgeに対する類似Knowledge候補
  • semantic community assignmentとrelation / semantic comparison
  • contradiction detection用Knowledge、recent selection、semantic neighbor pair

この状態では、UIのBest Candidateが空になり、LLM merge reviewへ自動enqueueするpairを作れない。今回の再計算でもsimilarity threshold 0.85と0.90の両方で293件すべてにcanonical候補がなかった。LLM queueを追加しても、入力候補の品質不足は解消しない。

3.2 DeadZoneはquality verdictではない

現行のreachability riskは、active、未選出、累積選出0、embeddingあり、importance / confidence、source density等から算出される。これは「到達されていない」を示すが、「不要」「重複」「誤り」を示さない。新しい、niche、特定repo専用、まだ該当goalが来ていないKnowledgeも同じbucketへ入る。

特に全communityでfeedback confidenceがinsufficientであるため、LLMが自然な説明を返しても、そのactionがretrieval outcomeを改善する証拠にはならない。

3.3 現行mutationは自動rollback contractを持たない

merge finalizeはstale inputをbody hashで防ぎ、input snapshotも保存する。一方、product-levelのundo action、merge lineageからの自動restore、再playによるnon-regression gateはない。誤mergeはcanonical body変更と旧Knowledge deprecationを同時に起こすため、自動化前にrecoverable mutationとして定義し直す必要がある。

3.4 Core queueとLLM capacityを競合させてはならない

計測時点でEpisode queueはpending 1,083 / failed 256、Covering queueはfailed 308だった。新しいcuration laneを同じprovider poolへ無制限投入すると、Knowledge生成と利用のcritical pathを遅らせる可能性がある。low-priority、daily budget、aging、queue pauseを独立して設定する必要がある。

4. 推奨する責務境界

Table: Curation responsibility boundary
Stage Owner Contract
Candidate detection Deterministic retrieval repository eligibility、scope、embedding、similarity、usage、source、ageからbounded候補を作る。
Semantic judgment LLM curator merge、keep separate、repair scope、needs evidence、escalateと根拠をtyped JSONで返す。
Mutation admission Deterministic policy gate LLM confidenceだけを使わず、scope、evidence、age、usage、replay、canary budgetを検証する。
Mutation Existing finalizer input hash、status、idempotency、lineage、audit、rollback snapshotを保持して反映する。
Ambiguous case Deterministic policy LLM disagreement、scope conflict、contradiction、insufficient evidenceを理由code付きblockedまたはawait_evidenceとして自動終端する。

Missing embedding、source link欠落、stale indexなど、deterministicに修復できるものをLLMへ送らない。LLMはsemantic subsumption、矛盾、canonical body compositionのように意味判断が必要な箇所だけを担当する。

5. Queue案の評価

最終形としては、landscapeCurationという新しいvisible laneを設ける価値がある。ただしこれはmerge executorではなく、LANDSCAPE findingを自動発見・評価・routingするorchestratorとする。

  1. Versioned LANDSCAPE snapshotからreview candidateをmaterializeする。
  2. 同一findingの重複enqueueをidempotency keyで防ぐ。
  3. deterministic evidence bundleを固定してLLM curatorへ渡す。
  4. LLMはtyped action planとcounter-evidenceを返す。
  5. policy gateがauto-resolve、existing merge review、repair candidate、blocked outcomeへroutingする。
  6. mergeは既存deadZoneMergeReviewとFinalizeを再利用する。

最初のPoCでは新queue tableを作らず、既存landscape_review_itemsのcandidateに対してshadow evaluationを実行してもよい。accuracyとaction distributionが分かる前にqueue schema、dashboard、schedulerを増やす必要はない。

6. 初期automation policy

Table: Initial action policy
Action Initial mode Reason
Missing embedding / index repair Automatic deterministicで可逆、LLM不要。
needs evidence Automatic routing source repairまたはobservation待ちへ送るだけでKnowledgeを破壊しない。
keep separate Automatic with TTL 同じfindingを一定期間抑制し、signal変化後に再評価できる。
appliesTo / reachability repair Blocked until replay gate replay contractが実装されるまでは自動終端し、実装後にbounded automationへ解放する。
merge / deprecate Exact duplicate only V1はbodyとnormalized appliesToが完全一致する場合だけ自動deprecateし、それ以外はblockedにする。
contradiction / cross-repository candidate Automatic block scopeまたはpolicy conflictをmutationせず、理由付きterminal outcomeとして記録する。

7. 検証計画

Phase 0: Evidence parity

  • SQLiteでscope-aware nearest neighbor、semantic community comparison、contradiction candidateを実装する。
  • PostgreSQLとSQLiteで同一fixtureのcandidate pair、similarity order、scope exclusionを一致させる。
  • 同文面・異repo fixtureを必ずnegative caseに含める。

Phase 1: Shadow evaluation

  • 既存review itemを変更せず、最低200件のstratified caseでLLM action planだけを保存する。
  • merge、deprecate、repair、keep separate、needs evidence、contradictionを含める。
  • 人間labelは初期評価用に限定し、2者labelと不一致adjudicationでreferenceを作る。
  • 現行heuristic、LLM curator、heuristic + LLM + policy gateを同一候補で比較する。

Phase 2: Autonomous observation

  • UIに未処理job、LLM recommendation、counter-evidence、policy gate結果を表示する。
  • UI表示は観測専用とし、production jobのaccept、override、dismissを要求しない。
  • 既存4件の成功だけを精度根拠に使わない。

Phase 3: Bounded automation

  • 最初はnon-destructive actionだけを自動化する。
  • destructive actionはmax 5件/day、同一repository内、rollback可能、replay gate通過を条件にcanaryする。
  • core queueの待ち時間またはfailure rateが悪化したらcuration laneを自動pauseする。

8. Success / stop gates

Success

  • repository eligibility violationが0件。
  • destructive action precisionのpoint estimateが98%以上、95% confidence lower boundが95%以上。
  • production jobのうちユーザー判断待ちへ遷移する件数が0件。
  • replay上のused retention、wrong、off_topicがbaselineに対して非劣化。
  • rollback rehearsalでbody、status、scope、embedding、lineageを復元できる。
  • Finding、Covering、Finalizeのqueue latencyとfailure rateを悪化させない。

Immediate stop

  • cross-repository mergeまたはscope lossを1件でも検出した。
  • source-supported unique contentをdeprecateした。
  • LLM resultとmutation対象のinput hashが一致しない。
  • rollback不能、audit欠落、同じfindingのmutation loopを検出した。
  • core queueのSLOを超える競合が発生した。

9. Decision

第6のvisible queueというproduct ideaを採用する。landscapeCurationを既存deadZoneMergeReviewとFinalizeへroutingするorchestration laneとして実装し、SQLite evidence parity、offline shadow、autonomous observation、bounded automationの順にaction権限を解放する。

production処理は人間を判断主体から外し、安全条件を満たさないcaseを自動mutationしない。現在のデータでは量的な必要性は確認できたが、semantic duplicateやscope repairのdestructive automation品質は未証明であるため、V1ではblocked outcomeとして残す。
