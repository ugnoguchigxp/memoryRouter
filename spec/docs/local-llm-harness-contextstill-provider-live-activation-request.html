1. 依頼理由と現在の阻害要因

ContextStill側は動的routeへ切替済みですが、live LARMが対応前releaseのため Agent Connectionを取得できません。ContextStillはfail closedでjobをclaimせず、 waiting_for_dynamic_providerとして待機しています。

2026-09-06のread-only確認結果
確認対象 確認結果 必要状態
LARM source HEAD b8f74b28ed530410ad50995b0811de40dbaca591 対応済み
live /health releaseCommit: 01667fe1a4f9acc18794ae9fd4264487c1063647 配備対象commitまたは後続commit
GET /v1/activity HTTP 401 local-nodeのAgent API方針に従いContextStillからHTTP 200
GET /v2/agent-profiles contextstill-backgroundなし 同Profileが1件だけ存在し、deprecatedでない
ContextStill Provider lease active 0件 canary実行中だけactiveになり、完了後に解放される

したがって原因はLARMの契約設計不足ではなく、対応済みsourceとlive releaseの不一致です。 healthが200であることだけではContextStill向けProvider成立とは判定しません。

2. 依頼する作業

  1. LARM worktreeが配備対象commitでcleanであることを確認し、既存release scriptの planを実行する。
  2. plan結果とcleanup対象を確認後、対応済みreleaseをliveへ配備する。
  3. local-node設定へ既存のcontextstill-background Profileと saaa-desktop Audienceが反映されていることを確認する。
  4. Service Activity、Profile discovery、Agent Connectionを公開契約どおり確認する。
  5. claimされたProviderで非streaming JSON completionとHTTP SSE completionを各1回実行し、 Connectionを解放する。
  6. secretを含まない受入結果をContextStill担当者へ返す。

3. 配備手順

最初にread-onlyのplanを確認してください。

cd /srv/ai/apps/local-LLM-harness
git status --short
git rev-parse HEAD
sudo bash deploy/local-node/scripts/release-larm.sh plan

worktreeがcleanで、HEADとplanが本依頼の対象に一致する場合だけ、次の既存手順を実行してください。 

cd /srv/ai/apps/local-LLM-harness
sudo env LARM_RELEASE_CLEANUP_CONFIRM=fbac1c432f65c213769f95f361a0faccbabd5e1ee4f56b4b090c89d3b7dd5890 \
  bash deploy/local-node/scripts/release-larm.sh apply

planが別のcleanup confirmation値を要求した場合は値を推測・再計算して続行せず、 plan全文と対象releaseを確認してから判断してください。

4. Service Activity受入条件

GET /v1/activity HTTP/1.1
Accept: application/json
Cache-Control: no-cache
  • query parameterとrequest bodyを送らない。
  • ContextStillが動作するMacからHTTP 200になる。
  • local-nodeで匿名Agent Connectionを許可する既存方針の場合、長期Bearer tokenを要求しない。
  • live環境のセキュリティ方針としてBearerを必須にする場合は、コードを変更せず、 ContextStillのresident環境へ安全に設定できるcredential受渡方法を提示する。 
{
  "contractVersion": "larm-service-activity.v1",
  "state": "idle",
  "activeWorkloads": 0,
  "observedAt": "2026-09-06T12:34:56.789Z",
  "validForMs": 1000,
  "retryAfterMs": 0,
  "reservationGuaranteed": false,
  "bootEpoch": "epoch-value",
  "configRevision": "revision-value"
}

idleではworkload 0かつretry 0、activeではworkload 1以上かつretry 1,000ms、drainingではretry 1,000msとします。未知field、空の世代値、期限切れsnapshotは 受入不可です。

5. Profile discovery受入条件

GET /v2/agent-profiles HTTP/1.1
Accept: application/json
  • contractVersionがagent-connection.v2である。
  • catalogRevisionが直前のActivityのconfigRevisionと一致する。
  • contextstill-backgroundが一意に存在する。
  • selectionPolicyがexplicit-onlyで、deprecatedがfalseである。
  • Provider protocolがopenai.chat-completions.v1である。
  • saaa-desktop Audienceが利用可能である。
  • HTTP SSE対応の有無をNative WebSocket用streamingProtocolの有無で判定しない。

6. Agent Connection・推論canary

Activityがfreshなidleの場合だけ、次のConnectionを作成してください。

POST /v1/agent-connections HTTP/1.1
Idempotency-Key: contextstill:deployment-canary:<random>
Content-Type: application/json
{
  "agentProfile": "contextstill-background",
  "explicitAgentProfile": true,
  "audience": "saaa-desktop",
  "client": "contextstill",
  "ttlSeconds": 900,
  "allowFallback": false,
  "deploymentPolicy": "existing-only"
}

6.1 Connection作成とclaim

  1. 201または202を受理し、202では同じConnection IDをreadyまでpollする。
  2. {"format":"openai-provider-v1"}でclaimする。
  3. claimのprovider.baseUrl、provider.model、短期tokenだけを使用する。
  4. POST {claimedBaseUrl}/chat/completionsへclaimされたmodel、Bearer、 stream: falseを送り、OpenAI互換JSON responseを確認する。
  5. Profile名をmodelへ代入せず、claimされたmodelを変更しない。

6.2 HTTP SSE canary

JSON canaryと同じclaimのbase URL、model、短期tokenを使い、同じChat Completions endpointへ 次のrequestを送ってください。 

POST {claimedBaseUrl}/chat/completions HTTP/1.1
Authorization: Bearer {claimedShortLivedToken}
Accept: text/event-stream
Content-Type: application/json
{
  "model": "{claimedModel}",
  "messages": [{ "role": "user", "content": "Reply with OK only." }],
  "stream": true
}
  • HTTP statusが200である。
  • Content-Typeがtext/event-streamで始まる。
  • 各eventが空行で区切られたdata: {OpenAI chat.completion.chunk JSON}として読める。
  • 少なくとも1件の有効なdeltaを受信する。
  • 終端のdata: [DONE]を受信する。
  • 成功した非SSE responseをSSE成功として扱わない。
  • Native WebSocket用streamingProtocolをHTTP SSEの前提条件にしない。

JSONとSSEのcanary完了後にConnectionをDELETEし、active Connectionを残さないでください。

7. 禁止事項

  • LARMへContextStill専用endpointを追加しない。
  • SAAAへの通知、callback、webhookを追加しない。
  • /v1/activityへProfile、Audience、Connection IDのqueryを追加しない。
  • claim外のProvider URL、model、credentialをContextStillへ渡さない。
  • 127.0.0.1:44448を動的Providerのfallbackとして案内しない。
  • claim tokenや長期Bearer tokenをlog、報告書、settings、SQLiteへ記録しない。
  • 配備後のcontract不一致を、その場の未承認コード修正で解消しない。不一致内容を証跡付きで返す。

8. 返却してほしい証跡

  • 配備した完全なGit commit ID
  • /healthのreleaseCommit、configRevision、bootEpoch
  • ActivityのHTTP status、state、activeWorkloads、validForMs、retryAfterMs
  • ProfileのID、selectionPolicy、deprecated、protocol、model
  • Connection createのstatus、ready到達、claim成功、JSON completion成功、DELETE成功
  • SSE completionのHTTP status、Content-Type、有効なdeltaの受信、[DONE]終端
  • canary中に127.0.0.1:44448を使用していないこと
  • secretを除去した時刻付き結果

9. 失敗時の扱い

release identity、readiness、Activity、Profile、Agent Connection、推論canaryのいずれかが失敗した場合、 ContextStillはdynamic routeのままfail closedで待機します。LARM担当者はrelease scriptの既存rollbackを使用し、 失敗したcontractとHTTP statusを返してください。 

cd /srv/ai/apps/local-LLM-harness
sudo bash deploy/local-node/scripts/release-larm.sh rollback

10. 完了条件

  • live releaseCommitが配備対象commitまたは承認済み後続commitである。
  • ActivityとProfile discoveryがContextStillホストから受入条件を満たす。
  • 汎用Agent ConnectionからclaimされたProviderでJSON completionが成功する。
  • 同じOpenAI互換Chat Completions endpointでHTTP SSE completionが[DONE]まで成功する。
  • canary Connectionが解放され、credentialが残存しない。
  • ContextStillのLLM必須jobが少なくとも1件完了し、Queue件数が減少する。
  • ContextStillの次job境界でActivityが再確認される。
  • 既存のNightWorkers、SAAA、static Provider契約に回帰がない。

ContextStill側の詳細契約は ContextStill動的LARM Provider実装計画、Service Activity契約は local-LLM-harness Service Activity連携契約を参照してください。
