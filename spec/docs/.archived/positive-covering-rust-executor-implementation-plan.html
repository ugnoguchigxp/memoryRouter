Positive Covering Rust Executor Implementation Plan

Status

Status: implemented / archived。作成日: 2026-08-19、完了日: 2026-08-20。実装、offline rehearsal、live backup、12件canary、all rollout、baseline 591件のdrainと照合を完了した。

本文書は Covering Queue Stall Investigation で確定した原因に対する恒久改修と、既存backlogを安全に復旧する手順を定義する。 Rust Runtime Closeout Implementation PlanのRust resident単独ownership、fail-closed、verified mutationの各contractを維持する。 完了証拠は Positive Covering Rust Executor Closeout Evidenceへ集約した。

1. Decision

  1. Positiveおよびpolarity未設定のcoveringEvidence contractをRustへ移植し、 context-stilld runを唯一のresident queue ownerに保つ。
  2. Coveringを既存のgeneric provider優先列へ単純追加しない。専用Covering laneでclaimし、Findingと Episodeの進行を保証する公平性制御を置く。
  3. 現行のnegative executorを共通実行基盤へ統合するが、negativeの入出力contractは変更しない。
  4. Source-only、external evidence、dedupe、procedure quality、persistence、retryを含むTypeScript contract parityが揃うまで、live既定値はnegativeのままにする。
  5. 実装後は固定manifestによるpositive canaryを経てallへ進み、591件という 2026-08-19時点のbaselineを照合しながらdrainする。

2. Goals and Non-Goals

2.1 Goals

  • Positiveとpolarity未設定CoveringがRust residentからclaim、実行、確定される。
  • 各jobがTypeScript実装と同じevidence status、candidate、参照、retry結果を作る。
  • Knowledge-ready時だけFinalizeを一度enqueueし、重複実行でも増殖しない。
  • External evidenceをSSRF防御、prompt-injection guard、引用境界付きで処理する。
  • Backlog復旧中もFinding、Episode、negative Coveringを停止させない。
  • queue inspectとdoctorがsupported/unsupported backlogを正確に報告する。

2.2 Non-Goals

  • Legacy TypeScript continuous supervisorをresident runtimeへ戻さない。
  • Pending rowを一括reset、skip、deleteしない。
  • Live databaseを暗黙に移動、置換、schema再設計しない。
  • Provider pool全体のschedulerを本改修と同時に全面再設計しない。
  • Promptの意味、importance threshold、dedupe thresholdを移植時に変更しない。
  • Canary gate前にlive positive rowを処理しない。

4. Target Contract

4.1 Polarity routing

Candidate origin JSONのpolarityが文字列negativeと完全一致する場合だけ negativeとする。大文字小文字変換やtrimは行わない。欠落、null、空文字、 positive、その他の値はすべてnon-negativeとしてpositive executorへ送る。これは現行 TypeScriptの分岐と同じで、元のorigin JSONは書き換えない。

ProviderQueueClaimSpec.requires_negative_candidate: boolは表現力が不足するため、 次の明示filterへ置換する。 

enum CandidatePolarityFilter {
    Any,
    Negative,
    NonNegative,
}

SQL predicateはNegativeとNonNegativeを排他的にし、同一rowを両laneがclaim できないことをfixtureで証明する。

4.2 Execution modes

CONTEXT_STILL_RUST_COVERING_MODEを次の4値contractへ拡張する。

Table: 4.2 Covering execution modes
Mode Claim可能なCovering
off なし。Legacy workerは起動しない。
negative Negativeのみ。移行中とrollback後の既定値。
canary Negativeと、検証済みcanary manifestに列挙されたnon-negative job ID。
all Negativeと全non-negative。Parityとcanary合格後だけ使用する。

不明なmode、読めないmanifest、database identity不一致、manifest digest不一致は negativeへ暗黙fallbackせず起動時configuration errorとしてfail-closedにする。 Automationの既定値はrollout完了までnegativeを維持する。

4.3 Fair scheduling

現在のprovider candidate比較はqueue orderをagingやpriorityより先に評価するため、Coveringをgeneric listへ追加すると長いbacklogがEpisodeを飢餓させる可能性がある。次の専用laneで回避する。

  • 現行negative_covering_turn_dueをpolarity非依存の covering_turn_dueへ一般化する。
  • FindingまたはEpisodeがrunnableなら、同一provider poolのCovering claimは既定60秒に最大1件とする。
  • FindingとEpisodeがともにrunnableでない場合は、pool capacityの範囲でCoveringを連続drainできる。
  • 同一jobと同一targetに二重leaseを作らない。
  • Fairness testはCovering backlog存在中もFindingとEpisodeのclaim/completionが継続することを検証する。

4.4 Provider contract

  • Queue rowのroute target候補はsource support、external evidence、MCP evidenceのroute設定から解決する。
  • 取得したprovider lease targetを、そのjob内の全LLM stageに固定する。
  • provider_policy=cloud_apiはcloud targetだけを許可する。利用可能なtargetがなければ cloud_api_provider_unavailableとしてretryし、localへ黙ってfallbackしない。
  • Busy、timeout、connection failure、parse failureは分類を保ち、provider cooldownとqueue retryを 二重加算しない。

4.5 Positive pipeline

Rust positive executorは次の順序と短絡条件を維持する。

  1. Queue、candidate、finding、source、provider leaseを読み、audit startを記録する。
  2. knowledge_candidate、wiki_file、web_ingest、 vibe_memoryを同じtoken window規則で読み、source referenceを構築する。
  3. Base candidate、importance、applicability、procedure qualityを正規化する。
  4. Deterministic source-support判定を行う。
  5. Active/draft Knowledgeに対するlexical/semantic dedupeを行う。
  6. URL、public specification、pricing/rate limit、latest/current等の同一predicateでexternal evidence 要否を決める。
  7. Source-onlyならvalue assessmentへ進む。External requiredならquery生成、search、fetch、final assessmentを実行し、設定時だけMCP evidenceを追加する。
  8. Applicability refinementを行う。
  9. Procedureをaccept、repair、ruleへdemote、またはinsufficientへ分類する。
  10. Resultを検証して保存し、knowledge-ready時だけFinalizeをenqueueする。
  11. Audit completed/failedとtool/provider metadataを記録する。

4.6 Result, retry, and idempotency

Table: 4.6 Result handling
Result Queue transition Required mutation
knowledge_ready completed Evidence upsertとFinalize enqueue
duplicate / near_duplicate completed Evidence upsert、Finalizeなし
insufficient completed Evidence upsert、Finalizeなし
reprocess_requested / tool_failed / provider_failed / parse_failed 30秒、60秒、最大300秒の指数backoff。max attempts到達後failed。 診断可能なEvidence/audit、Finalizeなし
未定義またはschema不正 failed Validation error、Finalizeなし

Evidence upsert、Finalize enqueue、queue terminal/retry transition、terminal event appendは同一SQLite writer transactionで行う。Commit成功後にprovider leaseをreleaseする。安定IDまたは既存unique keyを用い、同一(found_candidate_id, producer)のEvidenceと同一EvidenceのFinalizeは 高々1件とする。Commit失敗時はcompletedを返さない。

4.7 Prompt contract

Positive promptをRust sourceへ手作業で複製しない。.s11tnext/catalog.jsonからruntime-neutralな segment bundleを生成し、Rustはinclude_str!で取り込んで同じvariable/trust encodingを行う。

  • 生成対象はvalue assessment、applicability refinement、procedure repair、external search query、 external fetch selection、external final、MCP evidenceとする。
  • scripts/export-rust-covering-prompts.mjsを追加し、 system-context:build後に shared/prompts/generated/cover-evidence-rust.jsonを生成する。
  • system-context:checkは生成物の差分も失敗にし、TypeScript/Rustのrender parity fixtureを gateにする。

4.8 External evidence security

External pathはcanary前のblocking scopeである。Rust fetcherは現行TypeScriptと同等以上の 次を実装する。

  • HTTP/HTTPS以外、credential、明示port、localhost、private/link-local IPを拒否する。
  • DNSの全解決先を検査し、接続先をpinし、redirectごとに再検査する。
  • Response byte、redirect、site数、token budget、timeoutを制限する。
  • Readable text抽出、cache profile、force-refresh semanticsを維持する。
  • Hidden instruction、policy override、tool invocation、source suppression、secret exfiltrationを検査する。
  • Guardのdenyとunavailableはok=falseのtool resultにし、未検査本文を LLMへ渡さない。
  • 許可された本文もuntrusted/tainted/citation-requiredとしてpromptへ境界付きで渡す。

Optional MCP evidenceは設定されたContext7/DeepWiki routeをbounded callで実行する。未設定時は現行どおり no-opとする。設定済みなのにRust adapterが未対応の場合、allへ進めない。

5. Implementation Slices

5.1 Slice A: Claim and rollout control

  • CandidatePolarityFilterと排他的SQL predicateを実装する。
  • off | negative | canary | all parserとfail-closed validationを実装する。
  • Versioned canary manifest loaderとDB identity/content digest検証を実装する。
  • 専用Covering laneと60秒fairness gateを実装する。
  • queue inspectへnegative、positive supported、positive canary、positive unsupportedの runnable countを追加する。

5.2 Slice B: Common and source-only execution

  • Negative executorからclaim/heartbeat/provider/persistence共通部を分離する。
  • 全source kind reader、token window、source refsをRustへ移植する。
  • Source support、base candidate、value assessment、parserを移植する。
  • Dedupe、applicability、procedure repair/demotionを移植する。
  • Atomic Evidence/Finalize/queue transition writerを実装する。

5.3 Slice C: External evidence and MCP

  • External evidence predicateとstage orchestrationを移植する。
  • Search provider adapter、secure fetcher、guard、cacheを移植する。
  • Optional MCP adapterとbounded timeoutを移植する。
  • Tool call/audit event schemaをTypeScript側とcanonical比較する。

5.4 Slice D: Observability and recovery commands

  • Executor stateへmode、last positive claim/outcome、canary manifest digest、polarity別countsを追加する。
  • Event metadataへexecutor=rust、mode、route、target ID、source kind、polarity class、prompt catalog digestを記録する。Secretとraw source本文は記録しない。
  • Read-only backlog manifest、canary plan、reconciliation report commandを追加する。
  • DoctorのQUEUE_EXECUTOR_UNSUPPORTED_BACKLOGは、allで実際に未対応rowが0件に なった時だけ解消する。

5.5 Expected file layout

  • crates/context-stilld/src/domains/queue_lifecycle/executor.rs: lane schedulingとdispatch
  • crates/context-stilld/src/domains/queue_lifecycle/provider_lease.rs、 types.rs: polarity filterとclaim
  • crates/context-stilld/src/domains/queue_lifecycle/covering_executor.rs: common dispatch
  • positive_covering_executor.rs: positive stage orchestration
  • covering_source.rs: source load/support/dedupe input
  • covering_external.rs: search/fetch/guard/MCP
  • covering_prompt.rs: generated bundle renderer/parser boundary
  • covering_rollout.rs: mode、manifest、reconciliation
  • scripts/export-rust-covering-prompts.mjs、shared parity fixtures、queue smoke script

実装時にmodule分割を多少変更してよいが、claim、source、external、prompt、persistenceの責務境界は 保つ。

7. Implementation Phases

T0: Baseline and fixtures

  • Live DBをread-onlyで再集計し、job IDとcandidate/source content digestのmanifestを保存する。
  • Live DBの一時copyと小型fixture DBを作り、live DBへは書かない。
  • TypeScript reference runnerとcanonical fixture formatを固定する。

Gate: baseline全IDが重複なくmanifestへ入り、source欠落と既存Evidenceの有無が説明できる。

T1: Claim, mode, fairness, and prompts

  • Polarity filter、4 mode、manifest validation、専用lane、fairnessを実装する。
  • Prompt bundle generator/rendererとrender parity testを実装する。
  • Live automationはnegativeのまま維持する。

Gate: non-negativeを一切実行しない状態でnegative regression、排他的claim、fairness、invalid manifest fail-closedがpassする。

T2: Source-only positive parity

  • Source load、support、dedupe、assessment、applicability、procedure、persistenceを実装する。
  • Source-only shared fixturesとretry/idempotency testをpassさせる。
  • Live modeは引き続きnegativeとする。

Gate: source-only canonical outputとDB side effectがTypeScript referenceと一致する。

T3: External evidence and MCP parity

  • Search/fetch/final assessment、SSRF defense、guard、cache、optional MCPを実装する。
  • Adversarial URL、DNS rebinding、redirect、prompt injection fixtureをpassさせる。

Gate: guard fail-openが0件で、external fixtureのcanonical resultとaudit metadataが一致する。

T4: Offline rehearsal

  • 専用test DBで全fixtureとqueue smokeを実行する。
  • Live DB copyに対してbaseline全591件相当をdrainするrehearsalを行う。
  • Provider callはrecorded fixtureを使う決定的runと、staging providerを使うintegration runに分ける。
  • Reconciliation reportと推定drain時間、provider負荷、failure比率を保存する。

Gate: job消失0、重複Evidence/Finalize 0、completion-without-mutation 0、unsupported non-negative 0。

T5: Live canary

  1. Effective DB identityを再確認し、context-stilld backupで事前backupを作る。
  2. Read-only canary plannerで最大12件を選ぶ。内訳はsource-only rule 4、procedure 3、external required 2、missing polarity 3とし、不足cohortはsource-only ruleで補う。
  3. Manifestへversion、canonical DB path、schema version、job ID、candidate/source digest、生成時刻を 記録する。Raw contentとsecretは含めない。
  4. Manifestをvalidate後、modeをcanaryにしてresidentを1回restartする。
  5. 選択jobのterminal resultと、非選択positiveが未claimのままであることを確認する。

Canary pass条件:

  • 選択jobがterminalまたは正当なretry backoffにあり、job消失がない。
  • Terminal jobごとにEvidenceがちょうど1件ある。
  • Finalizeはknowledge-ready Evidenceにだけ、ちょうど1件ある。
  • Negative regression、stuck lease、heartbeat lossがない。
  • FindingとEpisodeのcompletionが観測期間中も継続する。
  • External guard bypassが0で、operatorがEvidence品質を手動確認する。

T6: Full rollout and backlog drain

  1. Canary pass後にmodeをallへ変更し、residentを1回restartする。
  2. 既定60秒fairness gateで開始し、provider error率と他lane latencyを観測する。
  3. Cadence変更が必要ならconfigurationだけを段階変更し、同時にconcurrency、provider target、promptを 変更しない。
  4. 15分ごとにreconciliation summaryを取得し、stop conditionを評価する。
  5. Baseline全件がaccountedになった後、遅延retryの期限を待って最終照合する。

T7: Closeout

  • Configuration、queue recovery、doctorの公開文書を更新する。
  • 実測結果とmanifest digestを別のcloseout evidence Spec HTMLへ残す。
  • queue:covering:onceは直ちに削除せずmanual break-glassとして2 release cycle維持し、 resident ownerと同時実行できないguardを追加する。
  • 本計画はcloseout evidenceから置換された時点でarchiveする。

9. Backlog Reconciliation

Baseline manifestの各jobは最終reportで必ず次のいずれかへ分類する。単にpending countが減ったことを成功と しない。

  • completed_knowledge_ready: Evidence 1、Finalize 1
  • completed_terminal_non_ready: Evidence 1、Finalize 0
  • retry_scheduled: attempt、next run、原因が存在する
  • failed_exhausted: max attemptsと最終原因が存在する
  • blocked_source_missing: source欠落を明示し、completedへ偽装しない

最終invariant:

  • Manifest ID総数 = 上記分類の合計で、missing/duplicate IDは0。
  • 期限到来済みでsupportedなnon-negative runnable pendingは0。
  • Completed rowにEvidenceがなく、またはknowledge-ready以外にFinalizeがある状態は0。
  • 同一producerの重複Evidenceと同一Evidenceの重複Finalizeは0。
  • 新規投入rowはbaseline cohortと別に集計し、復旧率の分母へ混ぜない。

10. Stop and Rollback

10.1 Immediate stop conditions

  • Wrong polarity dispatchまたはcanary manifest外のpositive claimを1件でも検出する。
  • Duplicate Evidence、orphan/duplicate Finalize、completion-without-mutationを1件でも検出する。
  • SSRF controlまたはexternal evidence guardがfail-openする。
  • Provider lease heartbeatが途切れ、stale recovery後も同一jobがrunningに残る。
  • Covering開始後にFindingまたはEpisode completionが公平性windowを超えて停止する。
  • Canonical parityに説明できない差が出る。
  • Unexpected provider/parse failureが同一classで連続3件発生する。

10.2 Rollback procedure

  1. CONTEXT_STILL_RUST_COVERING_MODE=negativeへ戻す。
  2. 新規claimを停止し、active jobはheartbeatを保ってcommitまたはretry transitionまで完了させる。
  3. Residentを1回restartし、negativeのみclaim可能であることをinspectする。
  4. Legacy TypeScript supervisorは起動しない。
  5. Correctに確定済みのrowは巻き戻さない。影響job IDをreconciliationで特定し、誤mutationがある場合だけ 事前backupと監査付きrepair commandを使う。
  6. Bulk resetやDB全体restoreは行わず、実データ破損が証明された場合に限り別承認で実施する。

11. Definition of Done

  • Positive、missing polarity、negativeのshared contract fixturesがTypeScript/Rustで一致する。
  • External evidence security fixture、idempotency、fairness、shutdown/recovery testがpassする。
  • all modeでsupported non-negative backlogがRust residentから処理される。
  • Baseline manifest全件がreconciliation分類され、job消失と重複mutationが0である。
  • Finding、Episode、negative Coveringの継続性にregressionがない。
  • Queue inspect、doctor、events、SQLite rowsが同じruntime truthを示す。
  • 公開configuration/recovery文書とcloseout evidenceが実測値で更新される。
