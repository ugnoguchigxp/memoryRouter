Coveringロジック評価と改善候補

評価日: 2026年9月6日。対象は現行Rust residentの covering_executor、組み込みプロンプト、後続Finalize。ユーザーの「Covring」をCoveringとして評価した。実装変更は行わず、コード読解と隔離コピーでの再現試験を実施した。

評価の結論

キュー処理と永続化の基盤は堅い一方、知識の採否を保証する境界には改善が必要である。元資料を見ない負の知識の評価、不明な採否の採用への変換、LLMによる所属プロジェクトの上書き、文字の類似度だけによる棄却、一時障害による候補の終了を優先して直したい。モデルの変更や閾値調整だけでは解消しない。

既存のCoveringテスト21件は成功した。隔離コピーに観測用テスト8件を追加し、合計29件が成功した。追加テストの成功は問題挙動の再現を意味し、望ましい仕様への適合を意味しない。本番データでの誤採用率、誤棄却率、発生頻度は未計測であり、ここでは断定しない。

現在の処理

  1. claim済み候補、元資料、project identity、active/draft知識の重複候補を読み込む。
  2. polarity == negativeなら負の知識用LLMへ送る。それ以外は元資料の取得、短すぎる候補の排除、重複判定、identity確認を行う。
  3. 正の知識は語句によって外部検索の要否を分岐し、LLMで根拠と価値を評価する。重要度、適用カテゴリ、identity、手順形式を確認・補完する。
  4. Evidence保存、Finalize enqueue、Covering状態遷移、lease解放、イベント記録を同一transactionで確定する。
  5. Finalizeは重要度・形式・適用カテゴリ・identity・embeddingを確認し、repo scopeのdraft知識を保存する。主張と根拠の再照合は行わない。

優先順位

P1は誤採用、誤帰属、有効候補の棄却に直結するため先行修正を推奨する。P2は検索品質、証拠の再現性、再処理の回復性を改善する。優先順位は到達可能な不正状態と影響に基づき、発生頻度を表すものではない。

根拠と改善の受入条件

F1: 負の知識が元資料を検証していない

provider.rs:16の request_negative_evidence はcandidateのtitle/contentだけを送信する。読み込まれたsource_contentやdiffは渡されない。negative_response.rs:130以降では、LLMが出したevidence文字列の異なり数を数え、regression / security_risk / data_integrity のタグがあると根拠件数による棄却を免除する。

再現試験ではsource_contentを空にし、架空のfailure/trigger/fix、data_integrityタグ、evidence空配列を返した。結果はconfidence 74のknowledge_readyで、参照0件のままFinalizeが1件作られた。さらに同じ試験でduplicate_statusを指定しても負の経路では参照されず、duplicate_refsも失われた。これはLLMが常に捏造するという主張ではなく、不正な応答を受理する境界の確認である。

改善: 元資料の抜粋・位置・資料識別子を渡し、主張ごとの支持／矛盾／不明を返させる。evidenceには元資料に存在する引用または照合可能な位置を要求する。高リスクタグは優先度やレビューの強さを上げる用途に限定する。独立した根拠数と同じ事象の言い換え数を区別する。負の経路にも最終本文を対象とした重複確認を適用する。

受入条件: 根拠0件、元資料に存在しない引用、同一事象の言い換え、元資料と矛盾するfixを採用しない。高リスクでも同じ最低条件を満たす。

F2: 未知statusが採用へ変換される

positive_response.rs:105のparserは許可されないstatusを捨て、title/body/contentが存在するとknowledge_readyを推定する。{"status":"rejected","title":"Rejected candidate"}、false_positive、not_reusableの3例で採用への変換を再現した。bodyやスコア、適用カテゴリは入力候補から補完される。またstatusだけがknowledge_readyの応答でも候補全体を引き継げる。

改善: statusの欠落と不正値を区別し、不正値をparse_failedにする。schemaVersionとstatusごとの必須項目を検証する。旧ラベル形式の互換処理を残す場合でも、その互換処理から根拠のない採用を作らない。confidenceを単に補完するより、判定理由と支持する参照を必須にする。

受入条件: 不明status、欠落status、誤った型、statusだけの採用応答で意図せずknowledge_readyにならない。明示的なinsufficientは候補本文が付いていても棄却を維持する。

F3: LLMが信頼済みidentityを上書きできる

source.rsで元情報からidentityを組み立てても、正の知識の parse_positive_candidate はdefaultのappliesToとLLM応答を merge_applicability に渡し、後から来るrepoPath等を優先する。再現試験では /work/project-a が /work/project-b に置換された。元のprojectIdentityを再適用する負の経路とは条件が異なる。

FinalizeはappliesToのidentityを解決してrepo scopeで保存するため、誤ったrepoPathだけが指定されていれば別プロジェクトへの帰属につながり得る。複数identityが矛盾した場合は後続でエラーになる可能性もあるが、元情報との一致を保証する処理にはなっていない。

改善: projectRef/repoPath/repoKeyは実行側が確定し、LLMが編集できるフィールドから除く。カテゴリ補完でも同じルールを使う。受入条件: LLMが別identityを返しても信頼済みの所属が維持されるか、明示的な不整合として停止する。

F4: 文字の近さが意味の同一性として扱われる

deduplication.rs:57以降はbigramの一致からスコアを計算し、0.93以上をduplicate、0.82以上をnear_duplicateにする。execution.rs:228以降でどちらもLLMの確認前に終了する。共通本文に続く Do run the migration automatically. と Do not run the migration automatically. は0.994でduplicateになった。

SQLと関数引数にはscope、project identity、polarity、適用カテゴリの比較もない。同文であっても別repoにだけ存在する知識を理由に候補を捨てる可能性がある。近似候補をMerge Reviewへ送る処理は、このRust Coveringのpersist経路にはない。

改善: 同一scopeと適用条件での完全一致だけを自動終了の基本にする。近似一致はduplicate、complement、contradiction、unrelatedに分けて確認し、数値・否定・版・前提の差分を保護する。受入条件: 肯定／否定、上限値、対応バージョン、対象repoが異なる候補を単なるduplicateとして捨てない。

F5: 補完中の一時障害が内容不足になる

execution.rs:393以降はapplicability refinementのエラーをイベントに保存して処理を続け、カテゴリが埋まらなければinsufficientにする。providerへの接続失敗を起こした試験で、reasonはapplies_to_categories_requiredとなり、永続化結果はCompletedになった。persistence.rsが再試行するのはprovider_failed、parse_failed、tool_failed、reprocess_requestedだけである。

procedure repairでも通信・parse失敗と根拠不足が同じエラー経路に入り、ruleへの降格またはinsufficientへ進むことをコードで確認した。この追加経路の失敗注入試験は今回実施していない。

改善: 補完結果を成功、内容不足、一時的失敗、不正応答に分ける。通信や不正応答で型を降格させず、適切なretry状態を返す。受入条件: 一時的な接続障害後に再試行でき、復旧後に元の候補を評価できる。

F6: 重複候補の取得と正規化が一致していない

deduplication.rs:26以降のSQLはraw title/bodyのlower一致、または先頭48／64文字の包含で最大40件を取る。後段で空白を正規化しても、前段で外れた候補は戻らない。全空白を3個に増やした既存知識は、正規化後にタイトル・本文とも完全一致するのに検索結果0件となった。更新日時順の40件上限も、類似度を計算する前に候補を落とす。

TypeScript版はlexical検索とsemantic検索を併用する一方、現行Rustのこの関数には意味検索がない。したがって旧実装の検索能力を現行実装の説明として使うべきではない。さらに重複判定は清書・repair前の候補に対して行い、最終生成本文では再確認していない。

改善: 正規化hashの完全一致検索、scopeを絞ったFTS・意味検索、最終本文の再確認を分ける。受入条件: 空白・改行の差による完全一致の取りこぼしをなくし、言い換え候補の再現率を別に測定する。

F7: 読んだ根拠とLLMに提示した根拠が異なる

positive_response.rs:99は元資料を先頭1,000文字に切り詰める。外部評価も external_evidence.rs でsourceを1,000文字にする。一方、source_referenceはそれより大きな読み取り範囲を支持根拠として記録する。試験ではtokens:0-1201の末尾に置いた根拠がsource_contentにはあるが、評価プロンプトには残らなかった。

初期の文字重なり判定が不支持でもログを残してLLMへ進む設計自体は、言い換えを許容する点で合理的である。ただし最終受理時に主張単位の根拠が必須でないため、切り詰められた支持根拠・反証をLLMが確認できない問題を補えない。

改善: 候補に関連する複数箇所と反証を予算内で選ぶ。実際に送った抜粋の位置・hash・切り詰め有無を記録する。受入条件: 先頭外の根拠に基づく評価ができ、保存した参照からモデルが見た内容を再現できる。

F8: 再Coveringが失敗済みFinalizeを再開しない

persistence.rsはcandidateごとのEvidenceを上書きするが、Finalize enqueueは同じevidence_result_idの行が存在すれば何もしない。試験では一度knowledge_readyを保存し、Finalizeをfailedにした後、再Coveringをknowledge_readyとして保存してもFinalizeはfailedのままだった。

通常の一回処理における重複防止としては正しい。問題は再処理によって根拠や本文が更新された場合の回復条件が、この関数内では定義されていないことである。運用入口がFinalizeも別途resetすれば回避できるため、すべての再処理操作が失敗するとは断定しない。

改善: Evidenceに改訂番号を持たせ、既存Finalizeがfailed/skipped/completed/runningの場合の扱いを分ける。処理中のものを無条件resetしない。受入条件: 根拠を修正して再評価した候補が、古いfailed状態に阻まれずにFinalizeへ進める。

維持したい点

  • Evidence保存とenqueue、状態遷移、lease解放が一つのtransactionにまとまっている。成功扱いだけが先行する構造になっていない。
  • queueとleaseのownershipを検証して古い実行結果をdiscardする。既存の再claim試験が成功した。
  • 基本経路のprovider/parse失敗には最大試行回数とbackoffがある。F5ではこの既存機構へ正しく接続すればよい。
  • ローカルファイルのroot制限、外部URLのprivate network遮断、redirect検査、取得量制限があり、該当する既存テストが成功した。
  • 外部資料を未信頼データとして渡す指示がある。取得の安全性と、主張を支える根拠の品質は別々に評価すべきである。

次の品質評価で測りたいこと

まずP1の境界を修正し、その後で匿名化した正解付き候補を使い、モデル・閾値・検索戦略を比較する。今回の8件の観測テストは、修正時に望ましい結果を期待する回帰テストへ書き換える。

  • 採用精度: knowledge_readyの主張が実際の資料で支持される割合。高リスク・負の知識を別集計する。
  • 取りこぼし: 有効な候補がinsufficient、duplicate、near_duplicateで終了した割合。
  • 重複・矛盾: 同義、補足、矛盾、無関係を分け、否定・数値・版・repo差分を含む評価セットで測る。
  • 運用品質: 一時障害からの回復率、Finalizeまでの到達率、再試行回数、LLM呼び出し数、処理時間。
  • 根拠の追跡性: 採用した主張に対応する実在の抜粋と位置を再確認できる割合。

追加の設計課題として、外部取得に成功した全URLへ自動でexternal_verificationを付ける処理は、単なる取得と主張の支持を区別したい。importance/confidenceも語句や項目数、LLM自己申告に依存するため、校正前に確率として解釈しない。またMarkdown正規化で改行・手順の箇条書きが失われる点は、procedure repairの根拠抽出と合わせて再評価したい。これらの実データ上の影響は今回未計測である。
