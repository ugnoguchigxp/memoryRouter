SQLite単一writer・外部I/O分離 実装計画

Status

Status: implemented and initial live rollout completed.

Created: 2026-08-29

Plan ID: sqlite-single-writer-external-io-isolation-v1

対象: Rust residentが所有するfindingCandidate、episodeDistiller、 context_compileのwriter待機時間と外部provider実行境界。

本計画はSQLiteへの書込みを複数化しない。resident内の単一writerを唯一のread-write所有者として維持し、 複数のquery-only readerを組み合わせる。Findingの外部I/O workerはDB接続を持たず、Episodeは query-only connectionを利用できるがprovider待機をまたぐread transactionは保持しない。

context_compileのread／compose／persist分離、snapshot、telemetry、rollout modeは ContextStill Utility-RAG Foundation Implementation Plan を権威とする。本計画はその契約を変更せず、queue実行面への安全な展開とlive導入順を定義する。

1. Executive Decision

採用する実行境界を次に固定する。

query-only reader: immutable execution inputを取得
single writer:      claimとprovider leaseを短いtransactionで確定
external phase:     FindingはDB-free、Episodeはautocommit query-onlyでLLMを実行
single writer:      fencing確認後に結果またはsegment checkpointをtransactionでpersist

変更対象はwriterの個数ではなく、writerへ投入するjobの責務である。writer jobからnetwork request、process wait、sleep、thread joinを除外し、SQLite mutationだけを残す。

実装順は次のとおりとする。

  1. 現行挙動を固定するfailure testとwriter phase telemetryを追加する。
  2. findingCandidateをclaim／read／execute／persistへ分割する。
  3. provider unavailableの二重接続待ちとhot retryを止める。
  4. findingCandidateをcanary後にsplit modeへ昇格する。
  5. episodeDistillerへ同じ境界を展開する。
  6. context_compileは既存split_legacy_rankをcanary導入し、ranking変更を同時に行わない。
  7. 観測期間とstop conditionを通過後に、split modeを既定化する。

3. Current Problem And Baseline

3.1 Observed failure

  • queue.executor_tickが単一writer上でfindingCandidateの外部LLM接続を実行する。
  • 到達不能なlocal LLM targetで、Rust HTTP clientの接続待ち後にmacOS curl fallbackが追加で待つ。
  • 失敗ジョブが短い間隔で再claimされ、writerが連続して長時間占有される。
  • context_compileと軽量なcompile_evalも同じwriter queueで待つ。
  • legacy compileのduration_msはwriter取得後から計測され、callerが見たqueue waitを含まない。

3.2 Investigation baseline

Recorded compile duration approximately 13–17 seconds in reproduced calls legacy timing starts after writer acquisition

4. Goals And Non-goals

4.1 Goals

  • SQLiteへの全mutationをresident単一writerへ直列化したまま維持する。
  • 複数のquery-only readerがwriterと独立して一貫snapshotを取得できるようにする。
  • 外部LLM、HTTP、curl、process waitをwriter jobから除外する。
  • stale workerの結果が現在のqueue stateへ書き込まれないようfencingする。
  • claim、heartbeat、persist、lease releaseをcrash-safeかつidempotentにする。
  • provider outageがwriter starvationや毎分hot retryを発生させないようにする。
  • writer queue waitとwriter workを分け、caller-observed latencyとの差を説明可能にする。
  • surfaceごとにcanary、stop、rollbackできるようにする。

4.2 Non-goals

  • 複数writer、複数read-write connection、別processからのSQLite mutation。
  • SQLiteからPostgreSQLなど別databaseへの移行。
  • queue priority、provider pool構成、model quality、prompt内容の同時変更。
  • Foundation rankingの昇格とcompile split activationの同時実施。
  • 新しいdurable workflow engineや別queue storeの導入。
  • 既存backlogの自動削除、成功扱い、attempt countの無断reset。
  • UI-only progress stateやmemory-only provider healthをsource of truthにすること。
  • この計画だけを根拠にしたresident restart、live flag変更、live queue mutation。

5. Fixed Safety Invariants

次のinvariantはrollout modeにかかわらず破ってはいけない。

  1. SQLite core databaseをread-writeで開きmutationを実行できる所有者はresident単一writerだけである。
  2. readerはread-only open flagとPRAGMA query_only = ONを使い、schema変更を含むwriteを拒否する。
  3. live WAL databaseのreaderにimmutable=1を使わない。readerはWALを含む現在の一貫snapshotを読む。
  4. Findingのexternal execute関数はrusqlite::Connectionを引数、field、globalとして保持しない。 Episodeがquery-only connectionを利用する場合もprovider待機をまたぐread transactionを保持しない。
  5. writer jobはnetwork request、subprocess wait、sleep、blocking receive、thread joinを実行しない。
  6. claimとprovider lease作成は同じwriter transactionでcommitする。
  7. persistはqueue ownershipとactive provider leaseの両方を確認してからbusiness rowを変更する。
  8. ownership不一致の結果はSupersededとして破棄し、現在のqueue jobを変更しない。
  9. Findingのbusiness result、queue terminal state、queue event、lease releaseは1 transactionでcommitする。 Episodeは各segmentのdedupe済みresultとprogressを短いwriter transactionでcheckpointし、最終queue state、queue event、lease releaseを1 transactionでcommitする。
  10. persist retryは同じstable result keyを使い、downstream rowを重複作成しない。
  11. reader snapshotから現在のsource entity本文を上書きしない。
  12. heartbeat失敗をjob成功として扱わない。ownership喪失後の外部結果は必ず破棄する。
  13. provider unavailableはsemantic success、no-candidate、business failureと混同しない。
  14. split pathが失敗した場合、未persistの結果をcallerへ成功として返さない。

6. Target Runtime Architecture

6.1 Queue sequence

Scheduler
  -> Single Writer: claim pending job + create active provider lease
  <- ClaimedExecution identity
  -> Query-only Reader: load source/settings rows without mutation
  <- PreparedExecution with versions and hashes
  -> External Phase: call provider; never hold a read transaction while waiting
  -> Single Writer heartbeat jobs: short fenced updates only
  <- ExecutionResult
  -> Single Writer: verify fencing + persist result + release lease in one transaction
  <- Completed | Retrying | Failed | Superseded

claimを先に確定するため、同じjobを別workerが同時にprepareしない。reader phaseはclaim ownershipのもとで実行する。Findingはsourceとsettingsをowned valueへコピーしてreaderを閉じる。 Episodeはsegment間でquery-only readを行えるが、各statementをautocommitで完了してからproviderを呼ぶ。

6.2 Compile sequence

MCP request
  -> Query-only Reader: identity, candidates, settings, content versions
  <- PreparedCompile; close reader
  -> External Composer: planner + composer calls without DB connection
  <- ComposeResult
  -> Single Writer: one atomic persist job
  <- success only after commit
  -> MCP response

compileはqueue jobではないためclaim leaseを作らない。read snapshotをrun ledgerへ保存し、persist時に現在のKnowledge本文を 古いsnapshotで更新しない。既存split_legacy_rankの契約をそのまま利用する。

6.3 Process and connection ownership

Table: 6.3 Process And Connection Ownership
Component Connection Permitted work Forbidden work
Resident single writer the only read-write connection claim, heartbeat, state transition, atomic persistence, lease mutation network, provider inference, subprocess wait, sleep
Query-only reader one of multiple read-only connections consistent read and mapping to owned values; Episode segment間のautocommit read all mutation and schema operations
External phase Findingはnone、Episodeはquery-only connectionのみ HTTP, LLM inference, parsing, pure transformation direct mutation、read transactionを保持したprovider待機、durable state transition
Heartbeat guard writer handle only; no direct connection enqueue short fenced heartbeat jobs business result persistence

7. Queue Execution Contracts

7.1 Owned execution snapshot

findingCandidateとepisodeDistillerはsurfaceごとのowned execution typeを持つ。型名は実装時に次へ固定する。 

struct FindingExecution {
    job_id: String,
    worker_id: String,
    provider_lease: ProviderLeaseAssignment,
    attempt_count: i64,
    source: FindingSourceSnapshot,
    source_version: String,
    settings_revision: Option<String>,
    claimed_at: String,
}

struct EpisodeExecution {
    job_id: String,
    worker_id: String,
    provider_lease: ProviderLeaseAssignment,
    attempt_count: i64,
    max_attempts: i64,
    source: EpisodeSourceSnapshot,
    source_version: String,
    settings_revision: Option<String>,
    claimed_at: String,
}

API keyなどsecretはtelemetryやqueue metadataへ保存しない。workerへ渡すsecretはprocess memoryだけに存在し、 execution snapshotのDebug出力対象から除外する。

7.2 Claim contract

claim writer transactionは次をatomicに行う。

  1. queue priority、pause、next_run_at、provider cooldownを再確認する。
  2. 対象jobをpendingからrunningへ条件付き更新する。
  3. claimごとに一意なworker_idとprovider lease IDを生成する。
  4. active provider leaseをinsertする。
  5. locked_atとheartbeat_atを同じtimestampで設定する。
  6. claim eventをappendする。
  7. commit後にだけclaim結果をworkerへ返す。

claim transaction内でprovider request、source本文の大規模変換、prompt buildを行わない。

7.3 Reader snapshot contract

  • claim後にquery-only connectionを開き、必要なrowをmutationなしで取得する。
  • readerはjob ownershipを参照してよいが、ownershipを変更しない。
  • source key、source updated timestamp、content hashをsnapshotへ含める。
  • provider target、model、route、timeoutのeffective valueをsnapshotへ含める。
  • reader errorまたはsource missingは外部LLMを呼ばず、fenced writer jobでretry／skipへ遷移する。
  • Findingはreader connectionをprovider call開始前にdropする。Episodeはconnectionを再利用してよいが、 provider call開始前に実行中のread transactionを必ず終了する。

7.4 External execute contract

  • Finding execute関数のsignatureからConnectionを除去する。
  • Finding execute関数はowned snapshotだけを入力とし、結果をowned resultとして返す。
  • Episodeの外部phaseが参照できるconnectionはquery-onlyに限定し、mutation APIをwriter jobへ分離する。
  • HTTP status、connect failure、timeout、parse failureをtyped outcomeへ分類する。
  • 外部処理中のdurable progress更新はheartbeat guardにだけ依頼する。
  • panicはcatchし、tool_failed結果としてfenced persistへ渡す。

7.5 Heartbeat contract

heartbeatは20秒間隔を初期値とし、同じwriterへ短いjobとして投入する。次の条件を全て満たすrowだけを更新する。 

queue_job.id = expected_job_id
AND queue_job.status = 'running'
AND queue_job.locked_by = expected_worker_id
AND provider_lease.id = expected_lease_id
AND provider_lease.status = 'active'
AND provider_lease.worker_id = expected_worker_id

heartbeat更新件数が0の場合はownership喪失とし、guardへcancel signalを設定する。provider requestを即時中断できない場合でも、 最終結果はpersist時に必ずSupersededとなる。

7.6 Fenced persist contract

persist writer transactionはbusiness mutation前に次のownership queryを実行する。

SELECT EXISTS (
  SELECT 1
  FROM queue_table queue_job
  JOIN llm_provider_leases lease
    ON lease.id = :lease_id
   AND lease.queue_name = :queue_name
   AND lease.queue_job_id = queue_job.id
   AND lease.worker_id = :worker_id
  WHERE queue_job.id = :job_id
    AND queue_job.status = 'running'
    AND queue_job.locked_by = :worker_id
    AND lease.status = 'active'
)

偽の場合は次だけを行う。

  • stable IDのdiscard eventが未記録ならappendする。
  • 現在のqueue row、active lease、business rowを変更しない。
  • Supersededを返す。

真の場合は1 transaction内で次を行う。

  1. source versionがstrict-currentを要求するsurfaceではversionを再確認する。
  2. stable result IDまたは既存unique keyでbusiness rowをinsert／upsertする。
  3. queue jobをcompleted、retrying、failed、pausedのいずれかへ遷移する。
  4. claim fieldとheartbeatをclearする。
  5. 結果eventをappendする。
  6. provider leaseをreleaseし、release reasonを保存する。
  7. commitする。

7.7 Idempotency contract

  • result IDはjob ID、source version、producer versionからdeterministicに生成する。
  • persist responseが失われて再実行されても、同じbusiness rowを重複生成しない。
  • queue event IDもjob ID、lease ID、event typeからstableに生成する。
  • completed jobはclaim predicateから除外する。
  • 同じleaseに対するpersistの2回目はno-opまたは同じterminal statusを返す。

8. Provider Failure And Retry Policy

8.1 Timeout separation

  • connect timeoutとrequest／inference timeoutを分離する。
  • connect timeoutの初期値を5秒とする。
  • inference timeoutは既存runtime設定を維持し、writer占有時間とは無関係にする。
  • macOS curl fallbackはconnect refused、host unreachable、route unavailableでは実行しない。
  • curl fallbackを残す場合は明示的なtransport compatibility errorだけを対象とし、 --connect-timeoutと--max-timeの両方を指定する。

8.2 Job backoff

Rust側provider unavailable backoffを既存TypeScript contractへ合わせる。

Table: 8.2 Provider Unavailable Backoff
Failure count before update Next delay
0 60 seconds
1 120 seconds
2 300 seconds
3 600 seconds
4 1,200 seconds
5 or more 3,600 seconds

findingCandidateはprovider unavailableが8回連続した時点で既存pausedへ移し、 last_outcome_kind=provider_unavailable_exhaustedを保存する。jobは削除もfailed成功扱いもしない。 再開はoperatorの明示操作とし、この閾値はv1では固定contractとする。

8.3 Target cooldown

  • release_reason=provider_unavailable_retryのrecent leaseを既存cooldown signalとして使う。
  • cooldown中のtargetを新しいclaimで選ばない。
  • 同一poolにavailable targetがあればfailoverする。
  • 全targetがcooldown中ならjobをclaimせず、writerを即時解放する。
  • 同じ秒の後続successがある場合はcooldownを解除する既存契約を維持する。

8.4 Existing backlog

既に高attempt countとなったjobをmigrationで自動変更しない。split rollout後の次回provider unavailable結果をfenced persistし、既定のmax attempts以上ならpausedへ安全に遷移する。 削除、attempt reset、completed化は禁止する。

9. Context Compile Plan

9.1 Use existing split pipeline

native_compile.rsの既存context_compile_split、 prepare_split_compile、persist_split_compileを利用する。新しいcompile pipelineを追加しない。

  • prepareはquery-only readerを使う。
  • plannerとcomposerはreaderとwriterのどちらも保持しない。
  • persistはexecute_for_path_observedを通す。
  • run、items、traces、usage、feedback、countersを1 transactionで保存する。
  • persist失敗時はMCP success responseを返さない。

9.2 Rollout mode

  1. 現行legacyの固定fixtureとcaller-observed baselineを採る。
  2. split_legacy_rankで同じrequest contractとselected IDsを検証する。
  3. blocked composer中にunrelated writer sentinelが完了することを検証する。
  4. canary sessionだけをsplit_legacy_rankで実行する。
  5. 24時間のavailability、writer wait、output parityを観測する。
  6. stop conditionがなければ既定をsplit_legacy_rankへ変更する。

このrolloutでsplit_shadow_rankまたはfoundationへ昇格してはいけない。 performance boundary変更とranking変更を別restart・別evidenceにする。

9.3 Snapshot consistency

  • candidate body、source refs、updated timestamp、content versionをowned snapshotへ含める。
  • providerへ渡したcandidateとpack snapshotのcandidateを同一にする。
  • read後にKnowledgeが変更されても、古いsnapshotから現在のKnowledge本文を更新しない。
  • counter更新対象が消失した場合はmissing IDをdiagnosticsへ保存する。
  • historical run replayは現在のKnowledgeではなくrun snapshotを読む。

10. Observability Contract

10.1 Phase timings

queueとcompileの両方で次を分離して記録する。

  • readerWorkUs
  • claimQueueWaitUs
  • claimWriterWorkUs
  • externalIoUs
  • persistQueueWaitUs
  • persistWriterWorkUs
  • endToEndUs
  • heartbeatCountとheartbeatFailureCount

queueはterminal event metadataへbounded timing summaryを保存する。compileは既存Foundation run snapshotとappend-only telemetryを使う。 prompt、response本文、secret、absolute database pathをtelemetryへ保存しない。

10.2 Runtime health

  • writer statusはactiveOperation、queueDepth、commit countを継続表示する。
  • 外部LLM実行中にactiveOperation=queue.executor_tickが継続しないことを確認する。
  • provider cooldown target数とprovider unavailable pause数をqueue inspectへ追加する。
  • queue detailはpersisted rowとeventをsource of truthとする。

12. Delivery Units

P0: Baseline And Regression Harness

Behavior changeは行わない。

  • blocked provider harnessを追加する。
  • providerを30秒block中にwriter sentinelを投入するtestを追加する。
  • caller wall timeとrun duration_msをpaired記録する。
  • writer queue wait、writer work、external waitのbaselineを保存する。
  • read-only connectionがwriteを拒否するcontract testを追加する。

Exit: current failureが再現され、testが旧実装で失敗理由を明確に示す。

P1: Finding Pure Boundaries

  • FindingExecutionとFindingExecutionResultを追加する。
  • source readとprompt input buildをprepare helperへ分離する。
  • HTTP／parse処理をConnection-free execute helperへ分離する。
  • 現行persist処理をtransaction helperへ分離する。
  • fixtureで旧出力とのcandidate parityを確認する。

Exit: pure execute APIがSQLite型を参照せず、既存focused testsが通る。

P2: Finding Split Orchestration

  • writer claim、query-only prepare、external execute、writer persistを配線する。
  • coveringと同じheartbeat guard、ownership query、Superseded statusを導入する。
  • CONTEXT_STILL_RUST_FINDING_EXECUTION_MODE=legacy|splitを追加し、初期defaultは legacyとする。
  • split modeだけに新orchestrationを適用し、同一jobのLLM callを複製しない。

Exit: blocked provider中のwriter sentinelがgateを満たし、fencing／crash testsが通る。

P3: Provider Failure Control

  • connect timeoutを5秒へ分離する。
  • availability error時のcurl二重待ちを止める。
  • Rust finding backoffを60／120／300／600／1,200／3,600秒へ統一する。
  • 8回連続provider unavailableでjobをpausedにする。
  • 全target cooldown時はclaimしない。

Exit: 到達不能targetでhot loopがなく、writer workはnetwork timeoutを含まない。

P4: Episode Split Orchestration

  • P1／P2の境界をepisodeへ展開する。
  • 既存max_attempts、retry-after、dedupe、source fragment契約を維持する。
  • CONTEXT_STILL_RUST_EPISODE_EXECUTION_MODE=legacy|splitを追加し、別canaryにする。
  • findingとepisodeは独立flagを維持し、一方だけを即時rollbackできるようにする。

Exit: episode focused tests、provider unavailable tests、fencing testsが通る。

P5: Compile Split Activation

  • Foundation manifestとfixed fixtureでsplit_legacy_rankを再検証する。
  • legacyとsplitのselected IDs、output contract、persistence rowを比較する。
  • blocked composer concurrency testをpassさせる。
  • 明示canary、24時間観測、promotion decisionをevidenceへ保存する。

Exit: rankingを変えずにsplit boundaryだけを既定化できるevidenceが揃う。

P6: Closeout

  • public configurationとoperationsを更新する。
  • legacy rollbackの保持期間を1 release以上とする。
  • live canary evidence、stop decision、final modeを記録する。
  • 後続計画が本計画を置換した時点で本書をarchiveする。

Data integrity zero integrity, foreign-key, duplicate-producer, and fencing violations temp DB checks and failure-injection assertions

external LLM latencyそのものは本計画の短縮保証対象ではない。保証するのは、external latencyがwriter occupancyと unrelated request latencyへ伝播しないことである。

15. Rollout And Rollback

15.1 Pre-rollout

  1. git status、binary build ID、effective database fingerprint、runtime settings revisionを保存する。
  2. writer status、queue backlog、provider cooldown、失敗jobを記録する。
  3. 失敗を繰り返すlive finding jobはoperator判断でpauseする。
  4. backup preflightを実行する。backup作成はlive rolloutの明示承認がある場合だけ行う。
  5. focused tests、smoke、deterministic blocked-provider gateを通す。

15.2 Promotion order

  1. offline fixture and failure injection only。
  2. 全target unit testとblocked-provider failure injection。
  3. LaunchAgentにfinding／episodeの独立split flagを設定する。
  4. compileをranking不変のsplit_legacy_rankへ設定する。
  5. 1回のresident restartでbinaryと3つの実行境界を反映し、process重複時間を作らない。
  6. restart直後にwriter ownership、queue fencing、MCP compile、provider backoffを確認する。
  7. 後続観測でstop conditionを検出したsurfaceだけをlegacyへ戻す。
  8. Foundation rankingの後続判断は別作業で行う。

15.3 Stop conditions

次のいずれかでrolloutを停止する。

  • 2つ以上のread-write ownerまたはdirect worker mutationが観測された。
  • ownershipを失ったworkerの結果がpersistされた。
  • queue terminal state、business row、provider leaseがtransaction外で不整合になった。
  • duplicate business result、duplicate producer、counter二重加算が発生した。
  • readerからwriteが成功した。
  • external provider待ちがwriter workへ含まれた。
  • blocked-provider sentinel gateまたはwriter queue gateを超えた。
  • compile selected IDs、repository isolation、public MCP output contractが回帰した。
  • integrity checkまたはforeign-key checkが失敗した。

15.4 Rollback

  • 対象surfaceだけをlegacy modeへ戻し、他surfaceのmodeを同時に変更しない。
  • provider outage中にlegacyへ戻す必要がある場合は、先に対象queueをpauseする。
  • compileはCONTEXT_STILL_COMPILE_FOUNDATION_MODE=legacyへ戻す。
  • schema migrationがないためDB down migrationは行わない。
  • split modeで保存済みのterminal rows、events、run snapshots、leasesを削除しない。
  • Superseded eventとtiming telemetryはrollback後も監査証跡として保持する。
  • rollback原因と再開条件をevidenceへ記録する。

16. Commit And Review Plan

commitは次の責務単位に分ける。複数unitを1 commitへまとめない。

  1. test: capture writer starvation baseline
  2. refactor: split finding preparation execution and persistence
  3. feat: orchestrate fenced finding execution outside writer
  4. fix: bound provider unavailable retries and connect fallback
  5. refactor: split episode execution outside writer
  6. test: prove crash fencing and idempotent persistence
  7. ops: canary split legacy compile boundary
  8. docs: record single writer isolation rollout evidence

各reviewでは次を確認する。

  • 外部I/O call graphからwriter closureへ戻る経路がない。
  • execute型がConnectionまたはmutable repositoryを保持しない。
  • 全persist pathにownership queryがある。
  • 全terminal pathでlease releaseとqueue stateが同一transactionにある。
  • provider unavailableとbusiness failureが別outcomeである。
  • testが実際にblock、crash、stale result、rollbackを注入している。
  • 現在のuncommitted user changesを上書きしていない。

17.1 Post-implementation review

初回rollout後のコードレビューで、次の追加修正とfailure testを完了した。

  • provider claim確定後にheartbeat threadまたはquery-only readerの初期化が失敗しても、queue jobをpendingへ戻し、active leaseを解放するようにした。この2更新は所有権条件付きの同一 transactionで行い、lease fenceが失われている場合はqueue更新もrollbackする。
  • provider target設定はclaim前に検証し、設定不備によってrunning jobとactive leaseを残さないようにした。
  • heartbeat guardの停止を250 ms pollingからcondition variableの即時通知へ変更した。実writerを使う testでqueueとleaseのheartbeat更新、および60秒interval中でも1秒未満で停止することを確認した。
