Implementation progress

  • Phase 1は実装済み。後方互換なroute union、LARM connection設定、API validation、管理UIのconnection編集とroute選択、queue表示を追加した。
  • Phase 2は実装済み。Rust resident向けcontrol client、strict claim validation、credential redaction、connection manager state machine、busy／unknown時の fail-closed backoffを追加した。
  • Phase 3とPhase 4は実装済み。Rust residentは実行可能jobの存在をclaim前に確認し、connection単位で managerを再利用しながら、findingCandidateとepisodeDistillerを動的targetへ接続する。 job境界ではavailabilityを再評価し、queueが空ならconnectionを解放する。
  • Phase 0のLARM availability endpointとcontextstill-background Profileは外部実装待ち。 live activationを行わず、 providers.larm-agent-connection.enabledのdefaultをfalseに維持する。
  • 現時点のTypeScript実行経路は動的routeを実行せず明示的にfail closedとする。credentialとclaim payloadはsettings、SQLite、diagnosticへ保存しない。
  • コードレビューで、HTTP 201／202 create、availabilityの鮮度、boot epoch／catalog revision、connection lifecycle identity、claim expiry、URLとresponseの上限を追加検証した。短期tokenは redactedかつzeroize対象とし、release失敗時も不確実なlocal claimを再利用しない。
  • 旧TypeScript schedulerは、LARM routeだけでなくLARM targetを含むmixed poolもpool全体をfail closedとする。static targetだけを抜き出して暗黙実行する挙動は禁止する。findCandidateのsource／vibeが static／LARMに分かれる場合も、rowのrouteをclaim前に判定し、動的rowのattemptを消費しない。

1. Executive decision

ContextStillのRust residentが、実行可能なbackground queue jobが存在するときだけLARMを ポーリングする。LARMが利用可能と返した場合にAgent Connectionを確保し、claimで得た OpenAI互換providerを使ってjobを1件ずつ実行する。利用不能時はjobをclaimせず待機する。

実装判断を次に固定する。

  • SAAAとの通信、通知購読、activity推測を実装しない。
  • 動的provider lifecycleのownerはRust residentだけとする。
  • availability GETは事前ゲート、Agent Connection POSTは原子的な最終admissionとする。
  • Agent ConnectionがreadyになるまでSQLite queue jobをclaimしない。
  • connection token、動的base URL、claim payloadをSQLiteへ永続化しない。
  • connectionがある間も次のjobを開始する前にavailabilityを再評価する。
  • job実行中にforeground activityが始まった場合は、そのjobを完了または通常失敗まで進め、 次jobを開始せずconnectionを解放する。
  • static provider routeは既存挙動を完全に維持し、明示設定したrouteだけを動的化する。

2. Scope

2.1 In scope

  • runtime settingsの後方互換な動的connection設定。
  • Rust resident内のavailability poll、create、status、claim、renew、delete。
  • provider poolが動的targetを選択できるための型とscheduler統合。
  • findingCandidate、episodeDistiller、 coveringEvidenceの段階的rollout。
  • queue ownership、provider lease、fencing、retry、telemetryとの統合。
  • settings UI/APIでの設定表示、validation、保存。

2.2 Out of scope

  • agenticCompile、context_compile、embedding、searchの動的化。
  • TypeScript CLIやUI processによるAgent Connection lifecycle所有。
  • SAAA callback、SAAA API poll、SAAA process監視。
  • generation途中のpreemption、cancel、checkpoint resume。
  • 動的provider credentialのDB保存。
  • static fallbackへの黙示的切替。

3. Authority and precedence

Table: Authority
Concern Authority

queue job stateと再試行時刻 ContextStill SQLite queue row

矛盾時は次の順で優先する。

  1. SQLite単一writer、短いtransaction、ownership fencing。
  2. LARMのatomic admissionとcredential lifetime。
  3. foreground activityを優先するjob境界gate。
  4. 既存settingsとstatic providerの互換性。
  5. workerのwarm再利用とthroughput。

4. Target architecture

        |
        v

        |  GET profile availability
        |  POST connection -> poll -> claim

        |
        v

この境界は SQLite単一writer・外部I/O分離 実装計画を変更しない。availability、connection create、status poll、claim、renew、delete、 LLM requestのすべてをwriter transaction外で行う。

5. Runtime settings contract

5.1 Connection catalog

providersへ、static local modelとは別のcontrol-plane設定を追加する。 field名とdefaultを次で固定する。 

{
  "providers": {
    "larm-agent-connection": {
      "enabled": false,
      "connections": [
        {
          "id": "contextstill-background",
          "controlBaseUrl": "http://192.168.0.130:9810",
          "agentProfile": "contextstill-background",
          "audience": "saaa-desktop",
          "availabilityPollMs": 5000,
          "availabilityTimeoutMs": 2000,
          "controlTimeoutMs": 5000,
          "readyTimeoutMs": 180000,
          "ttlSeconds": 900,
          "requestTimeoutMs": 300000
        }
      ]
    }
  }
}
  • idはsettings内で一意かつ非空とする。
  • controlBaseUrlはcredential、query、fragmentを禁止する。
  • agentProfileとaudienceは非空の固定値とする。
  • ttlSecondsは1 jobのrequest timeoutとcleanup余裕を満たす値とし、 LARMの上限内でvalidationする。
  • tokenやclaim結果をsettingsへ追加しない。

5.2 Route discriminated union

現行routeをstatic variant、新しいrouteをLARM variantとして明示的なunionにする。 既存JSONでkindがないrouteはstaticとしてparseする。 

type StaticRuntimeSettingsRoute = {
  kind?: "static";
  provider: RuntimeProviderName;
  model?: string;
  localLlmModel?: string;
  providerPoolId?: string;
  fallback: RuntimeFallbackTarget[];
};

type LarmAgentConnectionRoute = {
  kind: "larm-agent-connection";
  connectionId: string;
};

type RuntimeSettingsRoute =
  | StaticRuntimeSettingsRoute
  | LarmAgentConnectionRoute;

LARM variantへprovider、model、fallback、 providerPoolIdを併記することは禁止する。LARM claimが返すproviderを唯一の実行targetとし、 黙示的fallbackを発生させない。

serializerは既存routeへ一律にkind: staticを追記せず、現行settings snapshotと API responseを維持する。settings API、UI、Zod schema、Rust deserializerで同じvalidationを行う。

5.3 Provider pool target

内部provider pool targetへ次のvariantを追加する。

{
  provider: "larm-agent-connection";
  connectionId: string;
}

schedulerはrouteが明示した場合だけこのtargetを生成する。static local-llm targetへ変換したり、claim後のbase URLをsettingsへ書き戻したりしない。

6. Rust resident lifecycle

6.1 State machine

Disabled
  -> WaitingAvailability
  -> Creating
  -> WaitingReady
  -> Claiming
  -> Ready
  -> Renewing -> Ready
  -> Releasing -> WaitingAvailability
  -> Backoff -> WaitingAvailability

connection設定ごとにresident内で一つのLarmConnectionManagerを生成する。 同じconnection設定を参照する複数queue routeはmanagerを共有し、同時createをmutexまたは 単一scheduler ownerで防ぐ。

推奨配置はcrates/context-stilld/src/domains/provider_connection/配下とし、 control client、state machine、claim validation、redacted telemetryをqueue executorから分離する。

6.2 Polling policy

  • 対象routeにdue jobがない間はavailabilityをpollしない。
  • due jobがありconnectionがない場合は5秒を基準に20% jitterを加え、 LARMのretryAfterMsを下限として再評価する。
  • transport error、HTTP 5xx、unknownは5秒から最大60秒まで指数backoffする。
  • unavailable、schema mismatch、unsupported contractは最大5分のbackoffとし、 operator向けにrate-limitした警告を出す。
  • validForMsを過ぎたresponseを利用しない。response cacheを永続化しない。
  • connectionがreadyの場合も、各job開始前に currentConnectionId付きavailabilityを評価する。

6.3 Create, ready and claim

  1. availableを受けたら、explicitAgentProfile: true、 allowFallback: false、deploymentPolicy: existing-onlyで POST /v1/agent-connectionsを呼ぶ。
  2. 一つのlogical create retryでは同じIdempotency-Keyを再利用する。 新しいadmission試行へ移る場合だけ新しいkeyを生成する。
  3. 201または202を受け、terminal failureまたはreadyまでstatusをpollする。
  4. ready後にopenai-provider-v1 formatでclaimする。
  5. claimをstrict validationし、短命targetをmemoryだけに保持する。
  6. ここまで成功した後で初めてSQLite queue jobをclaimする。

availability取得後にPOSTがresource競合で拒否されることは正常なTOCTOU raceである。 queue jobは未claimのまま残し、LARMのretry hintに従ってWaitingAvailabilityへ戻る。

6.4 Claim validation

少なくとも次を検証する。

  • connection ID、Profile、audience、boot epoch、revisionの整合。
  • providerがちょうど1件で、protocolとclaim formatが期待値である。
  • base URLが許可されたscheme、host、port、pathを満たす。
  • model名とOpenAI互換設定が欠落していない。
  • credential typeが対応形式で、expiryが現在時刻より十分先である。
  • provider healthがreadyかつaccepting requestsである。

validation失敗時はLLM requestを送らずconnectionをdeleteし、credentialを含まないerrorだけを記録する。

6.5 Renewal

job開始前に、credentialまたはconnection expiryまでの残時間が requestTimeoutMs + 30秒未満ならrenewと再claimを完了させる。 renewには毎回新しいidempotency keyを使う。job実行中の定期renewはv1では行わず、 job開始時点で十分なlifetimeを確保する。

6.6 Release

次の場合はbest-effortでconnectionをDELETEし、memory上のclaimとtokenを破棄する。

  • 対象routeに次のdue jobがない。
  • job境界のavailabilityがbusy、unavailable、unknown。
  • claim、renew、provider healthまたはrequestの回復不能error。
  • resident shutdown、settings変更、route無効化。

process crashやSIGKILLではDELETEを保証できないため、LARM TTLを最終cleanupとする。 ContextStill再起動後に旧connectionを推測して再利用しない。

7. Queue integration

7.1 Execution sequence

  1. query-only readで対象routeのdue job有無を確認する。
  2. 動的targetならconnection managerからready targetを取得する。
  3. single writer transactionでqueue ownershipと内部provider leaseをclaimする。
  4. immutable execution inputを確定し、writerを解放する。
  5. claim由来のproviderへ外部LLM requestを送る。
  6. single writer transactionでownershipとleaseを再検証して結果をpersistする。
  7. 内部provider leaseをreleaseする。
  8. 次jobの有無とLARM availabilityを再評価する。

connection確保の待機中にqueue jobをrunningへ変更しない。したがってLARMが長時間busyでも、 job attempt、ownership timeout、writer待機を消費しない。

7.2 Foreground activity at job boundary

foreground priorityはjob境界で適用する。LLM request送信後にLARMのprotected runtimeがBUSYへ 変化しても、進行中requestは通常どおり完了または失敗まで処理する。その後は次jobをclaimせず、 connectionを解放する。

この判断により、部分responseの破棄、queue checkpointの曖昧化、強制cancelのprovider差異を v1へ持ち込まない。hard preemptionが必要になった場合は、LARMのcancel契約とContextStillの checkpoint契約を別計画で定義する。

7.3 Failure mapping

Table: Failure mapping
Failure Queue state Action
availability busy／unknown／transport error 未claimのまま managerだけbackoffする
connection POST race rejection 未claimのまま retry hint後にavailabilityへ戻る
ready timeout／claim invalid 未claimのまま DELETE、redacted error、backoff
LLM requestのbusy 503 pendingへ戻す LLM Provider busy 503 contractを適用
job完了後にownership喪失 現ownerを維持 superseded outputをdiscardする
resident crash 既存recovery契約 LARM側はTTLでconnectionをreclaimする

8. TypeScript boundary

TypeScript側は次の責務だけを持つ。

  • settings schema、route union、UI editor、API responseのvalidation。
  • dynamic routeとstatic routeの表示と保存。
  • 構成testと後方互換snapshot。

TypeScriptの明示CLIまたはsidecar executionが動的routeを直接実行しようとした場合は、 dynamic_provider_requires_rust_residentとしてfail closedする。static providerへ 黙示的にfallbackしたり、二つ目のconnection managerを起動したりしない。

9. Security

  • control HTTP clientとprovider HTTP clientはredirectを禁止し、proxy利用を明示的に制御する。
  • response body size、content type、JSON nesting、timeoutをboundedにする。
  • controlBaseUrlとclaimのbase URLはloopback、許可private network、明示host policyに 適合させ、URL credential、query、fragmentを拒否する。
  • tokenをzeroizing memoryで保持し、Debug、panic、error、event、SQLiteへ出さない。
  • promptとcompletionをconnection telemetryへ含めない。
  • claimのexpiryとLARM boot epoch変更を検出したら再claimせずconnectionを作り直す。

10. Observability

次の非機密fieldをstructured telemetryとして記録する。

  • connection設定ID、Profile、route、queue kind。
  • availability state、reasonCode、observed age、poll duration、backoff。
  • create、ready、claim、renew、deleteのdurationと結果分類。
  • connection IDの短いhash、catalog revision、boot epoch。
  • job boundaryで継続、停止、releaseを選んだ理由。

token、authorization header、完全なclaim payload、prompt、completionは記録しない。

11. Implementation phases

  1. Phase 0: LARM変更依頼のcontract testとlive endpointを先に完成させる。
  2. Phase 1: settings union、Rust deserializer、UI/APIを追加する。 defaultはdisabledとし、runtime動作を変えない。
  3. Phase 2: LARM control client、state machine、claim validationをunit test付きで追加する。
  4. Phase 3: findingCandidateだけをfeature flag下で動的routeへ接続する。
  5. Phase 4: live canaryと観測期間を通過後、 episodeDistillerへ展開する。
  6. Phase 5: split execution invariantを再確認して coveringEvidenceへ展開する。
  7. Phase 6: 他のprovider-pool queueは個別のread／execute／persist監査後に追加する。

12. Test plan

12.1 Settings tests

  • 既存settings fixtureが変更なしでparse、serializeされる。
  • static routeのAPI snapshotとUI保存結果が変わらない。
  • LARM routeへstatic fieldを混在させる設定を拒否する。
  • unknown connection ID、重複ID、不正URL、timeout／TTL範囲外を拒否する。

12.2 Connection manager tests

  • due jobがなければavailability requestを一度も送らない。
  • busyまたはunknownではconnectionを作成しない。
  • availableでexactly one connectionを作成し、ready後にclaimする。
  • available後のPOST拒否でqueueをclaimせずbackoffする。
  • 同時tickでもcreate、renew、deleteが重複しない。
  • 同じlogical create retryでidempotency keyを維持する。
  • claim field、host、expiry、healthの不一致をfail closedで拒否する。
  • job deadlineに対してlifetime不足ならrenewと再claimを先に行う。
  • すべての通常終了経路でDELETEを試み、crash時はTTLへ委譲する。

12.3 Queue and fencing tests

  • external connection ready前にqueue rowをrunningへ変更しない。
  • writer transaction中にcontrolまたはprovider network I/Oを行わない。
  • 動的targetでも内部provider leaseを1 jobずつ取得する。
  • connectionを再利用しても次job前にavailabilityを再評価する。
  • foreground busyをjob境界で検出したら次jobをclaimせずDELETEする。
  • job実行中のbusy変化では進行中requestを強制中断しない。
  • ownership喪失後のresponseをpersistしない。
  • provider busy 503を既存retry contractへ正しくmappingする。

12.4 Integration and canary

  1. worker runtimeがCOLD、foreground runtimeがIDLEのbaselineを確認する。
  2. due jobなしでLARM pollとworker起動が発生しないことを確認する。
  3. foreground runtimeをBUSYにし、jobがpendingのままworkerが起動しないことを確認する。
  4. IDLEへ戻し、availability、connection create、ready、claim、job実行を確認する。
  5. 連続2 job間でcurrent connection付き再評価とconnection reuseを確認する。
  6. 次の境界でforegroundをBUSYにし、2件目以降を開始せずreleaseすることを確認する。
  7. queue空でconnectionがDELETEされ、workerが期待どおりCOLDへ戻ることを確認する。
  8. resident kill後にTTLでallocationが回収されることを確認する。

13. Rollout guards

初期releaseでは次を満たすまでdefaultをdisabledのままにする。

  • LARMとContextStill双方のcontract testがgreen。
  • static route regressionがない。
  • SQLite writer hold時間が外部connection待ちで増加しない。
  • busy中にworkerを起動しないcanaryが成功する。
  • tokenまたはclaim payloadがlog、DB、diagnostic dumpへ出ない。
  • connection leakが通常終了で0件、crash後にTTL内で0件へ戻る。

stop conditionは、foreground busy中の誤起動、connection leak、duplicate execution、 ownership fencing違反、static route regression、credential露出のいずれかとする。 発生時はdynamic routeをdisabledへ戻し、static設定には触れない。

14. Acceptance criteria

  1. SAAAから通知を受けず、LARMのAPIだけでbackground開始可否を判定できる。
  2. 空いていない間はqueue jobが未claimのまま保持され、DB writerを占有しない。
  3. 空いた後はexactly one connection、exactly one jobの順で処理を開始する。
  4. 各job境界でforeground優先が再評価される。
  5. 動的credentialとprovider endpointがmemory外へ残らない。
  6. 既存static provider routeと公開settings contractが後方互換である。
  7. shutdown、error、queue emptyでconnectionを解放し、crash時はTTLで回収される。
  8. 単一writer、外部I/O分離、provider lease、ownership fencingを維持する。
