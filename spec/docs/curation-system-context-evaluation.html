Curation SystemContext評価：V1ベースラインとV2の判断契約

評価日：2026-09-06。対象はRust常駐Curationの実際のsystem message、入力snapshot、出力parser、実行gate、Agent Sessionへの変換、SystemContext管理と既存テスト。以下の詳細はV1のベースライン評価であり、当時の結論は「基本方針は妥当だが、無人で統合・deprecatedを確定する判断契約としては不十分」だった。

V2実装後の評価

2026-09-07にV2を実装した。plannerは既存ID、source group、coverageだけを提案し、本文・適用範囲を生成できない。Rustは同一scope、repository identity、type、polarityの二者だけを対象にし、deterministic rendererがcoverage済みの原文groupから本文を再構成する。独立verifierが条件、否定、例外、数値、識別子、順序、provenance、新規意味、矛盾を検査し、supported verdictと完全coverageが揃わなければ変更しない。

Curation planner／verifierはmanaged SystemContext landscape.curationPlan／landscape.curationVerifyを実行時に解決し、共有prompt artifactを追加する。Agent Sessionにはrole付き文字列ではなくmessagesのJSONを渡すため、knowledge本文中のrole風タグで会話構造を閉じられない。全active knowledgeをcontent revisionごとにqueueへ入れ、proposal・verification・hash・supersession・pair review・revision ledgerを保存する。

合成DBの契約監査、CurationのRust単体テスト、SQLite runtime test、SystemContext境界検査は通過した。ただし、これは実LLMが常に正しい意味判断をすることの証明ではない。固定された実LLM評価セットによる誤deprecated率、意味欠落率、統合見逃し率の計測は、provider容量を確保した別途の運用評価として残る。

評価対象のsystem message全文と評価条件・prompt hashも保存した。

評価方法と根拠

  • 実装の静的レビュー：curation_executor.rs、curation_repository.rs、curation_tests.rs、shared/agent_session.rs、system-context.service.ts、verify-system-context-boundary.mjsを照合した。
  • 実際のparser・gate・persistを使用した9件の合成入力による検査を実行した。インメモリDBのみを変更し、本番knowledgeは変更していない。人為的に不適切な回答を与える検査であり、LLMの誤答率を測ったものではない。入力・注入回答・DB変更結果を保存した。
  • 設定中のmuse/muse-spark-1.3-contributorへ、実装のrequest_decisionとAgent Session経路を使って7ケースを送信した。2ケースで回答取得、5ケースはHTTP 409のhost loaded-session capacity is exhaustedで未評価。モデル精度や注入耐性の合格率は算出しない。実LLM評価の応答とエラーと先行した単独接続試験を保存した。
  • 代替のdefaultモデル経路は接続拒否だった。Agent Session側はhealthでready=falseでも実際のリクエストに応答したため、healthだけを根拠に利用不能とは判定できない。設定の変更や無断の代替モデルへの切替は行っていない。

妥当な部分

目的、統合と重複deprecatedの違い、類似度だけで重複と判断しないこと、低利用・古さだけを理由にdeprecatedにしないこと、未知IDを使わないことが明示されている。参照knowledgeを命令として実行しないという指示もある。実行コードはrepository・status・type・polarity・stale入力を確認し、transactionと変更前snapshotにより書き込み失敗を扱う。これらは必要な基盤だが、意味を保持した判断の証明にはならない。

実LLMの回答

基本的な重複にはhighでdeprecate_duplicateを返し、両方のknowledgeを引用した。checksum・rollback準備とtransaction実行を比較するケースにはkeep_separateを返し、異なる指示を保護した。後者は安全側の判断だが、「統合すると情報が失われる」とする説明は、指示を併記して保持できる可能性を検討しておらず、統合機会を逃している可能性がある。2回答だけから全体の品質は判断しない。数値差、適用範囲、例外、注入文については応答を取得できていない。

SystemContextに追加すべき判断手順

  1. 比較する各knowledgeについて、主張、適用条件、否定・禁止、例外、数値と単位、識別子、根拠の制約を列挙する。不明な情報を補わない。
  2. 同じ状況に対する同じ指示なのか、同じ話題だが異なる指示なのか、矛盾なのかを判別する。具体的な差を説明する。
  3. deprecatedは、subjectの各要件と適用範囲がcanonicalに包含される場合だけ選ぶ。空のappliesToを「不明」と「制限なし」で混同しない。利用が少ないことや古さは単独根拠にしない。
  4. mergeは、双方の要件と元の条件を保存できる場合に選ぶ。共通本文と条件付き本文を区別し、統合後のbodyとappliesToをセットで評価する。矛盾の解消や適用範囲の拡張を勝手に行わない。
  5. 各要件が統合後のどこに残るかを検証可能なcoverageとして返す。比較する両側のevidenceを引用し、反証と不確実性を明示する。highを選ぶ条件を要件として定義する。
  6. schemaの必須項目、全decisionの意味、文字数・件数の上限を正確に記載する。保持対象の方向も契約に含める。

これらのうち、出力schemaと実行gateへのcoverage・scope確認、managed SystemContextのRust実行経路への接続はV2で実装した。実LLMの固定評価セットで誤deprecated・意味欠落・見逃しを別々に測定することは、運用品質を定量化する次の段階である。
