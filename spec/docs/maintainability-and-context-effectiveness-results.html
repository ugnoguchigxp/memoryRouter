検索評価で直した問題

ケースからprojectRef・repoKey・repoPathを検索へ渡す。ラベルがないケースはunscored、取得エラーやdegradedはfailedとして記録し、後続のケースを続行する。期待ID・禁止IDの重複、ケースIDの衝突、空結果期待との矛盾を検証する。

完全な関連情報ラベルがあるケースだけで適合率とF1を算出する。ラベル不足はnull、一件も正解に当たらなかった測定は0として区別する。MRR、nDCG、検索時間、実際の空結果数、エラー数、データセットのハッシュを追加した。CLIの--checkでは、空の評価や未採点が合格にならない。

生成入力の欠落と修正

RustとTypeScriptのcomposerは、候補本文を先頭の1文・160文字へ縮めていた。そのため「上限は8」「相対パスを認めない」などの後続条件を、検索が成功していてもモデルへ渡せなかった。

候補ごとに最大1,200文字の本文を渡し、短い資料は改行を含めてそのまま保持する。長い資料は先頭と末尾を残し、省略箇所とtruncatedを明示する。条件・否定・数値・識別子を出力に残す指示と、資料内の役割変更指示へ従わない境界を追加した。Rustのgoalも240文字から4,000文字へ拡張した。長文の中間部分の情報保持には限界がある。

実モデルによる比較

Azure OpenAIで実際に報告されたモデルはgpt-5.4-mini-2026-03-17。12件の仕様判断を各条件1回、合計36観測で比較した。採点用の期待値はモデルに渡していない。知識は固定した21件で、うち8件は履歴スコアが高い無関係な知識、1件は別プロジェクトの知識である。これは検索が履歴スコアに偏る条件を再現するための、意図的に厳しいfixtureである。

結果を使う範囲

今回の課題は改善に使用した固定の仕様判断である。コードを変更してテストを通す一連の実作業、独立した未知の課題、利用者の修正時間については未実証である。採点情報をモデルに渡さないことと、改善から独立した課題で検証することは別である。同じ小規模セットでの100%を一般的な生産性向上率として扱わない。

productionの検索モードは変更していない。Foundationの広範な課題、shadow／canary、遅延・安全条件の検証は未充足であり、promotionEligibleはfalseを維持する。既存の試験レポートだったexperimentコマンドは実装済みだが、結果だけで自動的に有効化しない。

継続検証と実行方法

通常のverifyには、保守性上限、採点情報の非送信、課題の正解情報取得、別プロジェクトの除外、provider失敗の集計、呼び出し上限と順序、Unicodeを含む証拠本文保持の回帰テストを追加した。通常検証は外部モデルを呼ばず、provider経路のテストにはローカルHTTP mockを使う。

実行手順、JSONLラベルと比較課題の定義は検索・生成評価の操作ガイドに記載した。通常のbun run verifyは、保守性・効果回帰・型・lint・整形・Spec・全単体テスト・Webビルドまで成功した。Rust workspaceの402テスト、SQLiteの59テストが成功し、Clippy、rustfmt、SQLite Writer所有権チェックも通過した。PostgreSQLを必要とする結合試験と、本番shadow／canaryは今回の検証に含めていない。
